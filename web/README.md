# janusgate-web — Standalone Web Frontend for JanusGate

> Single source of truth for this project's design and architecture. Contracts and invariants stated here are **normative** for the `web/` workspace.
>
> The JanusGate gateway is normative for everything wire-level. The repository root's `README.md` §7 defines the management API, and the **generated TypeScript bindings (§7) are that contract's machine-readable form** — payload shapes are deliberately not restated in this document, so the two can never drift. When something here disagrees with the gateway, the gateway wins.

---

## 1. Overview & Scope

**janusgate-web** is a standalone, statically-hosted single-page application (SPA) that administers a [JanusGate](https://github.com/EAimTY/janusgate) instance through its versioned management JSON API (`/management-api/v0/*`). It lives in this repository as the `web/` workspace, beside the Rust gateway it administers.

JanusGate itself is **headless**: it exposes three outward serving API families — OpenAI-compatible (`/api/openai-v1`), Gemini (`/api/gemini-v1beta`), and Anthropic (`/api/anthropic-v1`) — beside the management API (`/management-api/v0/*`), and ships no frontend of its own. janusgate-web is the missing control plane UI — deployed **separately, anywhere that serves static files**, talking to any JanusGate instance over the network.

### Deployment model

```text
┌─────────────────────────┐         cross-origin fetch          ┌──────────────────────────┐
│ janusgate-web (static)  │  ─────────────────────────────────▶ │ JanusGate (headless)     │
│ any static host, public │   POST /management-api/v0/<action>  │ anywhere reachable       │
│ no backend of its own   │   Authorization: <token>            │ management_api.token     │
└─────────────────────────┘   Content-Type: application/json    └──────────────────────────┘
```

- **Deploy anywhere.** The build output (`target/web/dist/` from the repository root) is plain static files (`index.html` + JS + CSS). Any static host works; no server-side rendering, no edge functions, no backend of its own.
- **Public by default.** Anyone who can reach the deployed URL can open the app. Opening it grants nothing by itself: every management call requires the target instance's management token, which the app never ships with.
- **First-visit connection setup.** The app holds no connection on first entry, so it presents a connection screen asking for exactly two values: the JanusGate **management API base URL** (e.g. `https://gateway.example.com`) and its **management token** (matching `management_api.token` in that instance's configuration). The pair is verified with one probe call (`POST /management-api/v0/providers:list`) before it is accepted and persisted.
- **Connection persists locally.** The accepted pair lives only in the browser's `localStorage` (key in `src/config.ts`). Returning visits skip setup; a "forget" action clears the stored pair and returns to setup. The app administers one instance at a time.
- **Cross-origin is the normal case.** The app's origin and the gateway's origin are expected to differ, and CORS on the gateway makes that work (§5). No proxying, no same-origin requirement, no backend-for-frontend.

### Goals & non-goals

- **Goals:** one-connection administration of providers, models, serving keys, usage reads, and OAuth flows; zero build-time or deployment-time configuration — the same artifact points at any instance; minimal moving parts (static files + browser `fetch` + one dev-time codegen step).
- **Excluded:** serving inference traffic (clients call the gateway's `/api/*` directly, never through this app); user accounts, roles, or sessions in the app; multi-tenancy; any credential handling beyond the management token and the serving keys themselves — upstream OAuth secrets and provider API keys are minted inside JanusGate by its own flows, and the app only relays the administrator's input, while serving-key secrets are typed or locally generated in the app and relayed to the gateway. Request content — prompts, completions, headers — is never shown anywhere: usage reads carry ids and numeric facts only.

## 3. Connection Model

A **connection** is the pair `{ baseUrl, token }`:

- `baseUrl` — the JanusGate instance's origin (scheme + host + optional port), e.g. `https://gateway.example.com`. It is normalized once at setup: surrounding whitespace is trimmed and trailing slashes are stripped, so composing `{baseUrl}/management-api/v0/<action>` yields exactly one `/` per boundary. Only the origin is entered; the management path is fixed by the contract.
- `token` — the instance's management token, sent verbatim (§3.3). It is never rendered back in full, never written to the URL, and never logged.

### 3.1 Lifecycle

1. **Absent → setup screen.** With nothing stored, the app renders only the connection form (base URL + token). This is the first thing any visitor sees.
2. **Verify → persist.** Submitting fires the connection probe — `POST {baseUrl}/management-api/v0/providers:list` with an empty `{}` body — carrying the candidate token, under a 15-second deadline (`connectionProbeTimeoutMs` in `src/config.ts`, applied through the `deadlineController` of `src/connection/deadline.ts`) so a dead address cannot hold the submit busy on the browser's full fetch timeout. Only a `200` persists the pair and enters the app; any failure (network error, non-2xx, non-JSON, a contract-violating body) keeps the user on setup with the failure reason shown. A cancel while the probe runs is control flow, never a refusal: it aborts the attempt and reopens the form — the token, the inline errors, and any diagnosis cleared, and the address too unless the screen had seeded it (a mid-session 401's, a forget's, or any refusal's), since losing that seed would demand exactly the origin retype it exists to spare — while a refusal that lands after a cancel still seeds the address as every refusal does.
3. **Stored → administer.** Returning visits read the pair from `localStorage` and go straight to the app. The stored pair is re-validated lazily: the first management call answering `401` (errno 2) proves the token dead, which clears the stored pair and returns to setup with an explanatory message and the address field seeded with the address the app already knew — the token is never restored, since re-entering it is the point of the reconnect.
4. **Forget.** An explicit action clears the stored pair and returns to setup with the address field seeded with the address the forgotten connection served — the token is never carried, since re-entering it is the point of the rotation.

### 3.2 Addressing

- The management API root is therefore `{baseUrl}/management-api/v0`, and every route is a **`POST`** to `{management root}{path}` — the paths in the generated route table are relative to the version, e.g. `{baseUrl}/management-api/v0/providers:list`.
- Readiness to construct a path from the route table is the reason the version segment is fixed by the contract rather than user-entered: the app never concatenates a version it does not own.

### 3.3 Authentication on the wire

Every management call sends the token verbatim in the `Authorization` header **without any `Bearer` prefix**:

```text
Authorization: <token>
Content-Type: application/json
```

This matches JanusGate's management authentication exactly (a `Bearer`-prefixed value is rejected with `401`). Comparisons on the gateway side are constant-time; a mismatch yields errno 2 / HTTP 401. Requests carry no cookies — the app sends `credentials: "omit"` and never sets or reads cookies.

## 4. Management API Contract

### 4.1 Where the contract lives

**The generated bindings are the contract's single machine-readable home.** Every request and response payload type, the route table (path → method → request/response type), the errno taxonomy, and the closed vocabularies (provider kinds, discovery states, request-accounting sets) come from the gateway's own generator — the Rust sources at the repository root (§7 of the root `README.md`; the generation workflow is §7.1 below). Application code imports them and never restates a payload shape.

This section documents only what the types cannot carry: the transport-level rules, the error taxonomy's client-side meaning, and the semantics that live in the gateway's prose (two-state fields, full-state writes, single-use OAuth states).

### 4.2 Transport

- **Every route is `POST` with a JSON body**, carried by `Content-Type: application/json`. No method carries semantics; reads and writes are distinguished by the action name (`providers:list` vs `providers:create`), and a no-argument request sends an empty `{}` object.
- **The version prefix is not optional.** `{baseUrl}/management-api/v0/<path>` is the only addressable root; a path outside the version prefix is answered with an **empty 404** that carries no errno body and involves no authentication — the auth middleware wraps the version router only, so this 404 renders even for a wrong token — while a path beneath the version that matches no route is answered with the version's errno-shaped 404 (there authentication applies first: an unauthorized request is rejected with 401 before the 404 is produced). A non-JSON body therefore means "this is not the management API", and the client reports the HTTP status alone.
- **Body limit is 2 MiB** for the whole management surface; a larger body is rejected with errno 7 (413).
- **A wrong method on a known path** is rejected with errno 8 (405) and an `Allow` header; a wrong or missing `Content-Type` is rejected with errno 9 (415) before any parsing. Both are client bugs in this app, never user-recoverable states.
- **Preflight `OPTIONS` requests are answered by the gateway's CORS layer, before authentication** — that is what makes the cross-origin flow work without a token on the preflight (§5).

### 4.3 Error taxonomy

Failures render `{"errno": <number>, "message": <string>}`. The errno is from the version's closed taxonomy, and each errno pins exactly one HTTP status:

| errno | Category | HTTP | The app's reaction |
| :--- | :--- | :--- | :--- |
| 1 | `invalid_request` | 400 | Show `message` — a rejected field or malformed body; a bug in the app's own request construction |
| 2 | `unauthorized` | 401 | Clear the stored connection and return to setup (§3.1) |
| 3 | `not_found` | 404 | The addressed row is gone: refresh the listing and show `message` |
| 4 | `conflict` | 409 | Show `message` — a taken name or a colliding model ID; resolve by editing the input |
| 5 | `upstream_error` | 502 | Show `message` — the gateway's upstream failed; the foreign status is inside the message, never the HTTP status |
| 6 | `internal` | 500 | Show `message` — a gateway fault |
| 7 | `payload_too_large` | 413 | Client bug (the app never builds bodies near 2 MiB) |
| 8 | `method_not_allowed` | 405 | Client bug |
| 9 | `unsupported_media_type` | 415 | Client bug (the app always sends `Content-Type: application/json`) |

Messages whose cause is internal render a fixed category message; the underlying cause is in the gateway's log, not on the wire. The app never invents a message of its own for a management failure — it renders the gateway's `message` verbatim.

### 4.5 Semantics the types cannot carry

These rules come from the gateway's design and must be honored by every call the app makes:

- **Entities are addressed by id.** Providers, physical models, pools, public routes, and API keys each have their own never-recycled row identifiers. Physical models contain exact account-local upstream IDs and capability facts; they do not contain public IDs or overrides. Public routes own the explicit globally unique client-facing `public_id` and target either a physical `model_id` or a `pool_id` plus exact `upstream_id`. Discovery and model creation automatically expose standalone models as `provider.model_prefix + upstream_id`. Any pool membership suppresses those entries; each containing pool exposes its member inventory union as `pool.model_prefix + upstream_id`, selecting only members that possess the exact model. Renaming an account changes its label without changing a route or client identifier. Name conflicts return 409 without overwriting another entity.
- **Fields are two-state, never three.** A field is either always present (required, nullable only where it mirrors a nullable storage column: `expires_at`, a provider row's `base_url`, availability `blocked_until`, a model row's eight capability columns — the four discovery-owned base facts and their four administrator overrides — an `api_log` row's `http_status`, `upstream_http_status`, and five token columns) or **absent-keeps** (omissible, never `null` — the write-only secrets `api_key` and `credentials`, the `usage` reads' paging fields, and every field of the shared usage filter (README §7.1)). The bindings render these as `field: T | null` and `field?: T` respectively. Sending `null` where absence is the only alternative is a 400; sending `null` for a mirror column is meaningful and kept.
- **Machine-consumed text is routing-safe.** Exact upstream IDs, public route IDs, serving-key secrets, upstream static keys, hand-replaced OAuth credential fields, and provider base URLs use printable ASCII without whitespace. Model identifiers additionally exclude `/` and `:`; a base URL is a nonempty `http://` or `https://` address. Human account, pool, and serving-key labels remain free-form. Automatic public IDs concatenate the standalone provider or pool model prefix and exact upstream ID. Additional aliases are authored explicitly; there is no physical-model ID override.
- **Updates are full-state writes.** `providers:update`, `api-keys:create`, and `api-keys:update` state the row's *complete* desired readable state; `models:update` states the complete state of the row's writable settings, and `models:create` the complete desired initial state — an omitted required field is a 400, not a "keep". Consequently every edit in the app is a **read-modify-write**: render the row, change the one field the administrator touched, send the whole row back. `models:create` is addressed by a fresh (`provider_id`, `upstream_id`) natural key.
- **Write-only secrets are the exception**: omitting `api_key` (static-key providers) or `credentials` (OAuth providers) keeps the stored secret, so the UI never has to re-collect a secret it cannot read back. Serving keys are the counter-exception: `api-keys:list` and `api-keys:create` return the plaintext `key`, because the administrator needs it to configure serving clients — the UI shows it in full with a copy action.
- **Responses carry only what the caller cannot derive.** `providers:update`, `providers:delete`, `api-keys:update`, `api-keys:delete`, and `models:delete` answer `{}`; `oauth:reauthorize` answers the new flow's `grant`-discriminated start union (`StartProviderOauthResponse`); `models:discover`, `models:create`, and `models:update` answer the fresh physical inventory rows; `api-keys:create` answers the server-assigned `id` and `created_at`; the definition write routes answer the stored version's identity. A `usage:list` page's next cursor is the last returned row's `started_at`, which the client derives; a definition listing's latest version of a name is likewise the client's derivation (`MAX(version)` over the listing), never a movable alias the server substitutes. The app installs what a response carries instead of refetching it, so a discovery, a model write, or a key creation needs no follow-up read; a write answering `{}` refetches the listing it can change (§6.3). A row never carries a verdict the caller derives — the three-input effective serving state and each capability's effective declaration (`override ?? base`, with its overridden/discovered/unknown provenance) are computed client-side from rows the app already fetches — and a usage row or bucket never carries a name: labels resolve through the entity lists.
- **Nothing is created or deleted implicitly.** Model rows arrive through `models:discover` or `models:create`; `models:update` never creates a row (an unknown `model_id` is a 404) and never touches `discovery_state` or the capability base columns, so it cannot restore a vanished row — recovery is an upstream reappearance or a `models:create` claim of the vanished natural key, which resumes service under the requested state. Discovery never deletes a row: an unlisted row is marked `vanished`, keeping its curated columns while its capability base columns are rewritten to the latest extracted facts, and only `models:delete` removes one (a deleted `discovered` row returns as a new row with a fresh identity on the next discovery). Providers of the two OAuth kinds are created only by `oauth:complete` — `providers:create` is static-key-only. Serving keys arrive only through `api-keys:create`; deleting a key revokes it and cascades its model access rules while historical accounting remains. An upstream reporting no models rejects the discovery before any write, so curated rows are never mass-vanished by an empty report.
- **Route targets change independently of public names.** Moving a public route from a direct model to a pool retains its public ID unless the administrator explicitly edits it. Several public routes may reference the same target. Physical-model deletion cascades its direct routes; disappearance during discovery suspends them while preserving their identities, and rediscovery restores eligibility. Authored routes prevent deleting their referenced pool until removed or retargeted. Pool deletion removes its automatic entries and restores standalone entries for providers leaving their last pool.
- **OAuth states are single-use and expire after 10 minutes.** A completion consumes the state even when the token exchange then fails, so a failed completion restarts with a fresh `oauth:start`. Rejections computed before consumption (an empty or malformed `code`, a grant mismatch) leave the pending flow intact; a taken creation name is not one of them — the consume-then-fail order spends the flow and only then answers the name-taken 409 (root README §7.1), so that failure too restarts with a fresh `oauth:start`.
- **A filtered `models:list` for an unknown `provider_id` yields an empty list**, not a 404 — a filter addresses no row. The app must not read "no models" as "provider missing"; the provider list is the authority on existence.
- **Closed vocabularies are enumerated once, exhaustively.** The provider kinds, the discovery states, and the request-accounting sets (`ApiLogEndpointType`, `ApiLogOutcome`, `UsageGroupBy`) arrive as plain unions with no runtime list, so `src/management-api/vocabulary.ts` holds one `Record<Union, …>` per vocabulary: the record type is exhaustive, so a variant added to the contract fails to compile until it is listed, and the select options, display labels, and wire-value narrowing all derive from that one declaration. Reasoning effort is the gateway's own closed vocabulary — `none | minimal | low | medium | high | xhigh | max`, parsed per surface and rendered verbatim into the target upstream's parameter, never mapped across vocabularies — and the value domain of the per-model capability declarations: the model detail page states each effective set with its provenance, and the model forms override per field (an empty level selection declaring no levels, a token override naming a positive integer). No accounting row carries one.

### 4.6 Client-side discipline

- **Unknown input is narrowed explicitly.** Every management response is validated before use (object shape, required keys, value types). A body that does not match the expected shape is a contract violation: the app reports it as an error rather than rendering partial data or defaulting fields. No `any`, no unchecked assertions.
- **Read-modify-write adapters construct requests field by field** — never by spreading a response row into a request body. A provider row carries `id` while its update request carries `provider_id` and restates every readable field, so a spread would smuggle `id` into the body, which the gateway's strict parsing rejects with a 400. Each adapter is one explicit mapping from a listed row to that row's update request, per wire field set — the provider update is one branch, since rows of both credential kinds (`api_key` and `oauth`) share one wire shape.
- **Errors are rendered, not swallowed.** The gateway's `message` is what the administrator sees; the errno drives control flow (§4.3).

## 5. CORS & Hosting Requirements

Cross-origin calls are the normal operating mode, and they impose exactly one requirement on each side:

- **Gateway side.** The administered instance's `management_api.cors.allowed_origin` must include the origin janusgate-web is served from (a specific origin such as `https://admin.example.com`, or `"*"`; an empty list disallows all cross-origin requests), otherwise the browser blocks every management call before it leaves. `management_api.cors.allow_private_network` additionally governs Private Network Access preflight for instances on private networks. Both live in the instance's JSONC configuration file; changing them means editing that file and restarting the gateway. Preflight `OPTIONS` handling and CORS response headers are entirely the gateway's job.
- **App side.** Nothing special: plain `fetch` calls carrying `Authorization` and `Content-Type: application/json` (both non-safelisted, so preflights happen — expected and answered gateway-side), with `credentials: "omit"`.
- **Static-host SPA fallback.** Client-side routes (deep links into the app) require the host to serve `index.html` for unknown paths. The app's own router treats unknown client routes as not-found.

## 6. Application Shell, Routes & Screens

### 6.1 The shell
The app has exactly two top-level states, chosen by the connection state (§3.1):

- **Unconnected** — the connection screen fills the viewport; nothing else exists. It states what JanusGate is, what the visitor needs before connecting, and — when the probe is refused — the app's own diagnosis of why. That screen is the first contact most operators have with the product, and a cross-origin refusal is the failure they are most likely to meet.
- **Connected** — the admin shell: a top bar (the mark, a three-state theme switch, and a confirmed *disconnect* action, whose armed confirm asks the question and states the consequence — reconnecting means entering the token again), a context bar (the `Overview` / `Providers` / `Inventory` / `Pools` / `Public routes` / `API keys` / `Usage` navigation, the instance address, the validity stamp of the last read, and *refresh*), the routed screen, and a quiet footer naming the connected instance.

The document title follows the state the app is in, derived in one place beside the routes: unconnected, the page is the connection screen (`Connect to JanusGate`); connected, it is the routed screen's name, worded as the screen's own heading, with the identifier of the row the route addresses where it carries one (`Providers · JanusGate`, `Edit provider #12 · JanusGate`, `Create model · JanusGate`, `Page not found · JanusGate`). The browser's tab, history entries, bookmarks, and screen-reader page announcements therefore say which screen — and which row — they hold, across the multi-tab use the addressable, filter-is-the-route URLs invite.

The shell is created per connection: the connection object keys the boundary, so a different instance gets a fresh shell, a fresh management API client, and fresh screen state — nothing can leak across instances. The token is never rendered; the address and the read's timestamp are the only connection facts the shell shows.

*Refresh* bumps one counter in `src/refresh-state.ts`; the mounted screen re-runs its read when it moves, and reports the moment a read succeeded, which is what the validity stamp prints. The stamp prints the bare wall clock while the read is from today, and the date beside the clock once it is older, so a lapsed stamp reads as stale at a glance rather than as current — it never ages on a timer, so the shape must stay truthful without re-renders.

All of them are deep links, so the static host must serve `index.html` for unknown paths (§5). The OAuth flows are steps inside the provider creation and reauthorization forms, not destinations of their own.

### 6.3.1 Upstream quota on provider details

Every quota observation carries explicit routing applicability: `monitoring_only`, `all_models`, or `models` with a nonempty set of exact upstream IDs. Presentation labels and named scopes never select models. The authored descriptor defaults omitted applicability to monitoring; model selectors preserve literal, required field, and map-key contexts, and a map-key selector requires a map source. The full definition editor and stored-definition decoder retain these recipes, while the observation decoder rejects missing or malformed applicability before rendering any rows. Existing researched presets remain monitoring-only until upstream evidence supports stronger routing claims.

The inference descriptor may also declare `quota_exhaustion` with an ordered nonempty list of exact rejection rules. The definition editor validates unique nonempty rule names, nonempty non-success HTTP status sets, a nonempty object-member code path with an exact string value, ordered restriction-key recipes, and account-wide or requested-model applicability. Rule order and identity segments are preserved; status sets are deduplicated and sorted to match gateway storage. An explicitly empty code string is valid, while status-only rules, regexes, and unknown members are rejected. These descriptors configure upstream rejection classification independently of quota observation recipes.

The *Upstream quota* card reads independently of provider/model listings, discovery, editing, and the gateway-accounting Usage card. It resolves capability by the exact `(provider_definition_name, provider_definition_version)` in the loaded definition catalog; a failed catalog read is an inline failure, never an unsupported verdict. A supported mounted identity starts in *Quota not observed*. Only *Refresh quota* or *Retry quota* starts an upstream quota request. The mounted controller lives outside keyed card renders, so ordinary row reloads, enabled toggles, focus changes, and local timers cannot poll quota. No list or overview probes quota.

The observation belongs to the upstream account and may include other clients. Supported but unobserved viewing, unsupported viewing, valid empty success, unknown measurement, zero use, unlimited, initial failure, and a failed refresh are distinct states. Refresh retains the old rows while loading and, on failure, states *Showing the previous reading.* beside the original observation time and age. Success replaces the entire snapshot, removing vanished entries. One immediate in-flight guard suppresses duplicate actions. Every nested wire variant has a closed shape; numeric domains, dates, safe integer timestamps/durations, and tuple identities are validated before any rows render.

Ratios show percent used to one decimal place, including over 100%; counters show used/limit and their declared unit. Remaining-only values have neither an inferred total nor a progress bar. Unknown and unlimited have no zero progress bar. Ratio/counter fill is visually clamped to 0–100, with accessible text preserving the actual observation. Durations state fixed elapsed units, calendar months say *Monthly*, and absent periods say *Period unknown*. Absolute reset times use the existing locale formatter and a local countdown; after the instant passes the old measurement remains with *Reset time reached; refresh to update*. Date-only resets display the original calendar date and *Exact reset time unknown*, with no timezone conversion or countdown.

The identity includes the management client/connection, provider ID, exact definition pair, base URL, and the controller's local generation. Replacing credentials, reauthorizing, or saving base settings occurs on the edit screen; leaving and remounting details discards the old observation and starts fresh, without exposing secrets or adding a server credential revision. Superseded requests abort where supported; both late successes and failures are ignored by generation and signal checks, including management 401 responses arriving from an aborted transport. Current inbound management authentication still resets the connection; an upstream quota 401/429 is a 502 confined to the card. Observation-age and countdown timers update only local text and are cleaned up on disposal.

The preset catalog contains quota recipes for five researched products. [Fixture provenance](../fixtures/quota/README.md) pins request, credential, and response evidence; every quota addition remains unverified by a live upstream query. The authored-definition validator, full JSON editor, stored-definition decoder, and base-URL inference preserve quota alongside the other independent descriptor sections. Generic/Zen recipes and Devin's documented credential gap remain unsupported.

### 6.4 Failure handling
- **401 (errno 2)** — the client hands the gateway's message to the connection service, which clears the stored pair; the connection screen explains it (§3.1). Nothing is retried with the dead token. The failure is stored whole — message, cause, and the address it addressed — so the screen can diagnose a rejection that happened while another screen was mounted, and the screen reseeds its address field from that address; the token never travels with the failure, because re-entering it is the point of the reconnect.
- **Every other failure** — the message is rendered where the action was taken, in the app's own diagnosis (`src/management-api/diagnosis.ts`). The gateway's message is kept verbatim as the detail whenever the gateway rendered one; a call the browser refused before it left keeps its original transport diagnostic beside the localized explanation (next bullet). The app adds only what it can be certain of: an unauthorized answer names `management_api.token`; an upstream refusal during discovery states both recoveries its indistinguishable causes admit — the gateway fails a refused call and an upstream genuinely listing no models alike (root README §7.1) — so the OAuth kind pairs reconnecting with the manual add, and the static kind the base-URL and API-key fix with it; an internal failure names the gateway's stderr log; and a conflict names the identifier that collided.
- **A call the browser refused before it left** is the one case the gateway cannot explain, so the connection screen probes the instance's origin with a no-CORS request (`probeReachability`): a resolved opaque response proves the network path, which makes the failure a CORS block, and a rejected probe makes it an address nothing answers; where no probe ran, the diagnosis states both causes rather than guessing. The refinement probe runs under the same 15-second deadline the connection probe itself carries (`connectionProbeTimeoutMs`, §3.1), so the "Nothing answered" refinement lands within that budget instead of pending minutes behind an address that never answers; an aborted probe — the deadline's expiry included — is never read as an answer about the network, so it classifies as "unknown" beside the no-probe case, never "unreached". One pairing needs no probe at all: an HTTPS page calling a non-loopback HTTP address is refused by the browser deterministically before any request is sent, and the diagnosis states the blocked mixed content outright, naming the two remedies — serving this app over HTTP as well, or adding `tls` to the gateway — while a loopback HTTP address keeps the probe, since the browser does not block it.
- **404 (errno 3)** — the addressed row is gone: the message is rendered and the listing that showed the row is reloaded, so the screen stops showing state the gateway no longer holds; the detail screens say so in place and offer the routes back.
- **Aborts** — navigating away cancels in-flight calls; an aborted call renders nothing.

### 7.1 Generated bindings

The wire contract enters this workspace as **generated TypeScript**, produced by the gateway's own generator from the Rust sources at the repository root — the gateway declares each route once (method, path, request type, response type) and emits the payload declarations plus the route table. Nothing about the management API is hand-written here.

```bash
npm run generate-bindings
```

The script is one command, inline in `package.json`, and does exactly this:

1. remove the previous output directory, so no stale artifact from an older layout survives;
2. run the gateway's bindings generator against the repository's local working tree (`cargo run --manifest-path ../Cargo.toml`, with the `management-api-typescript-bindings` feature), writing `src/management-api/generated/v0.ts`.

Properties of this arrangement, all deliberate:

- **The gateway is the only source of truth.** The Rust types are the schema; the generator derives the bindings from them, so the app cannot hold a stale copy of a payload shape without failing to compile against the regenerated file.
- **The output is a build artifact, not source.** `src/management-api/generated/` is gitignored (and therefore also outside Biome's scope, which reads `.gitignore`). A fresh checkout must run `npm run generate-bindings` before `npm run typecheck`, `npm run build`, or `npm test` once application code imports the bindings.
- **The bindings regenerate from the local working tree.** A management-API contract change and its web adaptation are one atomic change: the generator runs against the same tree being edited — no clone, no network, no push-then-regenerate round trip. Regenerating against a different gateway revision means checking out that revision and running the script again.
- **It is a dev-time step, not a build step.** Running it requires a Rust toolchain; the first invocation compiles the generator, and subsequent ones are incremental. It is never wired into `npm run build`, so the deployed artifact is built from TypeScript alone.
- **The generator is idempotent and deterministic**: the same gateway revision always renders byte-identical output.

## 8. Configuration

There are two kinds of configuration, strictly apart:

- **Connection (runtime, per browser).** The `{ baseUrl, token }` pair from §3, stored in `localStorage` under the key in `src/config.ts`. No build-time or deployment-time values exist — the same `target/web/dist/` artifact administers any instance. Rotating a gateway's management token invalidates stored connections; the app recovers through the 401 path (§3.1).
- **Theme preference (runtime, per browser).** Light, dark, or the operating system's — stored in `localStorage` under its own key in `src/config.ts`, painted before the first frame by the inline bootstrap in `index.html`, and holding no secret. The top bar's control cycles light → dark → system and back, its glyph and label naming the state in force and the state one click away, so the operating system's choice — the initial value — is reachable again after any explicit departure.
- **Tunables (build-time, in code).** Every non-secret configurable value lives in `src/config.ts`, its single home. Changing one means editing the module and rebuilding. No runtime environment variables are read (`import.meta.env` is not a configuration mechanism here) — a static artifact that behaved differently per host via env injection would break the one-artifact-anywhere promise.

No secrets ever appear in code, in `src/config.ts`, or in this workspace. The management token exists only in the administrator's browser storage and on the wire to the configured instance.

## 9. Conventions

The normative rule list is `AGENTS.md`; this section orients:

- **Imports:** `/` is the `web/` root. Prefer root imports (`/src/...`) unless the module is in the same folder (`./module`) or a sibling subtree (`../folder/module`). Generated files are exempt from this rule but should be imported through the same root style.
- **Types:** strict TypeScript throughout — no `any`, and no assertion a preceding runtime check does not justify; unknown input (notably every management API response) is narrowed through explicit validation; exported functions and component helpers carry explicit return types.
- **Generics:** all-or-nothing naming per parameter list (single-letter when simple; otherwise every parameter multi-letter with a `T`-prefix for types / `F`-prefix for callbacks describing its role).
- **Booleans** carry predicate-style prefixes (`is`, `can`, `has`, `should`); names are unabbreviated (`id` and the usual short auxiliaries excepted).

TDD: write tests first for non-trivial logic; keep tests cohesive and aimed at first-party domain logic (URL normalization, response validation, read-modify-write adapters, connection state transitions, failure diagnosis, formatting), never at framework primitives.
- **Visual language:** every colour comes from the token set in `src/tailwind.css` (light by default, dark on demand); no ad-hoc values, no shadows, no state carried by colour alone (every status is icon plus words). `web/DESIGN.md` is the world's rulebook.
- **Docs first:** `README.md` is the source of truth — every behavior change updates it alongside the code.

## 10. Security Notes

- **Public app, secret-gated control.** Anyone opening the deployed URL sees the connection screen (or the admin shell); controlling an instance additionally requires its management token. The app's hosting needs no access control of its own for this to hold — but the token lives in that browser's `localStorage`, so only open the app in browsers you trust (any script running on the app's origin could read it; the app therefore ships zero third-party assets beyond its bundled code).
- **Token handling.** The token is sent only to the configured `baseUrl` (plus its `/management-api/v0/*` paths) and nowhere else; it never appears in URLs, logs, or error reports. A 401 anywhere clears it from storage immediately rather than retrying with it.
- **No sessions, no cookies** — none are set, sent, or read anywhere, matching the gateway; cross-origin calls explicitly opt out of credentials.
- **Transport.** Serve janusgate-web over HTTPS and point it at HTTPS gateway instances; otherwise the token crosses the network in cleartext. The app does not warn or enforce this — the deployment does.
- **CORS as allowlist.** A gateway listing `"*"` in `management_api.cors.allowed_origin` accepts management calls from any website. Because the token lives in this app's origin-scoped storage (not in a cookie), a foreign origin cannot borrow it — but prefer pinning the exact app origin anyway.
- **Upstream secrets stay in the gateway.** The app collects OAuth authorization codes (which it relays immediately to complete a flow) but never stores, displays, or logs them; provider credentials and upstream API keys are write-only from the app's perspective and are never returned by any route. Serving keys are the exception: the gateway returns them in full so they can be copied into client configuration — they are shown as data with a copy action, and never placed in a URL, a log, or storage beyond the gateway's own answers in memory.

## 12. Invariants

1. The same static artifact administers any JanusGate instance; no instance address or token is ever baked into a build.
2. The connection pair exists only in the browser (`localStorage` + memory) and on the wire to the configured instance — never in code, config, URLs, or logs.
3. Every management request is a `POST` to `{baseUrl}/management-api/v0/<path>` carrying `Authorization: <token>` verbatim (no `Bearer` prefix) and `Content-Type: application/json`; any 401 clears the stored pair and returns to setup.
4. Payload shapes are never restated in this workspace: the generated bindings are the contract, and application code compiles against them. A body that violates the expected shape is reported as an error, never partially rendered.
5. Reads that mutate (updates, deletions, creations) follow the gateway's full-state and two-state rules: complete desired state on update and create, omission — never `null` — for write-only secrets, explicit field-by-field construction rather than spreading a row into a request. Serving-key secrets are the readable exception: they are restated like every other field and shown in full with a copy action.
6. No request, response, token, or usage data is persisted anywhere except the connection pair in `localStorage`.
7. The wire contract is owned by the gateway's `README.md` §7 (the repository root) and its generated bindings; on any conflict with this document, they win.
8. The artifact carries no asset files — no fonts, images, or third-party scripts — so the token in this origin's storage is reachable by no code the app did not ship; the app's marks are drawn SVG and its type is the platform's own stack.
9. Every failure is explained where it happened: the gateway's message is rendered verbatim, the app's own diagnosis adds only what it can prove, and no failure is swallowed or replaced with a generic notice.
10. The outward surface paths the console prints are the gateway's own (root `README.md` §1 *Outward Protocols*) and the only endpoint advice the app gives: routing is by public model ID alone, so no screen may present a provider kind or a model as bound to one surface.

### Serving-key model access

Key creation, editing, and detail read provider, pool, physical-model, and public-route inventories through the existing management list actions. Creation participates in the normal read/cancellation/notice/Refresh lifecycle and cannot submit before the first required inventory success. Reads never poll upstream quota or definitions for permission editing. The key list stays a navigation surface without these inventory reads. New drafts explicitly start with deny and empty arrays.

Model access shares the settings form and its single full-state save: default Allow/Deny, provider and pool defaults with Inherit/Allow/Deny, and public entries grouped by current typed owner with the same choices. Direct ownership resolves the physical target's provider; Pool ownership is the target pool, never a member provider. Automatic entries, aliases, globally disabled and surviving unavailable entries remain editable, and owners without routes can specify defaults for future entries. Public-ID/owner-name search and Overrides only hide rows without altering policy. Effective permission and its key/provider/pool/model-override source are shown separately from structural availability. A pool grant includes future eligible members, and lower defaults affect existing inheriting entries.

Draft edits are immutable. Inherit removes exactly the addressed rule; explicit decisions equal to inherited defaults remain pinned. Generated policy types travel through response validation, complete-state adapters, equality, dirty tracking, refresh holds, save reconciliation, secret rotation, and enable toggles. Array reorder alone is not a change. Refresh recomputes labels, grouping, and inherited previews while retaining dirty authored intent; server permission changes participate in row holds. Deleted references remain visible as “Deleted provider/pool/route #ID” with their decisions and Remove override. Known missing references block submission until explicitly removed or resolved by refresh. A racing 404 retains the draft and offers refresh/retry through the existing action flow. Successful save reconciles the full submitted state. Key detail shares the read-only resolver and grouping, with an Edit API key link beside Secret, Details, and Usage. Deletion removes rules and keeps accounting.

## Localization

The static SPA owns localization under `src/i18n/`. Six languages ship: English (`en`), Simplified Chinese (`zh-CN`), Traditional Chinese (`zh-Hant`), Japanese (`ja`), Korean (`ko`), and Spanish (`es`). Every language is a complete, standalone nested literal catalog of equal structure in `src/i18n/catalogs/`, and no catalog derives from, extends, or overrides another — there is no base-plus-translations representation. English is the only eagerly bundled catalog: it is the synchronous bootstrap and the browser's final fallback, while the other five load as separate on-demand chunks through entry-shaped loaders that are identical for every language. Traditional Chinese is authored directly in Taiwanese terminology, never produced by converting Simplified Chinese. One private i18next instance registers immutable resources in the `translation` namespace. Components read `translation()` and call its typed selector API in tracked presentation computations; the facade returns the committed fixed translator. Routes, forms, management clients, and OAuth lifetimes do not depend on language. English resource types are the compile-time selector inventory, while development checks validate every translated resource independently of its literal values and grammatical plural categories.

The language preference is `system` or a registry tag, persisted under `janusgate-web:language`. Browser matching considers `navigator.languages` in order, then matches exact canonical base tags, explicit or inferred language-script tags, and the language's declared default. Chinese resolves through the inferred script, so a `zh-TW`, `zh-HK`, or `zh-MO` browser selects `zh-Hant` while a bare `zh` selects the `zh-CN` language default. Malformed external tags are ignored. Unsupported candidates fall through to the next browser preference; English is the final fallback. Display formatting uses the committed catalog tag rather than a separate browser region preference. Disconnecting or forgetting an instance does not change language.

Startup initializes theme, awaits localization, and mounts the app once. A failed preferred catalog mounts English while retaining the requested preference for Retry. During later switches the previous activation stays visible until the requested catalog is ready. Requests are identified monotonically, including requests for an already active locale; superseded results cannot activate or persist. Pending loads share one promise per locale, successful resources stay cached for the session, and failed loads are retryable. The 15-second deadline is declared in `src/config.ts`. A late import can warm resources but cannot activate a timed-out request, and old cleanup cannot remove a newer retry. Storage refusal leaves the successful in-memory choice intact. `languagechange` follows current system intent, including a pending system switch, while explicit intent ignores it. Controller disposal removes listeners and timers. Pending intent is published synchronously before browser events can inspect it: Solid 2 schedules imperative signal writes, so the controller flushes the request-state update before awaiting its loader. Locale activation still commits the translator, tag, preference, and idle state in one snapshot.

To add a language, create a complete nested literal catalog with `as const` in `src/i18n/catalogs/`, add a canonical BCP 47 tag, autonym, and explicit dynamic loader to the registry, and declare the language default. Add the catalog to the development gate's static imports. Components must not introduce locale-specific branches. To add a message, author English and every shipped translation together and use a semantic selector at the presentation boundary. Catalog groups follow one placement rule: a screen's own copy — its heading and description, back labels, empty states, row marks, and stated trades — lives under `screens.<screen>`, while `helpers` holds copy owned by shared cross-screen components and feature helpers (tables, forms, the usage filter, access control, row-not-found, the preset catalog) and never carries a screen-named group. New message keys are semantic — the key names the message's role (`usageBackLabel`, `invalidStatusList`, `noModelPrefix`), not its English sentence spelled out in camelCase; the sentence-shaped keys already present in the catalogs are historical and are not a pattern to extend. Plural messages use native i18next suffixes and declare their semantic path and cardinal/ordinal kind in `metadata.ts`; call them with `count`, including zero. Resources must have equal semantic inventory, placeholder sets, and declared rich slots, while plural categories follow each locale's `Intl.PluralRules` contract. Never store a translated sentence as domain state or interpolate translated HTML.

`npm run check:i18n -w web` runs the catalog gate. Repository `npm run check`, `npm run test:web`, and `npm run build:web` include these checks. Catalog validation is development-only and is absent from the production import graph. Resource typing rejects unknown selectors; compile-only fixtures document the installed i18next release's interpolation guarantees.

Presentation formatting reads the committed catalog locale through cached named `Intl` formatters. Counts retain reported zero and render absent usage as `—`. Absolute instants use the browser-local zone with an explicit Gregorian calendar; freshness uses today's clock or an earlier date plus clock, always at 24-hour second precision. Credential distances floor to minutes and drop zero remainders; expiry exactly now is expired. Request durations floor to tenths below a minute, then use whole minutes and padded seconds without capping minutes at an hour. Machine values and `datetime-local` serialization stay ASCII and retain their existing parsing and bucket-boundary semantics.

Use logical spacing, positioning, borders, and reading-start text alignment for directional UI. Technical fields, identifiers, secrets, URLs, code, and JSON use `dir="ltr"`; human name fields use `dir="auto"`. Numeric table columns retain physical right alignment and isolate their numeric runs. Chart chronology keeps an LTR coordinate container. Only the glyph API's navigation chevrons mirror; status glyphs, branding, and external-link marks retain their orientation. Switch thumbs travel from logical start and reverse their checked translation in RTL. Do not insert direction characters into copied or stored values.

Rich messages use flat authored `[[slotName]]` markers and typed domain renderers in `i18n/rich.tsx`. Declare each message's exact slots in `metadata.ts`; the catalog gate rejects missing, duplicate, malformed, and extra slots. Every renderer produces its message through one typed render entry keyed by that same metadata path, so the slots a call site passes are compile-checked against the declaration the gate enforces on the catalogs, and plain-text renderings (accessible names) go through the entry's string sibling, which never interprets `$`-patterns in inserted values. All dynamic strings in a rich message enter as application-owned JSX slots, with machine values in LTR `bdi` and user names in auto-direction `bdi`. Catalogs control surrounding prose and slot order, while the application controls links and elements. Never interpolate user strings before parsing markers or rescan inserted values.

The browser baseline is the workspace's modern ES2022 browser target with native `Intl.Locale` (including `maximize()`), `Intl.PluralRules`, `Intl.NumberFormat`, `Intl.DateTimeFormat`, and `Intl.RelativeTimeFormat`. There are no localization polyfills or downloaded fonts. Date formatting intentionally uses the browser's local time zone, the Gregorian calendar, and `h23` for clocks; a catalog's tag is also its formatting locale.

For a development visual review, run `npm run dev -w web` and open `/localization-preview.html?locale=ar&theme=dark` (also `en`/`zh-CN`, `light`/`dark`). This isolated entry injects a representative Arabic registry and uses the shared controls, notice, confirmation, table, and chart. It never calls a gateway. Arabic is absent from the production registry and build. Review all three locales at desktop and narrow widths with mixed-script names, literal marker-looking values, validation, keyboard focus, directional switches, and locally scrolling tables. The automated integration suite additionally switches actual edited administration forms and an active device OAuth flow without replacing their state or issuing language-triggered management calls.
