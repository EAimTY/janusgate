# JanusGate — Self-Hosted AI Gateway (Rust)

> Single source of truth for the system design and architecture. Contracts and invariants stated here are **normative**.

---

## 1. Overview & Scope

**JanusGate** is a self-hosted, lightweight AI gateway written in Rust. It exposes three outward serving API families — OpenAI-compatible (`/api/openai-v1`), Gemini (`/api/gemini-v1beta`), and Anthropic (`/api/anthropic-v1`) — over one effective-model set, every surface serving every upstream format, backed by heterogeneous upstream accounts, managed via a versioned management JSON API (`/management-api/v0/*`). The repository additionally hosts [`web/`](web/README.md) — janusgate-web, the standalone statically-hosted administration frontend for that management API; `web/README.md` is the source of truth for the frontend, and this document remains the source of truth for the gateway.

### Providers: Definitions, Instances, Credentials

The provider model decomposes into **wire format (code) × connection configuration (data) × credentials (data)**:

- **Wire format** — the five codecs in `src/format/` (`openai_response`, `openai_chat_completion`, `gemini_generate_content`, `gemini_interaction`, `anthropic_messages`) render and parse bodies only. No backend branch identifies a product, infers a model's protocol, or restricts a product to a format.
- **Connection configuration** — a `provider_definitions` row (§3, §5): an immutable, one-format recipe keyed by `(name, version)` that describes inference URLs and headers, credential acquisition (a static API key, or an OAuth recipe with an authorization-code or device grant, token exchange, provisioning, and refresh mode), and model discovery. Every descriptor string is a `StringExpr`; every control-plane request is a `ControlRequest` (§5.1).
- **Credentials** — the `providers` row's tagged JSON (`{"type": "api_key", "api_key": …}` or `{"type": "oauth", "access_token": …, …}`), whose `type` always matches its definition's credential kind (§3).

A new provider that speaks an already-supported wire format is added by writing one definition row through the management API — zero backend changes. The frontend ships a preset catalog (§5.6) that prefills these definitions; the backend never seeds or special-cases a product, and an operator without the frontend authors definition JSON directly against the management API. Growing the descriptor vocabulary (a new value token, a render option, an extraction shape) is the documented extension path when a future provider genuinely does not fit.

### Outward Protocols
- **Chat Completions**: `POST /api/openai-v1/chat/completions` (streaming SSE & non-streaming)
- **Responses**: `POST /api/openai-v1/responses` (streaming SSE & non-streaming)
- **Responses Compact**: `POST /api/openai-v1/responses/compact` (non-streaming; the client-directed remote-compaction endpoint, §6.8)
- **Model Discovery**: `GET /api/openai-v1/models`
- **Gemini GenerateContent**: `POST /api/gemini-v1beta/models/{model}:generateContent` (non-streaming) and `POST /api/gemini-v1beta/models/{model}:streamGenerateContent?alt=sse` (streaming, only the `alt=sse` form is supported)
- **Gemini Interactions**: `POST /api/gemini-v1beta/interactions` (streaming per the API's own body `stream` + `alt=sse` convention)
- **Gemini Model Discovery**: `GET /api/gemini-v1beta/models`
- **Anthropic Messages**: `POST /api/anthropic-v1/messages` (stream via body `stream: true`)
- **Anthropic Model Discovery**: `GET /api/anthropic-v1/models`

### Design Principles & Non-Goals
- **Concrete JSON ownership**: Gateway-defined request and response envelopes, generated compaction controls, checkpoints, and sampling reports retain concrete Rust types through dispatch, IR translation, and client rendering. Upstream parsers deserialize complete documents from bytes directly into protocol types; configured response-envelope selection borrows the selected raw JSON member. Arbitrary JSON is confined to caller-authored tool arguments/results and schemas, operator-authored template literals and externally described control responses, and producer-owned replay fragments whose unknown members must survive. Template evaluation borrows the concrete codec body at its body placeholder instead of converting it into a JSON DOM.
- **Stateless execution**: zero persistence of *content* — prompts, completions, headers, and upstream error bodies are never written anywhere. Request accounting persists only usage's numeric facts as `ApiLog` rows (§3), governed by the presence of the `api_logs` configuration section (§8); with the section absent, not even those are written, while the existing api-log files stay readable.
- **Interactions statelessness**: the gateway never stores or chains. Interactions upstream requests always render `store: false` and never `previous_interaction_id`. Inbound `previous_interaction_id`, `background`, `cached_content`, and `webhook_config` are 400s on the Interactions surface; inbound `store` is accepted-and-ignored.
- **Headless server**: The gateway serves no frontend of its own — no SPA, no static assets. Administration is conducted exclusively through `/management-api/v0/*` JSON endpoints; the repository's `web/` frontend is a separately deployed static application that talks to those endpoints over the network and is never served by the gateway.
- **Strict model passthrough**: Zero automatic or hardcoded model mapping. Upstream calls pass the exact model identifiers yielded by upstream model discovery (`upstream_id`), even for OAuth providers. Reasoning levels are parsed into one closed shared vocabulary and written verbatim into the target's own level parameter — there is no cross-vocabulary mapping, and there never will be (§6.4).
- **Client-directed compaction**: The gateway fulfills a compaction request only when the client's own request states one — an explicit compact operation, trigger, or threshold control (§6.8). It never adds compaction to an ordinary request, never re-compacts on its own initiative, and decoding an existing compaction artifact is a replay, never a new summary call. Compaction is stateless like everything else: there is no server-side conversation storage, no Gemini-native compact mechanism, no managed agents or Live API/WebSocket transport, no account switching after an earlier compaction stage or accepted response, and no automatic compaction of an ordinary request.
- **Excluded**: Multi-tenancy, round-robin or weighted load balancing, retrying ambiguous execution outcomes, automatic model mapping, prompt caching, content logging (prompts, completions, headers, and upstream error bodies are never persisted or logged), billing/rate-limiting, outbound proxying, server-side conversation state.

## 2. Technology Stack & Request Pipeline

### 2.1 Technology Stack

### 2.2 Server Pipeline Architecture & Router Hierarchy

```text
[Incoming TCP]
               │
               ▼
      ┌─────────────────┐
      │server.rs+hserver│  (server.rs: TCP listener & accept loop; hserver: HTTP/1 & HTTP/2
      └────────┬────────┘   lifecycle; TLS handshake first when `tls` is configured)
               │ (invokes Router as tower::Service)
               ▼
      ┌─────────────────┐
      │   Root Router   │  (404: empty)
      └───┬─────────┬───┘
          │         │
          │         └──────────────────────────────────┐
          ▼                                            ▼
┌───────────────────┐                        ┌───────────────────┐
│ Management API Rtr│ (/management-api/*)    │    API Router     │ (/api/*)
│ (CORS)            │                        │ (CORS)            │
│ (Fallback: shared │                        │ (Fallback: shared │
│ empty 404)        │                        │ empty 404)        │
└─────────┬─────────┘                        └─────────┬─────────┘
          │                                            │
          ▼                                            ▼
┌───────────────────┐                        ┌───────────────────┐
│  Mgmt API v0 Rtr  │ (/management-api/v0/*) │ Format Sub-router │ (/openai-v1/*, …)  
│ (Management Auth) │                        │ (Format Auth)     │
│ (404: errno JSON) │                        │ (404: format JSON)│
└───────────────────┘                        └───────────────────┘
```

The outward serving facade in `src/api/serving/mod.rs` owns shared HTTP policy: authentication, body extraction, router fallbacks, JSON/error response builders, and model-list rendering. Its `completion` module owns parsing, route selection, compaction execution and fallback coordination, and the concrete artifact or checkpoint render selected for an operation. Its `delivery` module owns SSE pumping, detached JSON aggregation, buffered delivery, accepted-affinity publication, and final request accounting. Ordinary and checkpoint-prefixed JSON responses share one detached task and handoff lifecycle, while retaining their distinct codec render methods. Compaction execution retains one optional accounting draft: delivery takes it exactly once, and cancellation finalizes only a draft still owned by execution.

The server architecture separates low-level connection driving from hierarchical routing:
1. **Server Lifecycle (`server` module + `hserver`)**:
   - The gateway's own `server` module owns the TCP listener (`socket2`: dual-stack IPv4/IPv6, non-blocking, explicit listen backlog) and the accept loop, which retries failed accepts with exponential backoff and hands every accepted connection to one `hserver` connection driver — built once at startup with the HTTP/1 and HTTP/2 configurations over the root router, so serving a connection clones the driver's shared configuration instead of rebuilding it — which drives the low-level Hyper connection lifecycle — HTTP/1 or HTTP/2, selected per connection by protocol auto-detection (the HTTP/2 connection preface for plaintext prior-knowledge clients; ALPN for TLS clients) — directly over the accepted TCP stream, or wrapped in TLS (`rustls` via hserver's `tls` feature) when the `tls` configuration section (§8) is present. TLS applies to the whole listener: the PEM certificate chain and private key are loaded and combined into one shared Rustls server configuration when the configuration loads and recombined whenever it or its material changes (§8), and every accepted connection reads the currently active configuration for its handshake — established connections keep serving while new ones pick up a reload. The handshake offers both `h2` and `http/1.1` through ALPN and performs no client-certificate authentication; inbound access is governed by the gateway's own token authentication either way (§4).
   - Startup builds the shared `Context` (`src/context.rs`) — the `Database` handle plus the two upstream HTTP clients, data plane and control plane (§4) — and passes it to `server::Server::new(context)`, which binds the listening socket and builds the shared connection driver over the root router carrying the context as router state; `Server::run` then serves connections until the process is terminated. Startup also spawns the configuration watcher task (§8), which keeps the live configuration current with its files.
   - `axum::serve` is **strictly unused**. Instead, every accepted connection — after its TLS handshake, when TLS is configured — is delegated directly to Axum's root `Router` as an implementation of `tower::Service`.
2. **Hierarchical Routers (`axum::Router`)**:
   - **Root Router**:
     - Holds the shared `Context` — the `Database` handle plus the two upstream HTTP clients — as its router state and propagates it to sub-routers.
     - Nests `/management-api` and `/api` sub-routers.
     - Maintains its own top-level fallback route returning an empty HTTP 404 response for any unmapped root paths.
   - **Management API Sub-router (`/management-api`)**:
     - Parent router for every management API version.
     - Nests the version sub-routers (`/v0`) and applies the management CORS policy (`management_api.cors`).
     - Defines no route of its own: unmapped paths outside every version are answered with the same empty 404 the root router renders (§2.2).
   - **Management API Version Sub-routers (e.g. `/v0`)**:
     - Scoped to that version's management endpoints (`/providers:list`, `/providers:update`, etc.) and owning that version's payloads and error taxonomy.
     - Wrapped with management authentication middleware (`Authorization: <token>`) and the management body limit.
     - Answers unmapped paths beneath the version prefix with that version's errno-shaped 404 JSON error response (§7).
   - **API Sub-router (`/api`)**:
     - Parent router for all external gateway protocols.
     - Nests isolated format sub-routers (e.g. `/openai-v1`).
     - Defines no route of its own: unmapped paths outside every format are answered with the same empty 404 the root router renders (§2.2).
   - **Format-Specific Sub-routers** (`/openai-v1`, `/gemini-v1beta`, `/anthropic-v1`):
     - Scoped to that protocol's endpoints: OpenAI (`/chat/completions`, `/responses`, `/responses/compact`, `/models`); Gemini (`/models/{model}:generateContent`, `/models/{model}:streamGenerateContent`, `/models` — the model rides the URL path, never the body; `/interactions` — the model rides the request body, the path carrying no model slot, §6.5); Anthropic (`/messages`, `/models`).
     - Wrapped with format-specific authentication middleware: OpenAI `Authorization: Bearer <key>`; Gemini `x-goog-api-key` header only (no `?key=`); Anthropic `x-api-key` only with a required-present `anthropic-version` header (value not validated).
     - Answers unmapped paths beneath the format prefix with format-compliant 404 error payloads (OpenAI JSON error structure; Gemini `{"error": {code, message, status}}`; Anthropic `{"type": "error", "error": {type, message}}`) and wrong-method requests with format-compliant 405 bodies.
3. **Independent 404 Responses**:
   - Each routing domain answers its own unmapped paths: the root router with an empty 404, the management API v0 version sub-router with version 0's errno error JSON (§7), and each format sub-router with its own format's error JSON (`/openai-v1` OpenAI, `/gemini-v1beta` Gemini, `/anthropic-v1` Anthropic). The `/api` and `/management-api` parent routers own no route, so their unmatched paths reach the same empty 404.
   - That empty 404 is one shared handler: the root router declares it, and the two parent routers declare that same handler as their own fallback instead of inheriting it. axum 0.8 discards a nested router's fallback — together with every fallback collected from routers nested below it — when the router being nested declares none of its own (tokio-rs/axum#3138; axum 0.9 fixes the propagation through tokio-rs/axum#3158), so without the parents' declaration the sub-routers' 404s below them would never run. The rationale and the canonical `TODO(axum 0.9)` marker live on the shared handler in `src/router_fallback.rs`, referenced by one-line pointers at the nest sites; the parent declarations disappear with that release, and the observable behavior is identical either way, because all three name the same handler.
4. **Method Mismatch on Routed Paths**:
   - A request whose method is not registered on an otherwise-matching routed path never reaches the 404 responses: axum's method routing answers HTTP 405 with an `Allow` header listing the registered methods. Within a management API version sub-router that 405 renders the version's error body (errno 8 `method_not_allowed`); every outward format sub-router (`/openai-v1`, `/gemini-v1beta`, `/anthropic-v1`) renders the shared `MethodNotAllowed` contract variant in its own format's error envelope (§6.7).
   - This 405 is distinct from the 404 responses above, which serve only unmapped paths; the router-level authentication middleware still applies, so an unauthorized request is rejected with 401 before the 405 is produced.

**Fail-fast panics are contractual**: the process installs a panic hook before any other startup operation that prints the panic diagnostic to stderr and terminates the process with exit code 1, so a panic in any spawned task — accepted-connection or request-pipeline — kills the whole gateway by design instead of leaving a partially operational server behind.

## 3. Storage & Schema (Turso)

The database runs in-process via `turso` with SQLite-compatible syntax and strict column typing. The main schema is version 2, with an atomic migration from the version-1 baseline. Existing pools receive the editable prefix `pool-{id}-`; the migration replaces pooled providers’ automatic direct entries with pool-owned union entries while preserving authored routes and never-recycled route identities. Naming collisions abort the migration. Development databases preceding the baseline must be explicitly recreated by their owner; startup never deletes them. The schema is versioned in `src/database/schema/`: every version is one `version_x.rs` module defining `const SCHEMA: Schema` — its `version`, its complete DDL (`schema`, hand-written SQL), and the `migration` SQL that transforms the previous version into it — registered in ascending order in the module's registry, starting at version 1 with no gaps. Every schema modification creates a new version; existing versions are immutable history. Each version module contains one `SCHEMA` constant with its DDL and migration text; fresh-schema and constraint tests live beside the registry.

### Database Abstraction & Connection Pooling
- **Connection Pool**: Database access is managed through an in-process connection pool (`deadpool`), maintaining up to `database.max_connections` concurrent `turso::Connection` instances. When every connection is checked out, connection acquisition waits at most `database.pool_timeout` milliseconds before failing with `PoolTimeout`.
- **Connection Busy Timeout**: Every pooled connection and schema-bootstrap connection configures a 5-second busy timeout, so a write waits at most 5 seconds for the database file lock before failing with the underlying busy error.
- **Implicit Prepared Statement Cache**: All queries and executions on both `Database` and `Transaction` pass through `prepare_cached()`. Turso's statement cache is per-connection and persists across pool checkouts, so warm connections reuse their cached preparations; a freshly created pooled connection starts cold.
- **Eager Query Materialization**: `query()` drains every result set to completion and returns owned `Vec<Row>` values before the pooled connection is released. Lazily-consumed cursors are never exposed, so a result can never outlive its connection checkout, interleave with another borrower's statements, or leave unfinished statement state on a recycled connection.
- **Transaction Semantics**: A `Transaction` checks out and exclusively holds a pooled connection for its entire lifetime. Statement execution on the handle requires exclusive access (`execute()`/`query()` take `&mut self`), so statements within one transaction can never run concurrently or interleave. Explicit `commit()` or `rollback()` consumes the transaction and returns the connection to the pool; dropping an uncommitted transaction discards its connection instead of returning it to the pool, so the open engine-level write lock is released immediately rather than parked until the connection's next checkout. Connections that still report an open transaction at recycle time are discarded and replaced by the pool. A management read-then-write write the engine refuses with the stale-snapshot busy error — a concurrent commit landed between its read and its first write — is retried by the storage tier's transaction helper up to three attempts, re-reading and re-validating the newer state each time, before the last error surfaces.
- **Error Domain**: The database module defines an `Error` enum using `thiserror` that directly wraps underlying Turso engine errors (`Turso`), alongside pool lifecycle errors (`PoolClosed`, `PoolTimeout`), filesystem I/O (`Io`), invalid UTF-8 database path errors (`InvalidPath`), and typed schema-drift errors (`SchemaDrift`) — a database file not interpretable under its registry: an unknown schema version, a foreign application-id stamp, or a failed schema batch. Connection pool errors with a backend cause are merged directly into `Turso`.
- **No Global Database Static**: The database is opened via `Database::open(path, registry, max_connections, pool_timeout)` — the `registry` naming the schema version registry the file migrates under, the main control-plane schema by default and the `api_logs` schema for api-log files (§3 *ApiLog Store*). Startup opens the main database and wraps the instance into the shared `Context` (§2.2) passed to `server::Server::new()` and injected into the Axum router hierarchy as shared state.
- **Schema Versioning & Migrations**:
  - Every modification to the database schema is a new version: a new `version_x.rs` module carrying its hand-written DDL — every statement is parsed by `turso_parser` and applied to a fresh database in tests — together with the migration that upgrades a database of the previous version, and a registry registration. Version 1's migration is empty: a fresh database receives its DDL directly.
  - On startup, `Database::open()` reads `PRAGMA user_version` and binary-searches the registry: version `0` means fresh — it receives version 1's DDL and then continues the same forward walk, so a fresh database ends at the latest version however many exist; a known version is migrated forward one version at a time, each schema or migration text committed atomically together with its `user_version` advance, so a crash mid-chain leaves the database on its last committed version and the next startup resumes from there; a database already at the latest version starts immediately. Both the fresh-database decision and every migration step re-check the stored version inside their own write-locked (`BEGIN IMMEDIATE`) transaction — the version read that selects the work runs before any lock is held. Of several opens racing on one file, exactly one therefore applies the fresh DDL or a given migration and the others join the version it committed instead of double-applying.
  - An unknown version — negative or newer than the latest — fails the open with the typed `SchemaDrift` error, refusing to execute against a database this build cannot interpret: fatal at the main database's startup open, and scoped to the one failing request when an api-log day file carries it.
  - Every registry stamps its identity in the database header: version 1's SQL sets `PRAGMA application_id` to the registry's fourcc (`JGMD` for the main database, `JGAL` for api-log files). Before walking an existing database, the bootstrap verifies the stamp, and a mismatch — a file opened under the other registry, or a file predating the stamp — answers the same typed `SchemaDrift` error an unknown version does, instead of surfacing as missing-table errors on first query.
  - Migrations run under foreign key enforcement: the bootstrap connection enables `PRAGMA foreign_keys` before the walk, and each migration executes inside its own transaction, where SQLite defines the pragma as a no-op (Turso currently accepting it mid-transaction is a divergence from SQLite that may be aligned at any time). A migration must therefore never rely on disabling enforcement — it must be authored to hold under enforcement statement by statement, ordering table-rebuild steps so referential integrity holds at every intermediate state.
  - Tests enforce the registry ordering invariant (contiguous from 1), an empty version 1 migration, a per-version test applying each DDL to a fresh database, and — each step on its own fresh database — that version 1's DDL and every later version's predecessor-DDL-plus-migration leave the database at exactly the declared schema, compared through a canonical structural form (object set, column order, constraints, foreign keys, index definitions) rather than DDL text. Both registries — the main database's and the api-log store's — run the same tests.

Storage domain modules own their row projections and codecs: `models.rs` decodes physical inventory and capability columns, `provider_definitions.rs` decodes immutable descriptor sections, and `providers.rs` decodes credential-bearing accounts. Shared transaction coordination and the storage error domain remain at the storage root; joined account/model reads stay with their consuming domain.

### ApiLog Store

The `api_logs` table lives outside the main database: one SQLite (Turso) file per UTC calendar day of `started_at`, under the directory the `api_logs.path` configuration names (§8). The main database keeps its file lock and connection pool to the control plane; accounting INSERTs never contend with it, retention is whole-file deletion instead of `DELETE` + `VACUUM`, and the main database stays small and hot.

- **File layout**: files are `<path>/YYYY-MM-DD.db`, named for the UTC day of the rows' `started_at`, so filenames sort chronologically. Mapping a timestamp to its file is a pure function — there is no manifest or registry anywhere, and the directory listing is the only truth. A missing file is an empty partition, both for reads and as the pre-state of lazy creation; the directory itself is created lazily on first file creation, and an absent directory reads as empty.
- **Recording switch**: the presence of the `api_logs` configuration section *is* the switch (§8) — present, rows are written; absent, none are, while existing api-log files stay readable. There is no `is_enabled` field. The check is read live per dispatched request at the dispatch stamp, so a reload applies to the next dispatch; the `path` is consumed once at startup when the store is constructed, so adding the section or changing its path applies after restart — the same standing as `database.path`.
- **Write path**: the finalization point derives the day's file from the row's own `started_at` stamp — never from the finalization clock — consults the hot cache, and inserts one row. The hot-file connection cache is keyed by day, holds capacity 3, and evicts the least recently written day; capacity is a performance hint, not a correctness bound — a miss beyond it lazily opens the existing file, and a late finalization whose file was already retention-deleted recreates the file with that one row (deterministic attribution, accepted), and the mirrored edge is accepted in the same class: a retention sweep that unlinks a file while a finalization is mid-INSERT into it ends one of two ways — the INSERT succeeds into the now-unlinked file and the row is lost with no error surfacing, or the pool hands the finalization a fresh connection and the row lands in the recreated file of the late-write edge above (deterministic attribution, accepted). On a cache miss with no file present, the gateway creates the file, applies the `api_logs` DDL, and then runs the retention sweep; creating a new file is the sweep's only trigger, and opening an existing file for a late write never sweeps. The api-log databases reuse the pooled `Database` abstraction under the `api_logs` schema registry with a fixed write pool of 2 connections and a read pool of 1, and busy timeout and connection configuration match the main database. Failure semantics are unchanged: recording failures are logged and swallowed, never entering any HTTP error domain (§8). A drifted day file — one whose stored schema version or application-id stamp the `api_logs` registry cannot interpret — answers the typed `SchemaDrift` error at open, which the storage error domain classifies as drift: its writes are swallowed under the same recording policy, and its read fails that one request (below).
- **Schema versioning**: api-log files carry their own `PRAGMA user_version` under a separate version registry in `src/database/schema/` (`api_logs_version_1.rs`), reusing the same `Schema` machinery as the main registry. The unreleased baseline is one version 1 carrying the current `api_logs` table and its five indexes. Previous development layouts have no compatibility reader or upgrade migration; their owner recreates them explicitly. The gateway never deletes an existing database automatically.
- **Retention**: run only when a new api-log file is created, the sweep deletes files whose day-end is strictly older than now − `retention_days` (§8), evicting a cached file before unlinking it, never deleting the file just created, leaving unparseable filenames alone, and logging-and-swallowing deletion failures. With recording off, or with no new days, nothing is ever deleted — accepted.
- **Read paths**: `usage:list` and `usage:query` fan out over the retained files and merge (§7.1). The time filter bounds which files are queried, and so does `usage:list`'s `before` pagination cursor — a day strictly above the cursor's own day holds only rows at or after the cursor (`started_at < before`), so the walk never opens those files; a boundless aggregation (`usage:query`) scans all retained files (bounded by retention), while `usage:list` early-stops once its page fills. Reads never create files or directories; a corrupt file fails the request explicitly; an empty store answers an empty list page and a single zeroed total bucket.

### Automatic Model Exposure

A provider outside every pool automatically exposes each stored physical model as `provider.model_prefix + upstream_id`. Membership in any pool suppresses its automatic provider-prefixed entries, including membership in a disabled pool; removing its last membership restores them. Each pool has its own unique name, required `model_prefix` (including the empty prefix), and serving switch. It automatically exposes the union of its members' exact upstream IDs as `pool.model_prefix + upstream_id`, with one automatic entry per pool/model pair. New discoveries, manual creation, membership edits, and deletions synchronize exposure atomically. Dispatch considers only enabled members with an enabled, non-vanished instance of that exact model; a model present on one member routes only to that member. Disabled and vanished physical inventory retains the pool entry for recovery; removing the last inventory owner removes its automatic pool entry. Prefix renames preserve route identities for unchanged targets. Naming conflicts roll back the entire mutation. Authored aliases remain independent. Automatic entries are managed through their provider or pool and reject route updates and deletion. Deleting a pool removes its automatic entries and restores standalone provider exposure; authored routes still protect their referenced pool from deletion. OAuth create flows retain the provider prefix durably; renewal and reauthorization preserve it.

### Core Entities
- **ProviderDefinition** (`provider_definitions`):
  - `(name, version)`: the composite primary key. Every definition name accumulates positive, monotonically increasing immutable versions; the `version > 0` range is pinned by a schema `CHECK` and enforced in Rust by `NonZeroI64`. Definitions are never updated or deleted through the management API — an edit atomically appends `version + 1` from the stored latest, rejecting a stale base version as a conflict, and `ON DELETE RESTRICT` additionally protects referenced versions at the database boundary. The latest version is a listing convenience, never a movable alias for an explicit reference; any field, including `format` and the credential kind, may differ in the new version.
  - `format`: the one upstream wire format every inference of the definition speaks — a closed text enum `CHECK` over the five codecs.
  - `inference`, `credential`, `provisioning`, `discovery`, `compaction`, `quota`: the descriptor sections (§5), stored as JSON under `json_valid` checks only. Their shapes are the management write boundary's serde contracts, not column invariants; `provisioning`, `discovery`, `compaction`, and `quota` are nullable, and absent means the capability is absent, never defaulted.
  - The credential `type` discriminator (`api_key` | `oauth`) is the only stored credential-kind representation for the definition, and it must match the provider row's credential kind at the management boundary — SQL cannot inspect a referenced row without triggers.
- **Provider** (`providers`):
  - `id`: Integer `AUTOINCREMENT` primary key; the provider's public identifier. Every management reference to an existing provider — updating, renaming, deleting, discovering models, re-authorizing — goes through it, and it never changes.
  - `model_prefix`: required naming prefix, including the empty string; standalone automatic model names concatenate it with exact upstream IDs. Prefix edits atomically rename automatic entries, preserving route identities and rejecting collisions. Automatic synchronization updates surviving rows in place, preserving their route-attached permission rules.
  - `name`: unique, renameable label; content is the administrator's choice, validated only at the management boundary.
  - `provider_definition_name` / `provider_definition_version`: the exact immutable definition version the row's requests are interpreted against — the latest version is never substituted for it. Changing the reference is an explicit atomic rebind that validates the target version's existence, the credential-kind agreement against the replacement (or stored) credentials, inside the write's own transaction; a different credential kind requires replacement credentials obtained through the matching static-key write or an OAuth flow. The gateway never judges whether a model supports the target format.
  - `base_url`: the only persisted instance URL after creation. A definition whose expressions reference the base requires it; a frontend preset may supply it; and an OAuth exchange or provisioning extraction may replace it atomically with a renewal.
  - `credentials`: plaintext tagged JSON stored directly without encryption, exactly `{"type": "api_key", "api_key": …}` or `{"type": "oauth", "access_token": …, "refresh_token": … | null, "slots": {…}, "expires_at": … | null, "refresh_started_at": … | null}`. The OAuth variant always serializes both timestamp members (JSON `null` when absent); an absent member reads as `null`, which the SQL merge-patch renewal relies on. `expires_at: null` means no time-based refresh is scheduled — it does **not** mean already expired: without a known lifetime a renewable token is sent until the upstream rejects it or an explicit credential update or reauthorization occurs. Copilot-style durable tokens live in `slots` while provisioning supplies the short-lived access token, expiry, and endpoint.
  - `is_enabled`: stored serving switch (`0` or `1`, default `1`). Master switch for all models of this provider.
  - **The token-refresh lease** lives inside the credentials JSON (`refresh_started_at`), and every transition conditions on `json_extract(credentials, …)`: the acquire on a known, elapsed `expires_at` (a `null` expiry never refreshes) and no competing lease acquired after the 90-second staleness bound; the persist and the clear on the caller's own stamp, so a concurrent reauthorization, credentials replacement, or stale-lease reacquisition is never overwritten by a refresh derived from superseded credentials, and a refresher that lost the lease cannot erase the winner's — the loser re-enters the lease competition. Concurrent requests poll up to 100 seconds, deliberately longer than the staleness window, and the control-plane request timeout (§4) guarantees a stalled grant aborts and clears its lease before it could be stolen. Expiry and lease stamps render UTC microseconds. The renewal dispatches on the definition's refresh mode: a **grant** reads the stored refresh token and slots, retains an omitted rotation, recomputes expiry from the response's token data (never carrying a stale timestamp forward), and persists atomically under the lease; **reprovision** re-runs the provisioning sequence (§5.4) over the stored slots and updates the access token and base URL as its extractions supply them, replaces the stored refresh token when the sequence extracts a rotated one and leaves it untouched otherwise, and always renews the expiry (§5.4), in one conditional write; `refresh: none` never enters the lease. There is no implicit one-day lifetime: a provisioning-supplied expiry supersedes the response's token data, and the response's evidence is validated only when consulted — a mapped `expires_in` must still decode as an integer at the mapping boundary; its positivity is consult-time — expiry then comes from a positive reported `expires_in`, else a future JWT `exp` claim, else the definition's explicitly configured lifetime, else `null`, and a non-positive `expires_in` or a non-future `exp` is a malformed response.
- **OngoingOAuthFlow** (`ongoing_oauth_flows`):
  - *Ongoing* means unconsumed. The row references one exact definition version (the flow reads its OAuth recipe through it and stores no duplicate snapshot) and carries its whole lifecycle: the target (`purpose` = `create` naming `provider_name` and `model_prefix`, or `reauthorize` naming `target_provider_id` — a bare integer without a foreign key, so a later provider deletion cannot strand a result), the grant kind (`authorization_code` with `code_verifier`, or `device` with `device_code`, `device_user_code`, the verification URIs, the poll interval, and the next-poll instant), the working `slots` and `base_url`, `expires_at`, and the terminal outcome (`succeeded` with `result_provider_id`, or `failed` with a gateway-owned `failure_code`/`failure_message` pair — never upstream error bodies).
  - Cross-column `CHECK`s pin the lifecycle states: a create flow names its new provider and a reauthorize flow names its target, never both; a device flow carries its device columns and its next-poll instant exactly while it is pending; the exchange checkpoint of a completed exchange exists exactly while its claim is held — a device-only fact, and one a terminal row never carries; a terminal outcome excludes the poll schedule's claim and carries either a result provider or a failure pair, never both; a terminal outcome exists only on a device flow — an authorization-code flow is deleted by the atomic consume of its first completion attempt, so a terminal state is never persisted for it.
  - `state_token` is the random OAuth state value (the management API names it `state`), unique, consumed by one atomic `DELETE … RETURNING` so exactly one completion can ever observe it. Authorization-code TTL is 10 minutes; a device flow's comes from its authorization response or the definition's explicit fallback. A terminal device result stays until the management client retrieves it — single consume — or the expiry sweep removes pending and unconsumed-terminal rows alike. The background device poller resumes every unexpired pending flow from its stored schedule at startup, claims a due flow with one conditional `UPDATE … RETURNING` (`device_poll_started_at`), recovers stale claims once they outlive a claim-staleness window of twice the control-request timeout (§4) — strictly beyond it, so a claim is never stealable while its holder's exchange budget, or the claim-conditioned persist the exchange's outcome triggers, is still live; the extra recovery delay is the checkpoint guarantee's price — waits at least the stored interval between attempts (five seconds when the response omitted one), raises the interval permanently on `slow_down`, doubles only the next attempt's delay after a connection timeout while the stored interval stays untouched, keeps polling a rejection whose error code falls outside the definition's `terminal_codes` on the stored interval until the flow's own expiry ends it, re-stamps the claim with a compare-and-set after a completed exchange's provisioning returns and before the success commit — so a provisioning sequence longer than the claim-staleness window cannot be stolen mid-commit, and a re-stamp that finds the claim stolen abandons the commit — and commits a success — the provider write and the outcome — in one transaction; a provisioning failure after the completed exchange instead persists the terminal `provisioning_failed` outcome with the claim the flow still holds — it never reaches the re-stamp — a create flow whose provider name another row claimed before the commit persists the terminal `name_conflict` outcome the same way, the conflict being unwinnable however often the poll retried — and a failure of the commit transaction itself — the provider write, the claim-conditioned outcome commit, or the commit — persists the terminal `commit_failed` outcome against the re-stamped claim, so once the exchange completes the poll loop always stops at a terminal outcome and never re-runs the already-consumed grant exchange. As soon as an exchange completes the claimant also persists its mapped token fields into the row's `device_exchange_checkpoint` checkpoint — before provisioning runs — so a claim recovered after a restart resumes into provisioning and commit from the checkpoint instead of re-presenting the consumed device code, whose re-presentation an RFC 8628 upstream would answer with a terminal rejection masquerading as the user's verdict; the staleness window's strict slack over the control-request timeout is what keeps this persist's claim live, so a completed outcome can never be silently discarded by a competing claimant that recovered the just-became-stale row first; the lease alone prevents only concurrent double-exchange, and a recovered checkpoint that no longer parses fails the flow with the gateway-owned `internal_error` pair.
- **Model** (`models`):
  - `id`: Integer `AUTOINCREMENT` primary key; the row's identity, never recycled. Every row-addressed write goes through it.
  - `(provider_id, upstream_id)`: the natural key, unique. `upstream_id` is the exact identifier discovered from upstream and is used verbatim for upstream requests; upstream lists may discover IDs the definition's format cannot serve, and calling one mirrors the upstream error — operators disable the row or add models manually.
  - **Capability declarations** — eight nullable columns in two ownership classes, rendered on the model listings (§6.5) and never consulted at dispatch (§6.4). `thinking_levels` (a JSON array of the shared reasoning vocabulary, §6.4), `max_input_tokens`, `max_output_tokens`, and `compaction_support` (a JSON object of mechanism-to-support facts, §6.8) are **discovery-owned**: every refresh rewrites them for each listed row to that refresh's extracted facts, `NULL` when nothing was extracted — so a discovery whose descriptor extracts no capabilities resets them to `NULL`, and a stored value is always the latest upstream knowledge, never stale residue. `thinking_levels_override`, `max_input_tokens_override`, `max_output_tokens_override`, and `compaction_support_override` are **administrator-owned** nullable mirrors: `NULL` keeps the discovered value; a present value replaces that one field's declaration wholesale. The effective declaration of each capability is `override ?? base`. `NULL` means *unknown*, never "none" — an empty `thinking_levels` array is the positive declaration that no vocabulary level is supported. Within the compaction facts the unknown-versus-unsupported distinction is preserved end to end: the discovery-owned base stores only known facts (`supported`/`unsupported`; a member the descriptor extracted nothing for is absent, which reads as nothing known), while the override additionally admits an explicit `unknown` that suppresses both lower layers for that mechanism (§6.8). A manually created row stores `NULL` base columns; a `models:create` claim of a vanished row keeps its base columns (the last discovery's real facts) while the requested overrides apply.
  - `is_enabled`: serving switch (`0`/`1`, default `1`), written only by administrators; discovery never touches it.
  - `discovery_state`: `discovered`, `vanished`, or `manual`. `discovered` rows are marked `vanished` when the upstream list drops them — service suspended (the three-input status below is false): 404 on routing, absent from outward listings, still listed by the management surface. Recovery is the upstream listing it again (flip to `discovered`) or an administrator claim through `models:create` (lands `manual`). A `manual` row is never auto-vanished. Discovery writes only `discovery_state` and the capability base columns (below); deletion is administrator-only, and a deleted `discovered` row is rebuilt by the next discovery as a new row with a fresh identity. An empty or failed upstream list never mass-vanishes rows — a failed refresh is rejected before storage.
  - Effective serving — the one three-input definition shared by routing and the enabled-model listing, derived by management clients from the row's own inputs (rule 7): `provider.is_enabled && model.is_enabled && discovery_state != 'vanished'`.
- **ProviderPool** (`provider_pools`, `provider_pool_members`):
  - `id`: never-recycled `AUTOINCREMENT` identity; `name`: unique administrator-authored label; `is_enabled`: independent serving switch.
  - `model_prefix`: required prefix, including the empty string; automatic names concatenate it with the union of exact member upstream IDs.
  - Members carry `provider_id` and nonnegative `priority`, unique within each pool by both account and priority. Empty pools and noncontiguous priorities are allowed. Membership is ordered by ascending priority and replaced atomically with the pool's name and switch, using delete/reinsert inside one transaction so priority swaps cannot collide halfway through.
  - Removing an account cascades its memberships. Removing a pool is a conflict while an authored public route references it; automatic routes follow the pool lifecycle.
- **ModelRoute** (`model_routes`):
  - `id`: never-recycled `AUTOINCREMENT` identity, preserved when the target changes; `public_id`: unique routing-safe name; `is_enabled`: serving switch. `is_automatic` identifies a standalone provider-owned direct entry or a pool-owned model entry. Automatic entries stay enabled at the route level and follow their provider/model and pool switches; route update and deletion reject them with 409.
  - The target is exactly `Direct { model_id }` or `Pool { pool_id, upstream_id }`, serialized with snake-case `type` tags. Nullable SQL columns encode the same union without a redundant discriminator. Multiple named routes may target the same physical model or pool/model pair.
  - Direct targets reference physical models with `ON DELETE CASCADE`. Pool targets reference pools with `ON DELETE RESTRICT` and request an exact upstream identifier; missing current inventory is allowed when authoring a pool route. Discovery lifecycle changes never delete a stored route.
- **Account quota restrictions** (`provider_quota_blocks`):
  - Restrictions are keyed by account and the compact JSON ordered identity tuple, with typed JSON applicability, UTC-microsecond observation time, and a nullable strictly future reset. They are shared across pools, cascade with account deletion, and carry no reading history or content. `providers.quota_generation` and `quota_revision` are internal nonnegative ordering fences, never management editing fields.
  - Successful full observations compare both captured fences before applying any evidence and advance revision once. Applicable ratio ≥ 1, used ≥ limit, or remaining = 0 creates a block; positive available or unlimited evidence deletes its exact key. Unknown, omitted, and monitoring-only entries retain established blocks. Only a known future absolute reset is stored; date-only and past resets remain faithful in observations but produce a null block reset. A classified dispatch rejection compares generation alone and advances the current revision, so it wins over any read started earlier.
  - Availability reset, explicit credential replacement or OAuth reauthorization, definition rebind, and explicit base-URL change clear blocks and advance both fences in the same short transaction. Rename and serving-switch changes preserve them. Routine OAuth renewal/reprovision preserves exhaustion and both fences. Deleted accounts make late evidence a no-op; evidence never recreates account rows.

- **ApiKey** (`api_keys`):
  - `id`: Integer `AUTOINCREMENT` primary key; the key's public identifier.
  - `name`: non-empty human label, validated at the management boundary.
  - `key`: plaintext shared secret presented as `Authorization: Bearer <key>`; gateway-wide unique, routing-safe (management boundary); stored without encryption.
  - `is_enabled`: serving switch (`0`/`1`, default `1`).
  - `created_at`: UTC microseconds, stamped server-side.
  - `default_access`: required `allow`/`deny` decision, with a schema default of deny for baseline migration. Sparse rules are relational and resolve by stable route/typed owner identity (§3 *API key model permissions*).
- **ApiLog** (`api_logs`, stored in the day-partitioned api-log files of §3 *ApiLog Store*): request accounting, governed by the presence of the `api_logs` configuration section (§8). Each dispatched account attempt carries `model_route_id` alongside its real `provider_id` and `model_id`; none is a foreign key, so deletion preserves historical attribution. Dispatch-stage commitment remains active when recording is disabled. The first data-plane dispatch fixes duration origin and the recording switch for that attempt; quota checks and credential renewal never count toward it. The first upstream header status remains unchanged through counter, native fallback, summary, and generation stages. A successful 2xx header commits the account even if later body parsing fails.
  - One row per dispatched physical-account attempt — dispatch is the moment the upstream `send()` was issued; everything before it (authentication, routing 404s, token renewal, rendering failures) never reaches the table, and with the section absent no row is written while the management reads keep serving existing api-log files. No content is recorded: prompts, completions, headers, upstream error bodies, and the requested reasoning effort are absent.
  - The row closes exactly once under its current owner: the attempt boundary for a rejected or transport-failed dispatch, the detached non-streaming aggregation task for a non-streaming response, or the SSE render task for a streaming one. Single-account execution returns a typed predispatch failure, rejected response, dispatched ambiguous failure, or accepted event stream with its unfinalized draft; execution never chooses an outward status or finalizes a final failure. An owned draft guard covers cancellation before headers and while bounded rejection evidence is being read, recording `client_aborted` with no outward status and preserving headers only if they arrived. A consuming transfer hands the accepted draft to the response task; a consuming finalization hands failed or abandoned work to a detached writer before awaiting it, so cancellation cannot lose or duplicate the row. All standalone finalization paths share one detached-write entry point, which skips task creation for an unstamped draft using the dispatch-time recording decision, never the current configuration; response tasks still run independently when recording is disabled. Both response tasks own the request's accounting draft and outlive the handler, which hyper drops the moment the client departs, so the departure cannot lose the row: the non-streaming task consumes the upstream stream to completion and renders the aggregated body before attempting to hand it to the handler — the hand-off attempt is the client-liveness signal, finalizing `completed` + 200 when it delivers, `client_aborted` + `NULL` status when the handler departed mid-generation (no response was ever produced), and the classified `upstream_error`/`internal` outcome when the stream itself failed regardless of the client; the SSE task finalizes `completed` for a clean end, the classified outcome under the declared 200 for a mid-stream failure, and `client_aborted` for a broken body channel (200 once a frame had been enqueued, `NULL` before). One residual edge is accepted: a non-streaming disconnect after the rendered body was handed to hyper is unobservable, so that row records `completed`.
  - `id`: integer primary key **without** `AUTOINCREMENT` — no identity reference points at a log row, so its number may be recycled. It is never published: the rowid stays internal as the per-file tie-break (`ORDER BY started_at DESC, id DESC`), and `usage:list` paginates on `started_at` itself (§7.1).
  - No foreign keys and no name snapshot: `api-keys:delete`, `providers:delete`, and `models:delete` neither cascade into nor block log rows, sound because `providers.id`, `api_keys.id`, and `models.id` are never recycled; labels resolve through the entity listings.
  - Columns: `started_at` (dispatch instant, microseconds), `duration` (whole milliseconds to the recording instant, so pre-dispatch work never counts), `endpoint_type` (the outward endpoint, closed `CHECK` over the six outward endpoints — the five of §6.3 plus the compact route `openai_responses_compact`, §6.8), `is_stream` (`0`/`1`), `http_status` (`NULL` exactly when no response was produced), `upstream_http_status` (the first data-plane header status in an account attempt, `NULL` when no upstream response was obtained), `outcome` (`completed`, `client_aborted`, `upstream_error`, `internal`), and the five token columns (`NULL` when the upstream reported no usage; `output_tokens` includes `reasoning_tokens`).
  - Indexes: `started_at` alone plus one composite per attribution id; the low-cardinality columns are deliberately unindexed; list reads order by `started_at DESC, id DESC`.

  **Identity is never recycled.** Every integer identity a foreign reference can point at — `providers.id`, `api_keys.id`, and `models.id` — is an `INTEGER PRIMARY KEY AUTOINCREMENT` key; `ongoing_oauth_flows.id` carries it too so the rule holds uniformly even though nothing references it. The bookkeeping tables AUTOINCREMENT introduces (`sqlite_sequence`, Turso's `__turso_internal_*`) are internal objects excluded from the structural schema comparison.

  Every stored timestamp renders UTC microseconds; upstream wire units are untouched — a token endpoint's `expires_in` arrives in seconds and is scaled on write, and outward protocol `created` fields render seconds.

### API key model permissions

Every serving key stores a required `default_access` (`allow` or `deny`), sparse provider/pool defaults, and sparse public-route overrides. Permission resolves the first present decision: route override → typed owner default → key default. Direct owners are the physical model's provider; Pool owners are the pool, independently of member-provider rules. An owner deny is an inherited default that a route allow can override. Explicit decisions equal to inherited defaults remain authored pins. Inherit is represented only by an absent rule. Defaults apply to existing inheriting entries and future entries; discovery never materializes grants.

Permissions address never-recycled `model_routes.id`, not names or physical models. Renames and retargets preserve explicit route intent; retargets change the inherited owner. Deletion cascades rules for deleted identities, and recreation inherits without transferring grants by name. Key deletion removes permission rules while historical accounting remains. Provider/pool deletion keeps existing reference conflicts and removes only defaults and routes actually deleted. Disabled or vanished targets keep surviving rules.

All outward inference, compaction, replay, and model listings require an enabled key in the same database snapshot as route ownership and policy. Denied or absent public entries return native `ModelNotFound` 404 before affinity, quota, refresh, or upstream work, with no dispatched attempt log. A deleted or disabled authenticated key returns 401; database failures return 500. Listings filter before native projection, preserve structural capability composition and public-name order, and return normal empty pages. Permission grants never override global routing gates. Affinity reevaluation reauthorizes fresh snapshots; already admitted upstream work retains its admission across bounded account fallback and same-route compaction stages.

The main version-2 schema includes `api_keys.default_access` and three strict relational tables: `api_key_provider_defaults`, `api_key_pool_defaults`, and `api_key_model_route_overrides`, each keyed by key and target with cascading foreign references and target indexes. The incoming migration from version 1 gives existing keys deny with no rules. Development databases already stamped version 2 must be explicitly recreated by their owner to obtain the revised schema; startup never deletes them or upgrades a same-version database.

## 4. Security & Authentication

1. **Inbound Authentication**:
   - Authentication is format-specific and enforced at the router layer via Tower middleware before requests reach endpoint handlers:
     - **Management Version Sub-router (`/management-api/v0/*`)**: Uses management authentication middleware applied to the version sub-router. Requires `Authorization: <token>` without any `Bearer` prefix, matching `management_api.token` in configuration.
     - **Outward API Sub-router (`/api`)**: Performs no authentication itself and owns no route; it nests the format sub-routers and answers its unmatched paths with the same empty 404 the root router renders (§2.2). Each format-specific sub-router enforces authentication and protocol-compliant header parsing independently against the enabled gateway API keys stored in the database and managed through the management API (§7.1): the `/openai-v1` sub-router via `Authorization: Bearer <key>` conforming to the OpenAI specification (the `Bearer` scheme is compared case-insensitively per RFC 9110 §11.1 while the key itself is compared byte-exactly; malformed header forms — missing space, tab separator, glued scheme, leading whitespace, trailing content — are rejected); the `/gemini-v1beta` sub-router via the `x-goog-api-key` header only (no `?key=` query form); the `/anthropic-v1` sub-router via the `x-api-key` header only, with the `anthropic-version` header required present (value not validated).
   - All token comparisons use constant-time byte comparison. Mismatch yields HTTP 401. An empty or fully disabled key table authorizes nothing: a fresh database serves no outward traffic until the first key is created through the management API.
   - Error response bodies are router-domain specific:
     - Root router: plain HTTP 404 with an empty body.
     - Management API version sub-router (`/management-api/v0/*`): `{"errno": <numeric errno>, "message": <human-readable message>}`; the closed errno taxonomy and each errno's pinned HTTP status are defined in §7. An unmapped path outside every management API version reaches no version's 404 response and is answered with the shared empty 404 (§2.2).
     - Outward API format 404s: OpenAI JSON error structure `{"error": {"message": ..., "type": ..., "param": null, "code": ...}}` (404 carries `type: "invalid_request_error"`, `code: null`, `message: "Invalid URL (<METHOD> <path>)"`); Gemini `{"error": {"code": 404, "message": ..., "status": "NOT_FOUND"}}` per the official Status shape (google.aip.dev/193 — numeric HTTP `code`, canonical `status` name); Anthropic `{"type": "error", "error": {"type": "not_found_error", "message": ...}}`. Each surface also owns its 401/405 bodies in its own shape (§6.7).
2. **Plaintext Credential Storage**:
   - Upstream credentials and tokens are stored directly in plaintext JSON within the database, and gateway API keys are stored directly in plaintext alongside them. No encryption or decryption is performed.
3. **Network Invariants**:
   - Inbound endpoints do not use sessions or cookies. Cross-Origin Resource Sharing (CORS) is configurable independently on the outward API sub-router (`/api`) and the administrative management API sub-router (`/management-api`) via `cors` (`allowed_origin`, `allow_private_network`) in configuration. Preflight `OPTIONS` requests are handled and matching CORS response headers are attached, including Private Network Access headers when enabled.
   - The TCP listener pins `SO_REUSEADDR` on Unix platforms so a prompt restart never fails to bind while the previous run's connections still drain in TIME_WAIT; Windows is left at the socket default, because its `SO_REUSEADDR` semantics would let a second socket bind over a port another socket actively holds.
   - Accepted inbound TCP connections enable `TCP_NODELAY` (best-effort: a failure is logged and the connection is still served), so small streaming frames — SSE events in particular — are written immediately instead of stalling against Nagle's algorithm and the peer's delayed ACK.
   - Inbound connections speak HTTP/1 or HTTP/2, selected per connection by hyper-util's protocol auto-detection; TLS connections offer both `h2` and `http/1.1` through ALPN.
   - HTTP/1 connections that do not finish sending request headers within 30 seconds are closed; the deadline engages once protocol detection has selected HTTP/1. HTTP/2 connections are probed with keep-alive PING frames: a connection idle for 30 seconds is pinged, and a ping that goes unacknowledged for 20 seconds closes the connection. A PING must be answered by the peer's HTTP/2 stack — the kernel cannot answer on its behalf, unlike TCP keep-alive — so live-but-idle clients survive while dead or silent HTTP/2 peers are reaped.
   - Connections may park indefinitely between acceptance and their first request headers: neither hyper-util's protocol auto-detection nor the Rustls TLS handshake exposes a deadline, and no first-request deadline is imposed deliberately. A first-request deadline would burden legitimately slow clients while failing to bound resource exhaustion — an attacker holding sockets via slow request bodies or slow keep-alive traffic makes the same investment as one holding sockets silently — so the socket-exhaustion threat is answered, if ever, by connection-count limiting at the accept edge, not by opening-phase timeouts.
   - Outbound requests to upstream providers connect directly without proxying.
   - Both upstream HTTP clients refuse redirects outright: a 3xx response is itself the response the caller receives and flows through the existing non-2xx paths (gateway error mirroring §6.7, control-stage rejection §5.3), so definition-declared credential headers and request bodies are never re-dispatched to the `Location` origin.
4. **Resource Bounds** (value — where enforced — what it bounds):
   - Upstream connect timeout, 10 s — both upstream HTTP clients — TCP connection establishment to an upstream provider.
   - Upstream read idle timeout, 300 s — data-plane upstream HTTP client — silence gap between consecutive reads of an upstream body (reset after every successful read, so it never truncates a slow-but-flowing response; the data plane sets no total request timeout, so a long generation is never cut off).
   - Control-plane total timeout, 30 s — control-plane upstream HTTP client — total wall-clock budget of one short control-plane request (OAuth token exchange and refresh, model discovery, project onboarding §5), so a stalled request fails below the 90-second refresh-lease staleness window and below the 60-second device-flow claim-staleness window (§3) instead of holding its lease, its device-flow claim, or the requesting client for minutes.
   - Inbound HTTP/1 header-read deadline, 30 s — HTTP/1 connection builder — time a client may take to finish sending request headers before the connection is closed; it engages once protocol detection selects HTTP/1 (hyper's effective default is pinned explicitly, as the default is declared unstable).
   - Inbound HTTP/2 keep-alive PING interval, 30 s — HTTP/2 connection builder — idle time before an HTTP/2 connection is probed with a PING frame.
   - Inbound HTTP/2 keep-alive acknowledgment deadline, 20 s — HTTP/2 connection builder — time a peer has to answer a keep-alive PING before the connection is closed.
   - Inbound HTTP/2 concurrent streams per connection, 200 — HTTP/2 connection builder — concurrent request streams one connection may hold (hyper's effective default is pinned explicitly, as the default is declared unstable).
   - Inbound HTTP/2 header list size, 16 KiB — HTTP/2 connection builder — HPACK-decompressed header bytes one request may carry; larger header lists are rejected, bounding HPACK-bomb memory (hyper's default is ~16 MB and declared unstable).
   - TCP listen backlog, 32 — TCP listener setup — pending, not-yet-accepted connections the kernel queues before refusing new ones.
   - Request body caps, 64 MiB outward and 2 MiB management — axum body-limit layer on each sub-router — larger request bodies are rejected with HTTP 413.
   - SSE frame cap, 16 MiB — SSE frame parser — a single upstream SSE frame; a larger frame aborts the stream as malformed.
   - SSE body channel buffer, 64 — between the SSE renderer and the response body — backpressure toward the client. Upstream SSE/JSON parsing is lazy, polled directly by the response task without a producer task or an intermediate IR-event channel.
   - Upstream error-body reads, 4 KiB with 400-character excerpts — every upstream failure the gateway renders (gateway error mirroring §6.7, OAuth token endpoint rejections §5.3, model discovery rejections §7.1) — memory held to carry an upstream failure message.
   - Upstream success-body reads, 64 MiB — every non-streaming upstream success body the gateway buffers before parsing (completion responses and native-compaction reads, `src/http_body.rs`) — one complete JSON document; a body beyond the cap fails the request as an upstream failure instead of buffering unbounded bytes. The cap is the outward request-body cap of 64 MiB — the largest single exchange the gateway already buffers per request — far above any legitimate JSON, giving the JSON transport the same hostile-upstream posture the 16 MiB per-frame SSE cap gives the streaming transport.
   - Accept-failure backoff, 10 ms doubling to a 1 s cap — TCP accept loop — retry delay after a failed accept attempt.
   - OAuth onboarding budget, 60 s — the provisioning poll's budgeted long-running operation (§5.4) — total wall-clock time for project-ID resolution.

## 5. Provider Definitions: Descriptors, Engines, Presets

A provider definition is data. The engines — the five format codecs, the OAuth engine (all grant kinds), the provisioning engine, the discovery engine, the control-request executor, and the template interpreter that binds them — never special-case a provider. This section is the normative descriptor contract; the descriptor Rust types live in `src/provider/definition/`, and the wire shape follows the codebase convention (`type`-tagged enums, `deny_unknown_fields`).

Descriptor structure has one private owner, `provider/definition/expressions.rs`: its concrete borrowed surfaces enumerate values, row and object names, codec-body placeholders, and coalesce structure. Base-reference queries and required OAuth reference checks reuse that same enumeration as stage validation. `validate.rs` owns stage availability, slot sequencing, destination syntax, body-count rules, and diagnostics; literal JSON remains opaque. `DefinitionPayload` centrally enumerates the surfaces eligible to require an instance base URL, excluding the authorization URL and extra parameters whose stage forbids Base.

### 5.1 Templates, Control Requests, and Response Mappings

Every templated string in a descriptor — a URL, a header value, a query or form value, a JSON string leaf — is one **`StringExpr`**: an ordered sequence of `ValueExpr` parts concatenated into a single string. A literal string is a one-part expression; an authorization header is `[Literal("Bearer "), Secret]`; an inference URL can be `[Base, Model, Literal(":generateContent")]`. There is no separate URL placeholder parser or string-template language.

The value vocabulary: `Literal`, `Secret` (the API key or the flow's/provider's current access token), `Slot` (a working flow slot, or a stored credential slot afterward), `ClientId`, `ClientSecret`, `AuthorizationCode`, `CodeVerifier`, `RedirectUri`, `OAuthState`, `DeviceCode`, `RefreshToken`, `RequestUuid` (one fresh UUID per upstream inference dispatch, reused by every reference in that dispatch — headers and envelopes included; a later dispatch gets a new one), `Model` (the routed model's `upstream_id`), `Base` (the working flow / stored provider base URL), and `Coalesce` (first non-empty part — the Antigravity tier selection). `Coalesce` is the only compound part; nothing nests beyond its arguments. OAuth values are available only at stages that produce them, and the management write boundary validates each stage's expressions against exactly that subset — runtime evaluation of an absent value is stored drift and fails fast. Missing slots evaluate to the empty string, which is what lets a `Coalesce` over provisioned slots pick the first one the flow placed. URL assembly, header construction, and JSON rendering remain destination-specific consumers of the one evaluated expression.

**Control requests** — OAuth device authorization, token exchange, refresh, provisioning, polling, and discovery — share one shape: `{method: GET|POST, url: StringExpr, headers: [(name, StringExpr)], query: [(name, StringExpr)], body: none | form([(name, StringExpr)]) | json(TemplateNode)}`. `TemplateNode` is the typed JSON tree `Json (any literal leaf) | String (StringExpr) | Body | Object | Array`; an `Object` renders its members in the canonical lexicographic order of its name map, a repeated member name folding into its last spelling — member order and repetition are never carried — and `Body` is the codec-rendered upstream body and is forbidden in control requests. The executor sets `Content-Type` from the body variant; every other header, `Accept` included, is an explicit row — and because a header row reaches the wire as a literal header name, every header-row name across the definition (inference headers, every control request's headers, poll headers) must be a valid HTTP header name, and the operator-authored text of every header-row value — its literal segments, plus the configured client credentials once at the recipe — must be valid HTTP header-value bytes; the write boundary enforces both with a 400 naming the offending row, and dynamic value sources keep their fold-time contracts. Query-row names are exempt, riding their percent-encoding. Query rows — names and values alike — percent-encode with the same strict RFC 3986 unreserved-set encoder as the authorize URL (§5.3) and reach the built request pre-encoded, so the HTTP client's form encoding never re-encodes them — a space stays `%20` instead of the form-urlencoded `+`, which RFC 3986 §3.4 makes a literal plus in a query — while form bodies remain `application/x-www-form-urlencoded`, whose `+`-for-space rule is the content type's own. Rows join through one assembly step shared with the authorize-URL builder (§5.3): the `?`/`&` separator is placed into the evaluated URL's query component — before a `#` fragment when the URL carries one, the fragment riding again after the last row (RFC 3986 §3, everything after the first `#` being the fragment) — so an appended parameter can never fold into the fragment and silently drop from the request.

**Response descriptors** declare `encoding: json|form` and map fields `{path, target, required}`. `path` is the closed mini-vocabulary of object-member chains (empty = root; form responses are flat, one member). One descriptor maps each target at most once (write-time enforced, provisioning extraction lists included): the fold applies the fields in order, so a repeated target's earlier mapping is dead configuration silently overwritten by the later one — while cross-stage repeats stay allowed, several stages writing one slot each from its own response. A missing required path fails the stage; a missing optional path leaves its target unchanged; a present value of the wrong declared shape (`string`, `integer`, or `string_or_field:<f>` for the bare-string/`{field}`-object polymorphism) always fails — except that the `string` shape also reads a JSON number, rendering it as its decimal text (RFC 6749 §5.1, "Numerical values are included as JSON numbers"; RFC 8628 §3.2's numeric example), while a boolean or an object stays the wrong declared shape. Token-endpoint **error** parsing stays generic in the engine: RFC 6749 §5.2 string form, object form (`{error: {code}}`), and form-encoded `error=` are all attempted, and the extracted code is matched case-insensitively against the stage's configured `terminal_codes` — the full list is configuration, with no engine defaults.

### 5.2 Inference Descriptor

- `url` (required) and `stream_url` (optional): the dispatch selects the streaming URL only when streaming and one is configured. `headers` subsumes the auth style — `Authorization: Bearer <secret>`, `x-api-key: <secret>`, `x-goog-api-key: <secret>` are ordinary rows, whose names the write boundary holds to valid HTTP header names (§5.1).
- `upstream_streaming`: `always` (the upstream requires streaming; non-streaming clients get an aggregated response) or `match_client`. The decision drives both the rendered body's stream flag and the SSE-versus-JSON parser choice — never response-header sniffing.
- `render_options`: a closed per-format set (today `omit_max_output_tokens` on `openai_response` only); codecs reject options outside their set at write time. Adding one is the documented extension path.
- `envelope` (optional): a `TemplateNode` whose `Body` appears exactly once — the codec-rendered upstream body is spliced in at that node (the Antigravity request wrapper).
- `response_unwrap` (optional): the object member the gateway unwraps before the codec's parser ingests a response — JSON bodies and SSE frames alike (the Antigravity `response` envelope); absent means ingest as-is.
- The engine owns `Accept` (set from the stream decision); definition headers override it only by explicit row.

Data-plane connection assembly lives in `gateway/request.rs`: inference and explicit compaction operations share evaluated URL/header construction and typed envelope attachment. An operation's header overlay replaces inference rows case-insensitively; overlay rows precede surviving inference rows, preserving the order of both lists and their repeated rows. Every dispatch retains one request UUID across its URL, headers, and envelope. `gateway/dispatch.rs` owns the single send boundary: stamp immediately before sending, observe headers immediately after receiving them, bind account ownership on successful headers, and read a rejected bounded body once. Generation and native compaction classify and persist quota evidence before operation-specific unsupported classification; token counters explicitly disable quota classification. Successful payload parsing remains lazy for ordinary generation and eager for internal compaction, with no intermediate parser task or channel.

### 5.3 Credential Acquisition

`credential` is a tagged enum: `api_key` carries no secret and no OAuth settings; `oauth` carries the recipe — `client_id`, optional `client_secret`, optional `access_token_lifetime_seconds`, `initial_slots` (generators `uuid` | `uuid_hex`, run once per new flow before its first external request; reauthorization starts from the target provider's stored slots and initializes only missing names), the `grant`, the `exchange`, `id_token_claims` (JWT payload claims copied into slots), and the `refresh` mode.

- **Grant** `authorization_code`: `authorize_url` base, `redirect_uri`, `pkce: none|s256`, and `extra_params`. The builder appends `response_type`, `client_id`, `redirect_uri`, `state`, and the S256 `code_challenge` pair itself, percent-encoding every query component; extra parameters carry the rest (scopes, provider flags, markers), and an `extra_params` row naming one of the builder-owned parameter names — `response_type`, `client_id`, `redirect_uri`, `code_challenge`, `code_challenge_method`, `state`, matched case-sensitively — is rejected at the write boundary, because the duplicate row renders two same-named query parameters whose resolution is the upstream's. The write boundary requires an `s256` grant's exchange request to reference the `code_verifier` value part somewhere its expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because RFC 7636 §4.6 presents the verifier at the token endpoint whenever a challenge was sent, and conversely rejects an exchange request referencing the `code_verifier` value part under `pkce: none`: the begin mints the verifier exactly when the grant declares `s256` (its presence is the challenge pair's marker, RFC 7636 §4.2), so the reference is unsatisfiable and fails every exchange. The write boundary likewise requires an authorization-code grant's exchange request to reference the `redirect_uri` value part somewhere its expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because the builder appends `redirect_uri` to every authorization request and RFC 6749 §4.1.3 requires the token request to repeat it, identically, whenever the authorization request included it. The write boundary likewise requires an authorization-code grant's exchange request to reference the `authorization_code` value part somewhere its expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because the flow's completion supplies the pasted code and RFC 6749 §4.1.3 makes `code` REQUIRED in the token request, and a flow is consumed by its first completion attempt even when the exchange then fails (§7.2).
- **Grant** `device`: the authorization `ControlRequest` plus its response mapping, whose targets are `device_code`, `user_code`, `verification_uri`, `verification_uri_complete`, `expires_in_seconds`, `interval_seconds`. The write boundary requires `device_code` and `user_code` marked required and at least one verification URI; a missing interval means five seconds per RFC 8628; missing expiry is accepted only when the definition supplies `expires_in_fallback_seconds`, which the write boundary requires whenever the expiry mapping is absent or optional. The write boundary likewise requires a device grant's exchange request — the grant's polling request — to reference the `device_code` value part somewhere its expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because RFC 8628 §3.4 makes `device_code` REQUIRED in every token request, and a poll without it would ride non-terminal rejections until the flow's own expiry. The write boundary likewise requires a credential with no `client_secret` — RFC 6749 §3.2.1's not-authenticating condition — to reference the `client_id` value part somewhere the device-authorization request's expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because RFC 8628 §3.1 makes the client ID REQUIRED in the device-authorization request when the client is not authenticating; a credential with a client secret authenticates with it and is exempt. A present non-positive `interval` or `expires_in` is a malformed device-authorization response (RFC 8628 §3.2).
- **Exchange**: the `ControlRequest` whose form or JSON fields explicitly use `StringExpr` values (`grant_type` is a literal; `code`, `code_verifier`, `redirect_uri`, `device_code` the corresponding parts; GitHub's JSON `Accept` an ordinary header) plus its response mapping and `terminal_codes`. Exchange targets: `access_token`, `refresh_token`, `expires_in_seconds`, `id_token`, `base_url`, `slot:<name>`. The `access_token` may be supplied by a later provisioning step instead, but must exist before the provider write, and a provisioning extraction supersedes the response's token data — the response's expiry evidence is validated only when consulted; a mapped `expires_in` must still decode as an integer at the mapping boundary, its positivity being consult-time. An extracted `base_url` replaces the flow's stored base; a provisioning extraction replaces it again. Under a device grant this same request is the polling request; `authorization_pending` and `slow_down` are engine-owned schedule outcomes, not terminal codes, and a rejection whose code is outside `terminal_codes` is likewise only a schedule outcome, riding the stored interval until the flow's own expiry ends it. The write boundary likewise requires a credential with no `client_secret` — RFC 6749 §3.2.1's not-authenticating condition — to reference the `client_id` value part somewhere its expressions live in both the exchange request and a `grant` refresh's request — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because RFC 6749 §4.1.3 makes the client ID REQUIRED in a token request when the client is not authenticating and §6 re-authenticates the same way at every renewal; a credential with a client secret authenticates with it and is exempt. The write boundary conversely rejects every credential-stage expression referencing the `client_secret` value part when the credential configures no client secret — the authorize URL and its parameters, the device-authorization request, the exchange request, a `grant` refresh's request, and the provisioning steps and polls — because every stage that admits the part receives the configured secret, so the reference is unsatisfiable stored drift failing every evaluation (§5.1).
- **Refresh**: `grant` (its own request, optional response mapping defaulting to the exchange's, and terminal codes — a rejection whose code is in the list diagnoses the dead refresh token as needing re-authorization), `reprovision` (requires a non-empty provisioning list whose sequence extracts an `expires_at_unix_seconds` target), or `none` (always the tagged `{"type": "none"}` object; an OAuth-acquired credential that never renews). The write boundary requires a `grant` refresh's request to reference the `refresh_token` value part somewhere its expressions live — URL, header row, query row, form field, or JSON string leaf, directly or through a coalesce — because RFC 6749 §6 makes `refresh_token` REQUIRED in a refresh-token grant request, and a request without it fails at the upstream on every renewal into the grant's terminal-code diagnosis, sending a healthy provider into an endless re-authorize/refresh-fail loop. The write boundary likewise requires the referenced refresh token to have a guaranteed source — the exchange response mapping the `refresh_token` target `required`, or a `required` extraction in an unconditional provisioning step (a conditional `skip_if` step guarantees nothing) — because RFC 6749 §5.1 leaves the token optional in a success response, so an optional-only source would let an upstream legitimately omit it and strand every renewal on the absent stored value, while a required source fails the producing flow outright and keeps the stored token's presence guaranteed. The write boundary likewise requires a declared refresh response mapping to map the `access_token` target — a declared mapping replaces the exchange's default, and RFC 6749 §6 makes `access_token` REQUIRED in a refresh response — so a declared mapping without the token row is rejected at the write instead of failing every renewal at runtime. The write boundary covers the defaulted case the same way: a `grant` refresh with no declared response reuses the exchange response's mapping as the effective refresh mapping, so that mapping must map the `access_token` target — a token supplied only by provisioning is never renewed, and a provisioning-only token source would wedge every renewal after the token's first expiry. Static keys have no OAuth configuration at all.

### 5.4 Provisioning

An optional ordered sequence run after a successful exchange — and as the refresh action for `reprovision`, under the existing lease. Each step is one control request whose extractions fold into the flow's working state (`slot:<name>`, `access_token`, `refresh_token`, `base_url`, `expires_at_unix_seconds`); `skip_if: <slot>` runs the step only while that slot is absent (the conditional arm); `poll` repeats a request until its `done_path` turns true within a wall-clock budget, failing on the `error_path` payload and folding `result_extract` on completion. Both poll paths are object-member chains the write boundary shapes: a `done_path` must be non-empty — an empty chain addresses the response root, whose truthy read is always false, and the poll would end only at budget exhaustion, never completing — while an empty `error_path` is the configured no-error-inspection, under which the poll never fails on a payload. The provisioning stage's `secret` value is the exchange's access token, so a definition whose exchange maps no `access_token` target may not reference `secret` in its provisioning expressions — the boundary rejects the combination, and a provisioning-supplied token is reachable through the slot its extraction writes. Slot and base-URL values are validated as machine-consumed text before storage — the one contract every OAuth response fold applies, the exchange's and refresh grant's included, so a value an upstream response extracts is validated identically whichever stage extracted it. Extractions run before the poll, so the poll request can reference an operation name a previous step placed in a slot. The provider row changes only when all steps commit — atomically with the outcome, under the lease for a reprovisioning. A refresh mode of `reprovision` requires its sequence to extract an `expires_at_unix_seconds` target (write-time enforced), so a renewal always persists a fresh expiry and never rewrites the stored one to the `null` no-scheduled-refresh state; a reprovisioning that nonetheless completes without one is stored drift and fails the renewal. A provisioning-extracted expiry is consulted evidence (§7.2): it must be in the future, else the step fails as a malformed provisioning response. On the device grant the poller re-stamps its claim after provisioning returns and before the commit, so a provisioning sequence longer than the claim-staleness window (§3) cannot be stolen mid-commit; a re-stamp that finds the claim stolen abandons the commit instead.

### 5.5 Discovery

An optional descriptor: one control request, an extraction (`array_at` + `id_field` + optional `strip_prefix`, or `map_keys` over an object), and a pagination mode (`none`, token `pageToken`/`nextPageToken`-style, or cursor `has_more`/`last_id`-style, each with a page budget). A page budget that ends while the upstream still reports more pages — a next token present, or `has_more` true — fails the refresh as an upstream error before any storage write, so a too-small budget can never silently truncate the list. The continuation paths are non-empty member chains (write-time enforced): an empty chain addresses the page root, which can never continue the walk — a root object reads as a malformed token on every page, and a root object's truthy read is always false — so the boundary rejects the spelling rather than admit a mode that fails every refresh or ends after page one under a never-firing budget guard. In token pagination a present, non-null next-page token that is not a usable string fails the refresh as an upstream error — such a page is malformed, not finished — while an explicit `null` reads as the absent member, ending the walk, and an empty string reads as absent, an empty token naming no page. Discovery obtains identifiers and — where the descriptor declares a capability extraction — per-model capability facts; it never assigns protocol capability, and an unsupported combination still produces the upstream error when that model is called. Discovered identifiers are validated as routing tokens at the ingestion boundary before any row is written, and the existing `discovered`/`vanished`/`manual` state machine is untouched. A definition without discovery serves manual models only.

**Capability extraction** (§3) rides the `array` extraction as an optional `capabilities` object — the `map_keys` shape carries no per-entry object and declares none. `thinking_levels` is extracted through one of two shapes: `member_array` (`array_at` + `level_field` — each element of the addressed array names one level in a string member; the Codex backend's `supported_reasoning_levels[].effort`), or `flagged_keys` (`object_at` + `flag_field` — the addressed object's member names are levels, each member an object carrying its boolean flag at `flag_field` or a bare boolean standing as its own flag; the Anthropic `capabilities.effort` object, whose aggregate `supported` member is a bare boolean no vocabulary filter admits). `max_input_tokens` and `max_output_tokens` are integer member paths into each entry, non-empty by the same write-time rule as the continuation paths — the entry itself is never an integer. Extraction is strict and per-entry: a configured path absent or `null` on an entry leaves that entry's column `NULL` (unknown), while a present value of the wrong shape — a non-array where an array is declared, a non-string level member, a missing or non-boolean flag, a non-integer or non-positive token — fails the refresh as an upstream error before any storage write. A level string outside the shared vocabulary (§6.4) is silently skipped: the declared set is the model's supported levels within the closed vocabulary — a value the gateway would itself reject as a request parameter (the Codex backend's `ultra` and `persistent`, and model-defined custom efforts) is not a declaration the gateway can honor, so it never becomes one. Extracted sets are canonicalized on write: deduplicated, vocabulary-ordered.

The optional `compaction` extraction (§5.9, §6.8) reads per-mechanism compaction facts out of every entry, one boolean flag per configured mechanism: `messages_on_demand` and `messages_threshold`, each an `object_at` + `flag_field` pair addressing one object of the entry and the boolean member inside it (the Anthropic `capabilities.compaction.supported` and `capabilities.context_management.compact_20260112.supported` shapes — two independent facts, never one aggregate capability). A `true` flag extracts the mechanism's `supported` fact and a `false` flag its `unsupported` fact, both into the discovery-owned `compaction_support` column; an absent-or-null object or flag extracts nothing, leaving that mechanism unknown — the base column never stores `unknown`, because discovery extracts booleans and nothing else. A resolved object that is not a JSON object, or a flag that is neither boolean nor absent/null, fails the refresh as an upstream error before any storage write, exactly like every other present-wrong-shape capability value. Each refresh rewrites the whole column per row — facts a newer refresh no longer reports do not survive as residue.

The catalog is the only home for presets: the backend carries no provider constants and never seeds rows. Each preset carries its reference-implementation provenance (repo + rev / doc URL) and a verification status:

The OAuth and researched presets carry the compaction declarations (§5.9) their evidence supports, and evidence is per-mechanism: the Codex preset declares the explicit trigger and the automatic threshold compaction supported — the endpoint capabilities its client and backend behavior demonstrates — while nothing there evidences the standalone compact endpoint; the Claude Code preset declares the Messages on-demand and threshold mechanisms supported, each with its own beta overlay (`compact-2026-09-04` and `compact-2026-01-12`, two separate facts); the xAI preset declares the standalone compact operation supported and the explicit trigger and automatic compaction unsupported — a standalone compact endpoint does not imply native trigger or automatic compaction. Every one of these declarations rides an `unverified` preset until a live compact-and-continuation run verifies it.

### 5.7 Gemini Interactions Upstream Wire

The wire contract of the Interactions upstream. The codec speaks the **official Gemini Interactions dialect in both directions** (upstream parse/render and the outward `POST /interactions` client surface): the member shapes are pinned by the official reference (`ai.google.dev/api/interactions-api`, mirrored by the `googleapis/python-genai` types), not self-invented. What the official documents leave unpinned — whether SSE frames carry an `event:` line at all, and how partial a `step.start`'s step object may be — the gateway covers by emitting both discriminators (`event:` line and `event_type` member), accepting either inbound, and parsing step openings tolerantly.
- Always `store: false`, never `previous_interaction_id`: stateless full-history replay through the `input` Step array — `user_input` steps (`content` blocks), model `model_output` steps (`content` blocks), model `thought` steps (`summary` as a content-block array, optional `signature`; the step carries no `id`), model `function_call` steps (`id`, `name`, `arguments` as the JSON object itself — the official step carries **no** `signature` member, so the replayable thought signature rides the `thought` step), and `function_result` steps (`call_id`, optional `name`, optional `is_error`, `result` as string/blocks/object). Same-family thought steps replay byte-exact (opaque payload preserved; README §6.1), and the thought step is the bridge slot across the two Gemini protocols as well: a `function_call` whose upstream reported a GenerateContent `functionCall.thoughtSignature` renders a signature-only `thought` step beside the call — `summary` being optional on the official ThoughtStep (`ai.google.dev/api/interactions-api`) — both in the aggregated resource and as a `thought_signature` delta on the streamed wire, while an inbound thought step replays toward a GenerateContent upstream as that protocol's thinking part (`thought: true` text, the step's signature riding the part's `thoughtSignature`; README §6.4).
- Request body: `model` = `upstream_id`; `system_instruction`; typed function tools (`{"type": "function", name, description, parameters: JSON Schema}`); `generation_config` (`max_output_tokens`, `thinking_level` from the enum verbatim, `tool_choice` as `auto`/`any`/`none` or `{"allowed_tools": {"mode": "any", "tools": [<one function>]}}`) — the official `generation_config` pins **no sampling members** (no `temperature`, no `top_p`), so IR sampling values have no wire slot on this family and are dropped, never rewritten; `response_format` from the IR (official union `text`/`audio`/`image`/`video` — the gateway renders the `text` member, `{"type": "text", "mime_type": "application/json"}` for JSON outputs with the schema beside it; the OpenAI-style schema *name* has no official slot here and is dropped); `stream`.
- Streaming: SSE, discriminated by the `event:` line when the frame carries one, else by the payload's official `event_type` member. Events: `interaction.created` and the terminal `interaction.completed`, each carrying a partial Interaction resource under the `interaction` member; `step.start` (`{index, step}`), `step.delta` (`{index, delta}`), `step.stop` (`{index}` — the official stop carries **no** step, so the streamed deltas are the content of the steps they streamed; it may also carry `step_usage` (per-step) and `usage` (cumulative), both deliberately ignored in favor of the terminal resource's total); and the progress-only `interaction.status_update`, parsed and ignored (the terminal status and the usage total the gateway reports arrive only on `interaction.completed`). The official terminal resource carries `steps` only "if included in this event", so `interaction.completed` doubles as the fallback content source, and the gate is content-bearing delivery, not step opening: a bare `step.start` opening — or a delta carrying no payload — delivers nothing and leaves the fallback live, while a stream whose live `step.start`/`step.delta` events delivered content ignores the terminal resource's `steps` wholesale (the decision made once, before the walk), and a stream that delivered none recovers them exactly once through the complete-step path (text, reasoning, tool calls — rendered exactly as a non-streaming body's steps). The call half is content-gated the same way: a closing `step.stop` always delivers the complete call — the streamed argument bytes, or the empty object a zero-argument call's state assembles to — so a delivered call silences the terminal resource's `function_call` copies even where the steps fallback stays live, whose undelivered step kinds remain recoverable. Delta kinds: `text`, `thought_summary` (one optional content block), `thought_signature` (optional signature), `arguments_delta` (optional arguments); every other kind — media output (`image`/`audio`/`video`/`document`), `text_annotation_delta`, the server-side tool call/result deltas, and future kinds — is parsed and ignored, never aborting a stream of official events.
- Non-streaming: the Interaction resource (`id`, `model`, `status`, `steps`, `usage`).
- Status → finish mapping: `requires_action` → ToolCall; `incomplete` → Length (the deprecated `budget_exceeded` → Length too, the official documents it returning the same result); `cancelled` → Stop (deliberate: the interaction ended without failure and the canonical finish vocabulary has no cancelled member); `failed` → upstream failure per the error-mirroring policy; `completed`, the non-terminal `in_progress`/`queued` (which never terminate a conformant stream), and any future status → Stop.
- Usage: `total_input_tokens` → input; `total_output_tokens + total_thought_tokens` → output (IR output includes reasoning, matching the existing GenerateContent codec); `total_thought_tokens` → reasoning; `total_cached_tokens` → cached; no cache-write; `total_tool_use_tokens` and the by-modality breakdowns dropped.

### 5.8 Anthropic Messages Upstream Wire

- The wire contract of the Anthropic Messages upstream. `max_tokens` is required by the API: the client's `max_output_tokens` renders when present, else the fixed synthesis constant **16384**.
- Render: `system` string from IR instructions; IR messages grouped into strictly alternating user/assistant turns (first turn user; consecutive same-role IR messages merge; empty rendered content is not emitted); assistant reasoning blocks before their tool calls — a replayable same-family `thinking`/`redacted_thinking` block (a `thinking` block needs its non-blank signature) replays its opaque payload verbatim, while any other reasoning part — foreign-family, or a `thinking` shape without a signature — renders nothing (the official `ThinkingBlockParam` requires the upstream's own `signature`, so no synthetic block can replay; the API treats thinking history as optional); `tool_result` blocks (`content` string or text blocks, `is_error`); tools (`name/description/input_schema`); `tool_choice`; `output_config.effort` or `thinking: disabled` per the enum (§6.4); `output_config.format` renders `{"type": "json_schema", "schema": …}` from the IR `json_schema` response format beside the effort — the official `JSONOutputFormatParam` requires both its members, and the OpenAI-style schema *name* has no official member and is dropped — while free-form `json_object` has no upstream slot and fails naming `response_format`; `temperature`/`top_p` verbatim.
- Client direction: in the aggregated response body a same-family block replays its opaque payload verbatim only when it is replayable — a `thinking` block carrying its non-blank `signature`, or a `redacted_thinking` block (which carries `data` and no signature member by design); every other reasoning block — foreign-family, or a `thinking` shape without a signature — renders its text as an ordinary `text` block, because a signature-less `thinking` block is a shape the official schema forbids (`ThinkingBlock.signature` is required, like the request-direction `ThinkingBlockParam`) that could never replay, while the text is real content the replay-safe text channel carries. The streaming surface is unaffected: reasoning streams through the native `thinking_delta`/`signature_delta` frames documented below, whose frames are transient and never aggregate into a replayable block.
- Streaming: `message_start` (usage: input + cache columns), `content_block_start/delta/stop` (`text_delta`, `thinking_delta`, `signature_delta`, `input_json_delta`; the thinking block's start frame carries the official empty `signature` member — required on the official `ThinkingBlock` shape — which stays `""` until the `signature_delta` lands), `message_delta` (stop reason, cumulative output usage), `message_stop`, `ping`; mid-stream `error` events abort per policy. The outward `message_start.usage` carries the input and cache columns of the stream-head partial report when the upstream published one at stream head and zeros otherwise, and the terminal `message_delta` always carries the authoritative totals, which consumers merge over the opening ones. The outward renderer opens a `tool_use` block and emits its `input_json_delta` and `content_block_stop` together when the call completes rather than streaming argument fragments live — one conformant delta frame per call, chosen so the block's `id` and `name` are always known when it opens.
- stop_reason → finish: `end_turn` → Stop; `max_tokens` → Length; `model_context_window_exceeded` → Length (the turn truncated because the context window filled); `tool_use` → ToolCall; `stop_sequence` → Stop; `refusal` → ContentFilter; `pause_turn` → Stop.
- Usage: `input_tokens`, `output_tokens`, `cache_read_input_tokens` → cached, `cache_creation_input_tokens` → cache_write; `output_tokens_details.thinking_tokens` → reasoning (reported on the complete body's usage; in streaming only on the final `message_delta` event). The official Messages usage shape carries `output_tokens_details: {thinking_tokens}` (the `anthropic-sdk-python` `Usage`/`OutputTokensDetails` types), so the outward usage — the aggregated body and the terminal `message_delta` alike — renders that member with the IR reasoning value whenever the upstream reported the breakdown and omits the member when it did not.

### 5.9 Compaction Descriptor

The optional `compaction` section of a definition payload (§6.8) is the definition-level connection data remote compaction runs through. It is stored as its own `json_valid` column beside the other descriptor sections (§3), and a payload may name the section as `{}` to receive every default — the fully-unknown posture that selects gateway summarization for every compaction request. The section never decides a dispatch by itself: a mechanism's effective support resolves per selected model from an administrator override, then a discovery-owned model fact, then the declaration's `default` (§6.8), so the declaration is what a definition advertises and how it executes, not a routing verdict.

- `strategy`: `native_preferred` (the default — select a compatible configured native operation, otherwise summarize through ordinary inference on the selected provider/model, with a positively classified runtime unsupported response permitted one summary fallback) or `gateway_summary` (always generate a gateway summary, even when native compaction exists — the mode for portable state across later provider changes).
- `summary_budget` and `retention_budget`: typed nonzero token budgets, defaults 4096 and 8192. The summary budget bounds a gateway-generated summary's output; the retention budget is the soft target the retained suffix of a gateway checkpoint selects under (§6.8). Both are gateway budgets, never vendor capability facts.
- `can_export_native_summary`: `false` by default. It permits readable native compaction text to become ordinary summary text when the new target cannot consume the native block; it never authorizes discarding opaque reasoning or retaining invalid signed thinking. An intentional, documented downgrade — not native compatibility.
- `mechanisms`: the five per-mechanism declarations, every member optional — an absent member is the unknown state, meaning no declaration at all:
  - `responses_standalone_compact` carries `default`, the `operation`, and the `unsupported` classifier. The operation describes the compact connection independently of the inference descriptor — `url` (a `StringExpr`, never derived by appending to the inference URL), the full `headers` row list (subsuming the auth style), an optional one-`Body` `envelope` (§5.1), and an optional `response_unwrap` member — and frames its own parsing and body stream flags: the operation dispatches always non-streaming JSON, so an inference descriptor that forces SSE does not force it here, and a JSON upstream compact result still renders to a streaming caller's lifecycle. `default: supported` requires the `operation` (write-time enforced).
  - `responses_explicit_trigger` and `responses_automatic_compaction` carry `default` and the `unsupported` classifier: the trigger and the automatic controls ride the ordinary inference request, so no operation data exists.
  - `messages_on_demand_compaction` and `messages_threshold_compaction` carry `default`, the `overlay_headers`, and the `unsupported` classifier. The overlay headers ride the ordinary inference connection while the mechanism's beta applies — the `anthropic-beta` declaration foremost — and an overlay row replaces the inference's same-named row. `default: supported` requires non-empty overlay headers (write-time enforced), because a definition cannot advertise native support without configuring how to execute it; the same headers serve the replay of a returned compaction block, wherever the block later travels.
- `count_tokens` (optional, `anthropic_messages` only): the native token-count operation of the format's concrete count request — `url`, `headers`, `envelope`, `response_unwrap`, the same connection primitives, never guessed from the inference URL. Counter calls are opt-in definition data validated like every other operation surface; request-boundary threshold measurement uses them when configured and falls back to the text-only estimation below (§6.8).

Per-format gating is write-time enforced: the three `responses_*` declarations are accepted only on an `openai_response` definition, and the two `messages_*` declarations plus `count_tokens` only on an `anthropic_messages` one — a declaration on the wrong format is an operation the definition could never render, and names the format in its 400. The operation data is validated whenever present, regardless of the declared default, because an administrator model override can select a mechanism whose definition default is unknown. Every compaction expression stages against the same value vocabulary as inference (§5.1) — the compaction-operation and compaction-count stages admit exactly the inference stage's value kinds — and the write-time validation walks every compaction expression in the base-URL requirement predicate (§3).

**Unsupported classifier**: every declaration and operation may carry a typed positive unsupported-response classifier — `statuses` (upstream HTTP status values), `codes` (upstream error `code` members), `parameters` (upstream error `param` members). A dispatched native call whose response matches any listed criterion is a positive mechanism-or-model boundary, the one runtime evidence that permits the single summary fallback (§6.8). An empty classifier never positively classifies; free-form error-message substring matching and scripting do not exist.

### 5.10 Upstream Account Quota

Inference may declare an optional `quota_exhaustion` policy containing an ordered nonempty list of named rules. Each unique nonempty rule name describes a nonempty set of non-2xx statuses, a nonempty object-member path `code.at` and exact string `code.value`, a nonempty ordered `restriction_key` recipe of literal or `requested_model` segments, and applicability `all_models` or `requested_model`. The first matching rule wins; matching is case-sensitive and missing, null, numeric, or non-string codes do not match. Rule names never become restriction identities. Readable quota and rejection recipes must resolve the same ordered key and applicability if a positive quota reading should clear that rejection.

Rejection evidence requires the original body to finish successfully within 4096 bytes and parse as complete valid JSON before outward excerpt truncation. An overflow, interrupted stream, malformed JSON, or invalid UTF-8 cannot establish exhaustion. A status alone, body prose, timeout, or ordinary rate-limit header supplies no quota evidence. Classification applies only to rejected generation and native-compaction dispatches; positive quota classification precedes native-unsupported fallback. Control-plane requests and token counters never use these rules. A rejected OAuth renewal therefore stops before inference dispatch even when its error body matches a generation quota rule; it creates no inference accounting row or routing restriction.

A definition may carry `quota: QuotaDescriptor`: one read-only `ControlRequest` returning JSON, plus ordered object, array, or map extraction sources. Product URLs, credentials, headers, paths, and labels belong exclusively in definition data. The query uses the exact bound version and current provider credentials after normal OAuth renewal, including durable OAuth slots when the descriptor selects them. Quota requests allow only literal, secret, slot, base, and flat coalesce expressions; all request leaves participate in validation and the base-URL requirement. Quota is independent of discovery, inference, serving switches, and gateway accounting. Descriptors and current exhausted routing restrictions persist; observations, upstream bodies, and history do not.

Extraction is atomic and strict: absent/null optional sources and entries are omitted, missing optional facts become explicit unknown variants, and malformed present values fail the complete reading. Paths are object-member chains with explicit root/item/entry contexts. Arrays use required item-field identities, maps visit keys lexicographically, and identity tuples are never delimiter-joined. Source and entry order otherwise remain declared/upstream order. Duplicate result tuples fail. An explicit true unlimited boolean bypasses numeric measurement fields while preserving period/reset extraction.

Results carry observation time in UTC microseconds and independent entries with key tuple, label, scope, period, measurement, and reset. Measurements are unknown, used ratio, used/limit counter, remaining-only amount, or unlimited. Used values may exceed limits; remaining ratios must lie within their scale and remaining counters cannot exceed their positive limit. Numeric encodings explicitly distinguish JSON numbers, strict JSON numeric strings, and their union. Integer magnitudes, durations, and timestamps must fit JavaScript's safe integer domain; decimals remain finite and nonnegative, and negative zero normalizes to zero. Fixed periods are positive whole seconds; calendar month has no guessed alignment. RFC 3339 resets preserve their instant and reject any nonzero fractional digit beyond microseconds, including digits beyond the date parser nanosecond precision; integer Unix values use declared units, and date-only resets retain a validated calendar date without an invented timezone. Past resets are valid observed data. A future date-only reset, a calendar month, or a fixed allowance duration cannot supply an absolute availability recheck time; exhausted observations with only these facts retain an unknown-reset restriction.

`providers:quota` rejects unknown or unsupported providers before renewal/I/O, then uses the provider state returned by renewal as authoritative and rechecks capability. A disabled provider remains queryable. Exactly one quota request uses the control-plane timeout, with no retry or fallback. Success stamps observation time after JSON decoding and before extraction. No transaction spans network I/O. Quota upstream failures are 502s with safe cause/context and foreign status, never raw response bodies; normal renewal keeps its existing classification. Only normal renewal may write credentials. Quota queries never write models, serving state, or API logs. Listing, overview, discovery, and availability administration never poll upstream; pool selection checks candidates in priority order using the shared refresh cadence.

`providers:quota` forces a current-generation read and joins an existing current-generation flight. Each account has one exclusive read slot, including old-generation work that is still completing. A forced caller waits for an old-generation read to release that slot, then starts or joins a current-generation read; automatic selection may use an explicit reset's unexpired grace immediately. Caller cancellation does not cancel that read. Automatic checks throttle success, failure, and unsupported capability from monotonic completion time using the live refresh interval, shortened by a known future applicable reset; a reset becoming due means recheck rather than automatic replenishment. Revision-only evidence changes retain cadence. Failed, unknown, omitted, and monitoring-only evidence never clear a block; only positively available or unlimited evidence clears its exact key. Full reconciliation compares both the generation and revision captured immediately before I/O after credential renewal. A classified dispatch rejection compares generation only and advances revision, so it defeats an earlier quota read. Deleted accounts are never recreated.

Explicit credential replacement, reauthorization, definition rebind, and base-URL change advance generation/revision and clear obsolete restrictions transactionally. Rename, serving switches, and routine OAuth renewal retain them. Explicit availability Reset clears restrictions and installs an unknown/unblocked grace period of one live refresh interval; forced Refresh overrides it. Memory metadata is generation-scoped, so an old read cannot replace this grace. Reset publication carries the exact generation committed by its transaction and cannot grant grace to a later account mutation or replace a forced current-generation read that already completed. The control-plane timeout covers response-body reading as well as dispatch; a stalled body remains a timeout rather than malformed-observation evidence. Unknown-reset restrictions remain until exact positive evidence or explicit reset/account mutation, even if no readable entry exists for that restriction.

The authored vocabulary is concrete serde data in `src/provider/definition/quota.rs`, exported into the generated management bindings. Every source declares `type`, stable `key`, root-relative object-member path `at`, `is_required`, `scope`, and a nonempty ordered `entries` list. An `array` source additionally declares nonempty `identity` text sources, including at least one required `item` field; a `map` source derives identity from its member key. Each entry declares `key`, `label`, item-relative `at`, `is_required`, `window`, `measurement`, and `reset`, a `routing` member defaulting to `monitoring_only` — `all_models` affects every physical model on the account, and `models` carries a nonempty ordered list of required text sources resolving exact upstream IDs (literals must be routing-safe, field sources must be required, and `map_key` requires a map context) — with an optional boolean `is_unlimited` field. Keys must be unique among their configured siblings. Text, units, and path members are nonempty. `QuotaField` is `{base: root|item|entry, path: string[], is_required: boolean}`; `entry` is unavailable while evaluating source scope or array identity. Text sources are literal text, a string/integer field, or `map_key` in a map context. Integer identity fields use exact JSON integer spelling without floating-point conversion. Optional absent scope becomes unknown.

`{"type":"all_models"}` affects every physical model on the account; `{"type":"models","upstream_ids":[<QuotaTextSource>, ...]}` resolves a nonempty set of exact upstream IDs in root/item/entry/map contexts. Model field sources must be required and map-key sources require a map source. Unresolved, malformed, or unroutable model IDs fail the complete observation. Results publish the same tagged routing union with plain sorted, deduplicated strings. Presentation labels and `scope.name` never select models or imply account-wide applicability.

| Authored mapping | Declared alternatives |
| :--- | :--- |
| Window | `unknown`; `duration {seconds}`; `duration_field {value, unit: seconds|minutes|hours|days|weeks}`; `calendar {unit: month}` |
| Measurement | `unknown`; `ratio {value, scale: fraction|percent, direction: used|remaining}`; `counter {value, limit, direction: used|remaining, unit}`; `remaining {value, unit}` |
| Reset | `unknown`; `field {field, encoding: unix_seconds|unix_milliseconds|rfc3339|date}` |

Each numeric `value` or `limit` is `{field: QuotaField, encoding: number|numeric_string|number_or_numeric_string}`. Numeric strings use the JSON number grammar without whitespace, signs other than a leading minus, or nonfinite spellings. Validate every present active field even when a different optional field is missing; an optional missing counter value or limit produces an unknown measurement only after the other field validates. Only a present true `is_unlimited` bypasses numeric measurement fields, including missing required values or a zero limit; it does not bypass scope, window, or reset validation. A missing required boolean fails, and a present nonboolean always fails. Empty collections succeed with no observations; a present malformed source, item, entry, or field fails the whole reading.

Frontend presets carry researched quota recipes for Codex, Claude Code, Kimi Code, GitHub Copilot, and Antigravity. Their pinned evidence, request requirements, redacted response shapes, and individual limitations live in [the fixture provenance](fixtures/quota/README.md); all five quota capabilities remain unverified by a live upstream query. Claude's existing authorization includes `user:profile`; Copilot quota uses the durable `github_token` slot rather than the short-lived inference token; Antigravity uses the provisioned `project` slot. Devin remains without a quota recipe because the evidenced billing allowance read requires browser-session authentication and an internal organization ID, neither supplied by its current inference-key exchange. Generic static-key and OpenCode Zen definitions have no speculative quota read. Updating a preset creates a normal immutable definition version; an existing provider acquires the capability only through an explicit normal rebind/reauthorization.

## 6. Translation Architecture (IR)

All incoming and outgoing payloads map through an internal Intermediate Representation (IR):

```text
[Client Request] ──> [Parse to IR] ──> [Render Upstream Payload] ──> [Upstream]
                                                                        │
[Client Response] <── [Render Client Format] <── [Parse IR Events] <─────┘
```

### 6.1 IR Request

- `model`: resolved upstream model name (see §6.5); rendered verbatim into upstream payloads.
- `instructions`: concatenated system instructions.
- `messages`: ordered list of messages.
  - `role`: `user`, `assistant`, or `tool`.
  - `parts`: `Text {text}`, `Image {Inline {mime_type, data_base64} | Url (url)}`, `ToolCall {call_id, name, arguments, thought_signature?}`, `ToolOutput {call_id, content, is_error}` (`is_error` read and rendered by the Anthropic pair only; other surfaces drop it), `Reasoning {text, signature?, opaque}` (assistant reasoning block: text plus the opaque family-bound replay payload — an Anthropic `thinking`/`redacted_thinking` block or an Interactions `thought` step verbatim).
- `tools`: function declarations (`name`, `description?`, `parameters?` JSON Schema).
- `tool_choice`: `Auto | None | Required | Function {name}`.
- Sampling: `temperature`, `top_p`, `max_output_tokens` (all optional).
- `response_format`: `Text | Json | JsonSchema {name, schema}`.
- `reasoning_effort`: the client's reasoning level in the closed shared vocabulary (§6.4), or absent.
- `state_items`: opaque compaction state riding the history at its message positions — a Responses `compaction` item, a replayed reasoning item carrying `encrypted_content`, or an Anthropic `compaction` content block, each preserved verbatim as the producer emitted it (§6.8). A state item is protocol state, never conversation content: it renders only to a producer of its own family — the Responses upstream splices each item into its input at its position — and never crosses protocols or enters a summary. Gateway-flagged carriers (§6.8) ride the same channel only until compaction preparation decodes and removes them; a carrier reaching an upstream render is a fatal invariant violation, never forwarded.

### 6.2 IR Events

- `MessageStart {id, model}` — identifies the completion; emitted exactly once, first.
- `TextDelta (delta)` — incremental assistant text.
- `ReasoningDelta (delta)` — incremental reasoning/summary text.
- `ReasoningDone {text, signature?, opaque}` — a complete reasoning block terminating the streamed text with its signature, so streaming and aggregated renderings agree: parsers emit either deltas plus an empty-text done, or a done carrying the full text with no prior deltas — never both with overlapping text. OpenAI surfaces render the block's text through the existing reasoning channels and drop the opaque payload; same-family round-trip replays the opaque payload verbatim; cross-family it is dropped.
- `ToolCallDelta {index, id?, name?, arguments_delta}` — incremental tool call assembly; `index` is stable per call within the response.
- `ToolCallDone {index, call_id, name, arguments, thought_signature?}` — complete tool call.
- `Finish {reason, prompt_block_reason?}` — `reason`: `Stop | Length | ToolCall | ContentFilter`. `prompt_block_reason` is family-bound round-trip detail in the `thought_signature` mold: the verbatim upstream prompt-block reason, present exactly when the finish is a prompt-level block the upstream reported through its prompt-feedback channel (the only such reporter today is the Gemini GenerateContent parser, README §6.3); it rides the IR to the native render surface, and every other surface ignores it.
- `Usage {input_tokens, output_tokens, cached_tokens?, cache_write_tokens?, reasoning_tokens?}` — token accounting. The three breakdown values are `None` when the upstream reports no token-detail objects: a Chat Completions upstream that omits `prompt_tokens_details`/`completion_tokens_details`, or a Responses upstream that reports totals only. Chat Completions upstreams report the breakdowns through the official usage-object members `prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens`, plus `prompt_tokens_details.cache_write_tokens` — an official member some upstreams omit — and the gateway parses each member the upstream carries. An upstream that reports input usage at its stream head — the Anthropic `message_start` event — publishes a partial report with a zero output observation immediately after `MessageStart`; the terminal report overwrites it, and every rendering and the accounting take the last observation.
- `CompactionState {payload}` — a native compaction artifact observed in an upstream response: a Responses `compaction` output item or an Anthropic `compaction` content block, carried verbatim in arrival order (§6.8). No IR part absorbs it and no text channel carries it; the compaction outward renders own its lifecycle — the Responses renderer emits each item's `output_item.added`/`output_item.done` pair at its output position and splices it into the aggregated output array, the Messages renderer opens the block, adds one full-content `compaction_delta` when the block carries string content, and closes it at the next stream content index, and the aggregated body splices the block into the content at its position. Every distinct native compaction is preserved: streamed and terminal copies of one item deduplicate by identity (the item's `id`, or its serialized bytes when the producer minted none), never by text similarity.
- `CompactionMetadata {is_paused, iterations}` — native compaction lifecycle metadata, independent of ordinary generation usage (§6.8): whether the upstream paused after compaction, beside the iteration reports — one entry per billed sampling iteration — that the accounting's iteration totals and the Messages `usage.iterations` render consume. The Messages upstream parser emits it when its response carried the `compaction` stop reason or native iteration reports, the entries verbatim; the gateway synthesizes the same event for its emulated compaction lifecycles, its generated entries typing each report `compaction` or `message` and carrying the observed totals with no invented breakdowns.
- `Done` — terminal event; always the last event of every event stream, regardless of upstream shape. Parsers never emit it; the gateway appends it when the upstream response is fully consumed.

Every upstream response — SSE stream or JSON document — is parsed into a lazy IR event stream owned and polled by the response task, with no separate parser task or IR-event channel. SSE parsing drains the pending events and frames before reading another body chunk; a clean EOF flushes trailing frames and codec state, while a transport, framing, or payload failure emits only the terminal error and `Done` after any already-yielded events. Dropping the event stream releases its upstream body immediately; non-streaming aggregation remains detached and continues reading after handler departure to preserve final usage accounting. Every client response — streamed or aggregated — is rendered from IR events. Upstream payloads are third-party data modelled member by member: members the gateway does not read are ignored, while a member it reads whose JSON kind contradicts the protocol — a non-string text or a non-object tool-call arguments — makes the payload malformed and fails the request per §6.7 rather than being silently skipped. The parser is chosen by the upstream streaming mode the definition requested (§5.2) — never by response headers: the Codex upstream serves its 200 SSE streams without a `Content-Type` header. Non-streaming client responses are aggregated in memory from the same event stream (Text/Reasoning/ToolCall deltas → accumulated content, ToolCallDone → final calls, Finish, Usage; `MessageStart` contributes nothing — outward responses carry renderer-minted identifiers). When a tool-call done event carries no assembled arguments, the accumulated streamed deltas are used; the upstream parsers never emit a repeated ToolCallDone for an already-completed call index — each parser tracks the calls it has completed — and the aggregation path's repeated-done dedup guards that contract on the consumer side. For streamed Chat Completions, a tool-call done for a delta-opened call renders to the client exactly the argument bytes its live deltas did not already deliver — none when they already delivered all of them — a done for a never-opened index renders the complete call as one `tool_calls` delta chunk, and a divergent done whose arguments are not a superstring of the streamed bytes — or whose streamed byte count falls mid-character in the done's arguments — silently skips its residual argument frame. Outward Chat Completions tool-call indexes are renumbered dense: outward `tool_calls[].index` is dense from zero per choice in first-appearance order regardless of the upstream's IR indexes — a Responses upstream reports an item's `output_index`, its position among all output items, so a reasoning-plus-tool turn can open its first call at a nonzero IR index — while the IR index remains the stable internal identity the streamed-argument bookkeeping keys off.

Upstream refusal text is delivered as assistant message text (`TextDelta`), so it reaches clients through the ordinary text channel: Chat Completions upstreams map `delta.refusal` and `message.refusal` (content text before refusal text when one delta carries both), and Responses upstreams map `response.refusal.delta` events and `refusal` message content parts exactly like `output_text` parts.

Legacy Chat Completions upstreams still speaking the deprecated `function_call` protocol — `delta.function_call` fragments in a stream and a complete `message.function_call` in a body — parse into the ordinary tool-call assembly as the single call the legacy protocol permits, occupying the assembly's default index under a synthesized stable call id, with the modern `tool_calls` member taking precedence when one payload carries both.

Every provider definition names its upstream format outright, and its `upstream_streaming` mode decides the upstream's framing: `always` streams upstream on every dispatch (a non-streaming client receives an aggregated response — the Codex preset's mode), `match_client` follows the client's requested mode. The outward format matrix is unchanged — every outward endpoint routes every definition, because the gateway never judges whether a model supports the definition's format; the upstream is the sole authority, and an unsupported combination mirrors the upstream error (§6.7).

- Streaming clients receive live translated SSE chunks (`data: {json}\n\n`). Chat Completions streams end with a `data: [DONE]` sentinel; Responses streams end after the terminal `response.completed` or `response.incomplete` event. Every Responses SSE payload embeds its event name as a `"type"` field and a monotonically increasing `sequence_number`, so strict clients that discriminate on the JSON payload work without reading the `event:` line.
- Streaming Chat Completions deliver usage in a single terminal usage chunk immediately before `data: [DONE]`; when an upstream reports usage repeatedly, the last observation wins and renders once. Delta chunks carry no `usage` field at all — usage appears only in the final chunk.
- Responses `response.output_text.delta` and `response.output_text.done` events and `output_text` content parts always carry `logprobs: []` — empty when no logprobs are produced — because the official openai-python client requires the field.
- Every Responses usage object the gateway emits — in the `response.completed`/`response.incomplete` terminal events and in the aggregated non-streaming body — carries exactly `{input_tokens, input_tokens_details: {cached_tokens, cache_write_tokens}, output_tokens, output_tokens_details: {reasoning_tokens}, total_tokens}`: openai-python's `ResponseUsage` types all five fields, and every detail-object integer, as required without defaults, so a breakdown the upstream did not report renders zero-filled (`0`) while upstream-reported values ride through; `total_tokens` is the sum of `input_tokens` and `output_tokens`. The outward Chat Completions usage shape is unchanged (`prompt_tokens`/`completion_tokens`/`total_tokens`).
- Every Gemini usage object the gateway emits — the GenerateContent `usageMetadata` (the aggregated body and the terminal streaming usage chunk alike) and the Interactions `usage` object (the aggregated resource and the terminal `interaction.completed` frame alike) — carries the official total member always: the GenerateContent shape renders `totalTokenCount`, the sum of `promptTokenCount`, `candidatesTokenCount`, and `thoughtsTokenCount` (`ai.google.dev/api/generate-content`), and the Interactions shape renders `total_tokens`, the sum of `total_input_tokens`, `total_output_tokens`, and `total_thought_tokens` (`ai.google.dev/api/interactions-api`). Each total is present whenever its usage object is, because it is a deterministic sum of members the gateway renders unconditionally — the exact inverse of the upstream parses that fold the thought tokens back into the IR output total, and the same sum-of-rendered-members rule the Responses surface applies to its `total_tokens`.
- Every Responses response object the gateway emits — the `response` field embedded in streaming events, the terminal `response.failed` frame, and the aggregated non-streaming body — carries `parallel_tool_calls: false`, `tool_choice: "auto"`, and `tools: []`: the official Response shape types these fields without defaults, and the statics truthfully describe the gateway (no parallel tool-call control, the model decides when to call tools, no tool definitions are echoed back).
- The aggregated Chat Completions body always carries the official required-nullable choice and message members empty — the choice renders `logprobs: null` and the assistant message renders `refusal: null` — because the official chat completion object requires `logprobs` (anyOf object or null) and its response message requires `refusal` (anyOf string or null; openai-node types both required-nullable, `logprobs: Choice.Logprobs | null` and `refusal: string | null`) while the gateway produces neither, and the streaming chunk choice stays unchanged, its official required list (`delta`, `finish_reason`, `index`) carrying neither member.
- `Finish(Length)` and `Finish(ContentFilter)` render as `response.incomplete` carrying `incomplete_details.reason` (`max_output_tokens` / `content_filter`), both in the streaming terminal event and in the aggregated non-streaming response's `status`/`incomplete_details`; all other finishes render `response.completed` / `status: "completed"`.
- A turn whose upstream delivered function calls finishes with the canonical reason `ToolCall` — mixed text+tool-call turns included, matching official Chat Completions semantics: the Chat Completions upstream maps its native `finish_reason` (`tool_calls`, `function_call`); the Responses upstream reports `ToolCall` for a turn that delivered function calls under any status other than `incomplete` (the Responses status vocabulary has no tool-call value), including calls recovered from a terminal output array; the Gemini upstream reports `ToolCall` when the turn delivered `functionCall` parts under any finish reason other than `MAX_TOKENS` or a filter reason; a `finishReason` of `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL` (the model generated a tool call although the request enabled none), or `TOO_MANY_TOOL_CALLS` (the model called too many tools consecutively, so the system exited execution), however, is a failed generation — the turn aborts as an upstream failure under §6.7 instead of rendering a clean finish. Truncation maps `MAX_TOKENS` to the length finish, and the flagged-content finishes — `LANGUAGE` (unsupported language), `SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `IMAGE_SAFETY`, `IMAGE_PROHIBITED_CONTENT`, and `IMAGE_RECITATION` — map to the canonical content-filter finish; unknown finish reasons degrade to a clean `Stop` finish.
- A Gemini prompt-level block — `promptFeedback.blockReason` present with no finishing candidate; Gemini sends `promptFeedback` only when no candidate was generated — yields the canonical content-filter finish (`finish_reason: "content_filter"` / `response.incomplete` with `incomplete_details.reason: "content_filter"`), and a candidate `finishReason` wins when both are present, so a finishing candidate is never overridden by the feedback. The verbatim block reason rides the IR Finish event's `prompt_block_reason` to the outward render: the GenerateContent surface renders the official blocked shape — `promptFeedback: {blockReason}` with the upstream spelling unmapped, and no candidates — in the aggregated body, and mirrors `promptFeedback` on the terminal streaming usage chunk (which carries the feedback alone when the upstream reported no usage); a candidate-level content filter keeps the empty-candidate `finishReason: "SAFETY"` render, and every other surface ignores the detail.
- Malformed upstream SSE/JSON payloads abort the stream; clients that are already streaming receive a terminal `data: {"error": {...}}` frame (Chat Completions) or a `response.failed` event (Responses) with the translated error. This applies to malformed trailing frames flushed at end-of-stream as well: they abort the stream with an error frame instead of terminating cleanly. Upstream failures delivered inside a success transport abort the same way: an OpenAI-family stream frame or a 2xx JSON body carrying a non-null `error` value aborts with a terminal error frame / 502 instead of parsing as an empty success; a top-level `"error": null` is the normal success shape of the non-streaming Response object and parses normally — only a non-null `error` value aborts.
- The Responses upstream parser recovers message text, reasoning text, and function calls exactly once. Message and reasoning text recovery treats streamed and terminal items as fallback sources consulted only when no live event delivered the kind — live deltas exhaust every fallback source for that kind. A streamed `output_item.done` function_call item always completes its call, and only the terminal array's call copies are gated on live delivery — a gate only content-bearing call events satisfy: the argument bytes streamed for the call's output index, or the streamed done item itself. A bare `response.output_item.added` opening carries the item skeleton without argument bytes, delivers no call content, and never counts as live delivery, so a stream that opens a call but streams no arguments for it still recovers the call from the terminal output array. A static-key upstream that streams complete `output_item.done` items or only a terminal `response.completed`/`response.incomplete` event without live events therefore still delivers its `output`-array text and function calls to the client exactly once. Message and reasoning fallback recovery is keyed by the item's output index: a streamed `output_item.done` item and the terminal array's same-index copy are delivered exactly once together, and distinct indices each deliver exactly once — the dedup rests on the conformant identity between a streamed item's `output_index` and its terminal-array position.
- On a clean upstream end-of-stream the gateway flushes buffered parser state (e.g. pending Chat Completions tool calls) into the event stream before the terminal `Done` event; an aborted stream skips the flush. A clean end-of-stream that carried no finish reason (Chat Completions) or no terminal event (Responses/Gemini) degrades to a `Stop` finish, so streamed and aggregated renderings of the same stream agree.
- Upstream deadlines: two upstream HTTP clients share a 10-second connect timeout. The data-plane client enforces a 300-second read timeout that resets after every successful read of the upstream body and sets no total request timeout: a stalled upstream therefore aborts the request (mapped to 502 per §6.7) instead of hanging it indefinitely, while a slow-but-flowing response is never truncated. The control-plane client (token exchange and refresh, model discovery, project onboarding) bounds each request at 30 seconds total, so a stalled control-plane request fails below the 90-second refresh-lease staleness window and below the 60-second device-flow claim-staleness window (§3).

### 6.4 Reasoning Levels

> **One reasoning vocabulary, forever.** The whole gateway shares the closed enum `none | minimal | low | medium | high | xhigh | max` — one standalone shared vocabulary every layer names (the format codecs parse and render it, the capability declarations (§3) and their management overrides store it, the IR request carries it), never the property of the IR or of any one format. Inbound surfaces parse their own parameter into this enum; unknown strings are a 400 at the gateway (a deliberate reversal of the old opaque-passthrough contract). Upstream renderers write the enum verbatim into the target's own level parameter. **There is no cross-vocabulary mapping, and there never will be** — not deferred, out of scope permanently. A value the target does not support is rejected by the upstream and mirrored to the client per the existing error policy; that is the caller's configuration responsibility.
>
> - `none` renders as: OpenAI `reasoning.effort` / `reasoning_effort` `"none"`; Gemini `thinkingLevel` / `thinking_level` `"none"` verbatim; Anthropic `thinking: {"type": "disabled"}` (the native off spelling).
> - **Gemini has no off**: it rejects `"none"` with a 400 that mirrors to the client per §6.7. Sending `none` to a Gemini target is therefore a caller error surfaced upstream, not a gateway default.
> - Anthropic inbound: `output_config.effort` (optional — the container may carry a `format` alone, §6.6) parses into the enum; `thinking: {"type": "disabled"}` parses into `none`; `thinking` `adaptive`/`enabled` is accepted-and-ignored; `budget_tokens` is a 400 naming the field where its official member exists (`enabled`; legacy numeric mechanism, same stance as Gemini `thinkingBudget`); `display` accepted-and-ignored on its only official home, the `enabled`/`adaptive` variants — the official `ThinkingConfigDisabled` and `OutputConfig` carry no such member, so a stray `display` rejects as an unknown field.
> - Summary/display controls (`reasoning.summary`, `thinking_summaries`, `thinking.display`) never enter the IR. Existing Responses behavior is unchanged (`summary` accepts `auto` only); the two new surfaces' equivalents are accepted-and-ignored.
>
> When the client omits the field, no upstream parameter is rendered and the upstream's own default applies — that is not "no thinking". Token budgets are never rendered (the Gemini 2.5-era `thinkingConfig.thinkingBudget` and its kind are never sent): the gateway renders only `thinkingLevel`, so reasoning control is supported only on Gemini 3 generation and later models.
>
> The vocabulary is also the value domain of the per-model capability declarations (§3): discovery extracts a model's supported levels where the upstream reports them, the administrator overrides per field, and the effective set (`override ?? base`) is rendered on the outward model listings (§6.5) — a declaration, never an enforcement. The gateway never validates a request's level against the declared set: the upstream stays the sole authority, an unsupported value keeps mirroring the upstream error (§6.3), and a stale or missing declaration can therefore never reject a request the upstream would serve. One under-declaration edge is documented rather than patched: the Anthropic listing's effort capability carries no `none` member, so an Anthropic-discovered set never declares `none` even though `thinking: {"type": "disabled"}` is sendable — an override corrects it. Levels outside the vocabulary never reach a declaration (§5.5), and logs record no requested effort.
>
> Reasoning content is a separate concern (§6.2): same-family round-trip replays reasoning blocks byte-exact (both upstreams hard-require it — dropping or rebuilding them is a 400); the two Gemini protocols additionally bridge each other's replayable signature state, because the thinking docs require clients to resend thought blocks exactly as received: a GenerateContent upstream's thinking-part `thoughtSignature` survives the parse into the IR block's signature, an Interactions `thought` step renders toward a GenerateContent upstream as that protocol's thinking part (`thought: true` text, the signature riding the part's `thoughtSignature`, family membership decided by the block's thought-step opaque so a foreign family can never leak onto the wire), and a GenerateContent `functionCall.thoughtSignature` renders to the Interactions surface as the signature-bearing `thought` step beside its call — the official home of a replayable Gemini signature on the Interactions protocol (README §5.7). OpenAI surfaces render a block's text through `ReasoningDelta`/`reasoning_content` and drop the opaque payload; cross-family otherwise the opaque payload is dropped — the Anthropic Messages upstream renders no thinking block at all for a foreign-family reasoning part, since its API verifies the block signature and would reject any synthesized block, and the GenerateContent upstream likewise renders nothing for an Anthropic-family reasoning block.

### 6.5 Model Routing

- Client-visible model IDs resolve exclusively against enabled `model_routes.public_id`. A direct route requires an enabled account and an enabled, non-vanished physical target. A pool route additionally requires an enabled pool and selects structurally eligible accounts in ascending member priority for the exact authored upstream ID. Route, member, provider, and model rows are read from one coherent snapshot, released before upstream I/O. Committed member priority changes reorder new unbound selection without moving a live history binding. Alternative next user turns reuse the same completed historical prefix; changing sampling, instructions, stream mode, or a public alias in the same pool does not change that prefix's account. A bound history that switches to another public route/model within the same pool still requires its account; missing that model returns bound-account-unavailable even when another member can serve it. Execution carries the stable route ID, requested public ID, optional pool ID, and the real provider/model separately. Upstream bodies use the physical upstream ID; outward model fields keep the requested public ID. Discovery automatically exposes standalone provider models through their prefix and pooled provider models through each owning pool prefix. A vanished direct target suspends its stored route; rediscovery restores availability with the same physical identity, route ID, and public name. Unknown or disabled routes, disabled pools, and disabled direct targets return model-not-found (404). Enabled pool routes without a structural candidate return `PoolUnavailable` (503): OpenAI code `pool_unavailable` and type `api_error`, Gemini `UNAVAILABLE`, and Anthropic `api_error`. This is an upstream availability failure for accounting and produces no log row before dispatch.
- Ordinary pooled generation scans the same structural snapshot in priority order, checking each candidate's shared account quota through the optional control-plane refresh coordinator before dispatch. Known applicable blocks skip the candidate without an accounting row. Account restrictions apply across every pool containing that account; model-specific restrictions leave other exact upstream models eligible. Unsupported or failed optional reads preserve established blocks and otherwise leave the candidate eligible. Direct routes bypass quota preflight and dispatch once even when their account has recorded restrictions.
- A fresh pooled generation or compaction attempt can advance only after a complete rejected body positively matches the definition's exact quota rule on that account's first unaccepted data-plane dispatch. Every account is tried once. Each abandoned attempt is finalized before the next account is started, with its real provider/model/route IDs, first upstream status, `upstream_error`, NULL outward status, and no fabricated usage. Bare 429s, overload, truncated or malformed rejection bodies, transport errors, renewal failures, and accepted-body parser errors terminate the current attempt. Receiving 2xx headers commits the account before parsing. A later same-account compaction failure retains all already-reported stage usage in that one final attempt row; the first upstream status and final outward status remain independent. An empty compaction ledger leaves token facts unknown (`NULL`); an upstream report of zero remains a known zero. Protocol-required zero-valued response totals do not become accounting measurements. If every structural candidate is blocked or positively rejects quota, selection returns `PoolQuotaExhausted` (429) without another row: OpenAI `pool_quota_exhausted` / `rate_limit_error`, Gemini `RESOURCE_EXHAUSTED`, Anthropic `rate_limit_error`.
- A pool exhaustion response includes `Retry-After` only when at least one candidate has future absolute resets for every applicable restriction. That candidate's latest constituent reset determines its recheck; choose the earliest such candidate and round positive seconds upward. Unknown candidates do not suppress another candidate's complete reset evidence. Reset bounds are evaluated again at response time, so an earlier candidate whose constituent reset became due does not mask another candidate that still has complete future information. Quota timestamps and switches remain unchanged by this header.
- The shared in-process affinity cache accepts opaque history, complete-request, and artifact fingerprints in the `(api_key_id, pool_id)` namespace. It stores only fingerprints, account identities, and lifetime/ownership metadata; it has no database tables, prompts, outputs, or client session identifiers. Historical evidence prefers the longest completed prefix, then exact identity over relational identity at equal length. Conflicting registrations make that winning anchor ambiguous until expiry or eviction, without reviving weaker history or an older committed retry hint. Active verified producers and single-account artifact hints must agree with single-account historical/retry evidence. All five client parsers retain tool identity provenance and foreign result source types outside inference IR. The ordinary-history adapter projects accepted typed parts and preserves GenerateContent wire order through position references when inference parsing regroups text and tool results. Its window-projection entry point accepts original message offsets and active state items, consumes covered tool-source records without hashing covered content, and preserves uncovered native state positions without expanding hidden summaries. Authenticated boundary preparation now produces a content-free client-visible projection and latest-artifact digest, excluding superseded state even at a shared message offset. Gateway history hashes only the sealed token, while its artifact hint hashes the authenticated envelope ID; raw artifacts hash their canonical accepted payload. Missing inbound Responses compaction IDs remain absent instead of receiving random synthetic IDs; explicitly null IDs and authoring attribution remain null, preserving the canonical raw artifact identity. Ordinary and compaction routing share one Selection-owned affinity acquisition coordinator before quota selection, including authenticated-producer/cache conflicts, established artifact bindings, and reservation followers. A released reservation reloads the admitted route snapshot, adopts any new namespace or direct target, and revalidates native requirements against the refreshed pool. Native provenance is checked against authored membership, upstream model, and protocol before affinity acquisition; structural eligibility is checked afterward. A disabled native producer therefore cannot hide a conflict with contrary live cached evidence: conflicting requirements return 400 before the required account’s availability or quota checks. Replay-only ordinary generation commits successful headers through the retained selection handle and transfers its visible continuation to actual JSON/SSE rendering. Every internal native compaction, summary inference, and token-counter dispatch now commits successful headers through that same selection handle before body parsing; rejected headers do not commit it. A later parse failure or a counter-to-estimator fallback preserves that account for retries. Standalone compact responses register their actual latest artifact before delivery: a gateway response reuses its sealer-proven envelope identity, and a native response hashes the complete returned replayable artifact payload. No retained text is copied or our own carrier unsealed solely to derive this hint. Standalone responses also register their complete canonical returned-window history and the latest active-window history used by routing preparation. Typed views borrow existing response text and foreign reasoning strings, preserve image references and native state positions, normalize accepted empty invocation arguments to an empty object, and hash tool-result text parts with the ordinary codec’s exact leading-empty and blank-line separator rules. A window with an unreplayable item registers no historical prefix; its independently valid complete artifact can still establish its artifact hint. Synthesized compact-only Responses triggers now carry their sealer-proven identity through execution and register their artifact and returned-window history after the complete JSON or pre-rendered SSE response has been built, before handoff. This covers gateway summaries and wrapped native adapters without re-unsealing the carrier. Validated native Responses trigger lifecycles also transfer their accepted account and a new returned-window projection to actual JSON/SSE rendering. Native state is normalized through borrowed replay fields and positioned with digest-only output slots; the JSON path retains its concrete response type instead of assembling a second dynamic response value. Artifact digests publish before the completed native item’s final SSE frame, after its earlier frames passed the client channel; a later stream failure preserves that completed artifact hint while withholding whole-window history. Known departure before the artifact boundary and namespace deletion suppress registration. Other compaction output paths remain unfinished. Ordinary pooled generation acquires this evidence before quota selection. Released followers reload route gates and reacquire the current pool namespace, or resume direct routing if the target changed. Matching retries and concurrent followers execute independently on the established account; the leader commits successful data-plane headers before body parsing, so a later parser or transport failure cannot release that account. A bound account missing from the authored pool or without an eligible physical model returns `bound_account_unavailable` (503); its own quota restrictions or classified rejection return `bound_account_quota_exhausted` (429), with Retry-After derived only from that account. Conflicting active routing requirements return `routing_state_conflict` (400). Direct routes bypass affinity. Namespace acquisition checks committed key/pool presence after creating its ephemeral generation so deletion cannot recreate writable hints through an older snapshot. The detached non-streaming result task owns the accepted account and projects the actual rendered conversation fields through the client codec before handing off a successful response. All five JSON codecs register completed exact/relational history anchors; reasoning that a codec discards on replay is excluded, while GenerateContent thought text follows its accepted plain-text replay. A known handler departure, upstream failure, unreplayable foreign output, or invalidated namespace creates no completed output hint. The streaming result task enables codec-owned projection and registers a replayable continuation immediately before its last terminal frame, after earlier completion-tail frames have passed the client channel. Chat Completions projects actual emitted text/tool deltas: answer text is hashed incrementally, completed invocations release their content into field digests, and tool ordinals follow dense outward indexes independently of upstream indexes or completion arrival. Divergent upstream done identities and skipped argument residuals never enter the history. GenerateContent hashes actual emitted parts in stream order and follows its parser’s id-less semantics for empty call IDs; normalization of foreign argument objects and ignored thought flags follows the ordinary codec. Responses keeps incremental text field states and finalized call digests at the renderer’s first-seen output positions, so interleaved deltas and reverse call completion preserve the actual terminal output order; its authoritative done fields replace provisional call metadata, and adjacent assistant text extends the accepted input tail. State-bearing Responses items await authenticated state preparation. A clean Done with no additional emitted frame registers immediately before stream closure; upstream errors and a known departure suppress registration, with a known EOF-only departure finalized as client-aborted. Messages projects actual sequential text/tool blocks, including its emitted done identity and buffered-argument fallback. Known Messages thinking and Interactions thought payloads use component fingerprints: exact text and emitted signature are independently domain-hashed, and the canonical payload replaces each known text field with its digest while omitting the separately represented signature. Streamed reasoning retains text digest states and emitted signature metadata only; late signatures require no complete text carrier or generated-text buffer, and upstream-only completion text cannot replace emitted bytes. Thinking with a nonempty emitted signature still requires matching complete text. Opaque redacted reasoning discarded by the streaming renderer contributes no history part; its JSON representation participates only when actually emitted. Interactions projects actual step starts/deltas/stops in first-seen outward order, hashing text incrementally and releasing completed invocation fields into digests. Its divergent done fields and un-emitted identity changes never enter the history; actual residual arguments do. Signature-only thought steps release their canonical native reasoning digests at step completion and retain their actual outward order alongside invocations. Summary-bearing Interactions thoughts hash actual emitted bytes incrementally and borrow an existing complete event text or native thinking carrier only after its digest matches. Interactions preserves ordered summary block shapes, annotations, media fields, and absent versus emitted-empty summaries; its streamed text deltas coalesce into one summary block. The renderer retains no generated text or summary buffers, and closing a delta-only thought never repeats already emitted summary bytes. Unknown reasoning fragments, redacted payloads, annotations, and other foreign fields retain recursive canonical JSON hashing without component rewriting. Signed summaries still require matching existing complete text because their canonical signature precedes the summary. All five ordinary streaming codecs project their text/tool output; Signed Messages and Interactions reasoning without a matching complete text carrier still withhold their completed output anchor. Target-independent carrier authentication is connected before route selection, and active authenticated native windows constrain pooled selection to their compatible producer even after cache loss. Active-window fingerprints and cached-affinity conflict checks are connected to compaction selection. Internal compaction stages now commit first successful headers before parsing. Standalone and Responses trigger artifact registration are connected. Messages compact-only JSON and SSE register the actual normalized block artifact and its single-state returned window; gateway identities come directly from sealing. The Messages renderer exposes the actual completed prefix frame after its buffered head resolves, so registration precedes that block’s stop frame, survives a later failure, and is suppressed after a known departure or namespace deletion. Responses and Messages checkpoint continuations carry the sealer-authenticated identity and the accepted account through the answer dispatch and detached output task. Their JSON and SSE projection starts from the actual checkpoint state and extends only with the rendered answer; hidden summary and retained model-visible content are excluded. A completed streamed checkpoint registers at its own final prefix frame and survives a later answer failure; a complete answer establishes the returned active window independently of covered input. Messages native no-summary outcomes retain the original client-visible history, ignore strictly replayable null/no-op state, and establish only their actual answer, including signed reasoning actually emitted in JSON or SSE; no-op blocks never create artifact hints. Messages JSON projection borrows existing typed/opaque output fields, normalizes signed/redacted reasoning through the input codec’s canonical shape, and performs no extra whole-block text serialization or owned replay parse. Native Messages thresholds register complete replayable blocks and their active returned windows in JSON and SSE. A native stream’s canonical state reaches the renderer only after its upstream block stops, and registration precedes the actual outward block stop. An arriving checkpoint closes an earlier outward text/reasoning block, so subsequent answer deltas occupy new positions after the state and replay excludes the covered output; incomplete blocks, known departures, and deleted namespaces publish no checkpoint hints. A later generation failure preserves released checkpoints while withholding the unfinished answer’s full window. Native Responses automatic output uses the same renderer-owned artifact handoff as validated native lifecycles. A streamed checkpoint closes earlier text/reasoning items and resets covered field/relationship metadata, so post-state text and calls occupy new positions and covered calls completing late cannot alter the active window. Completed answer history still waits for terminal delivery. Fresh compaction operations retain their original ordered candidate snapshot and reservation while abandoning first-stage classified quota rejections. Each abandoned account is finalized before the next account is selected, with no outward status or fabricated usage. All target-dependent preparation restarts for the next physical account; authentication and client-visible projection remain request-owned. A counter, unsupported-native attempt, or accepted summary prevents later account switching, and bound quota rejections use only the selected account’s own reset bounds. Exhausting the scan returns pool quota exhaustion without an extra accounting row. Required-account failures remain distinct from pool exhaustion and arbitrary upstream rejection across the outward error envelopes: OpenAI preserves the explicit bound-account code, while Messages preserves its official error type and identifies the required account in the message. Authenticated native incompatibility retains the existing compaction error vocabulary before any dispatch.
- Canonical fingerprinting uses one random 32-byte process key initialized at startup, independent of compaction sealing keys and stable through configuration reload. Variable fields become domain-separated HMAC-SHA-256 digests; fixed-shape typed role/state units extend a length-framed history chain in one pass. Same-role messages merge, adjacent text concatenates byte-exactly, empty text creates no part, and state items break role runs. Foreign JSON sorts object keys recursively, preserves array order, and keeps normal JSON scalar representations. Exact tool identities use actual wire IDs; relational identities use canonical call ordinals and the codec-resolved call/result relationship. Synthetic internal IDs participate only in request-local relationship lookup, never in a projected unit. - Fresh complete-request establishment reserves one pending cache entry. Followers wait for the account decision and execute independent generations after commitment. Cancelling a follower releases only its wait; cancelling the leader before acceptance releases only its own reservation and wakes followers to re-evaluate. - Deleting a provider pool or API key invalidates its current cache entries and outstanding registration handles. - Gemini GenerateContent surfaces route the model from the URL path (`/models/{model}:generateContent`, `/models/{model}:streamGenerateContent`); the body carries no model. Public-route validation excludes `/` and `:` so every authored public ID is addressable through the URL-pathed Gemini surface.
- The IR `model` is always the `upstream_id` of the resolved row; public IDs never reach an upstream.
- Each surface's model listing renders its native shape over effectively enabled automatic and authored public routes: a direct route requires its own switch and an enabled physical target; a pooled route requires its own and its pool's switches plus at least one structural candidate. Discovery automatically exposes models through the standalone provider or each owning pool prefix. Temporary quota blocks do not hide a public route. Direct capability declarations resolve the target's own facts; pooled declarations combine all structural candidates independently of quota, using numerical minima and reasoning-level intersection only when every candidate's corresponding fact is known. A known empty intersection remains an empty array. Compaction support is supported only when every candidate supports it, unsupported when any candidate rejects it, and otherwise unknown. Pool labels provide the public owner label. Each listing ignores pagination parameters, and returns the full list in one page: OpenAI `{"object": "list", "data": [{"id": <public ID>, "object": "model", "created": 0, "owned_by": <provider name>}]}` (`created` fixed `0`); Gemini `{"models": [...]}` with no `nextPageToken`; Anthropic `{"data": [{"type": "model", "id": <public ID>, "display_name": <public ID>, "created_at": "1970-01-01T00:00:00Z"}], "first_id": <first entry's public ID, null when empty>, "has_more": false, "last_id": <last entry's public ID, null when empty>}` (entries ordered by public ID; `display_name` pinned to the public ID; `created_at` rendered as the epoch in the official RFC 3339 date-time string type — the same unknown-release-date convention OpenAI expresses through its integer `created: 0`). Each entry additionally renders its **effective capability declarations** (§3) in the surface's own spelling, every member present only when its effective value is known — an unknown (`NULL`) capability is omitted, never fabricated with a default: the OpenAI surface carries `max_input_tokens`, `max_output_tokens`, and `reasoning_levels` (an array of the vocabulary spellings — a gateway extension, since neither the official Model object nor any aggregator convention declares a level set); the Gemini surface carries the official `inputTokenLimit` and `outputTokenLimit`; the Anthropic surface carries the official `ModelInfo` members `max_input_tokens` and `max_tokens` (the output cap). The management `models:list` instead lists every row, `vanished` included, carrying each row's inputs (`is_enabled`, `discovery_state`); the caller derives the same three-input status from those and the provider's switch (§7.0 rule 7).

Public model listing uses a credential-free bulk projection in `storage/route_listing.rs`, separate from dispatch's credential-bearing `route_snapshot.rs`. Within the enabled-key policy transaction, one ordered `UNION ALL` query reads direct and pooled structural candidates, joining pool inventory on the exact `(provider_id, route.upstream_id)` pair. It selects the physical model codec's columns, typed owner identity and name, and only the definition's compaction defaults. Grouping follows stable route identity and authored member priority, with SQLite ordering public names; policy resolves against the authored provider or pool owner before capability composition. Credentials, OAuth state, unrelated descriptor sections, and quota restrictions are never loaded for listing.

### 6.7 Error Mapping

The `/api` surfaces share one closed, format-neutral error taxonomy — `Error`, the `crate::api` module's own error type, defined once beside the API router and rendered per format. One variant per contract row, each pinning exactly one HTTP status. Domain errors convert in exactly one place (`From<gateway::Error>` with the inner conversions for parse, storage, and provider failures); surfaces stop owning domain-to-contract classification. The request-accounting classification (`outcome` + status) derives from the same variant, collapsing the HTTP response, stream frame, and accounting mappings into one. Mid-stream terminal frames come from the same source: the HTTP error path and the stream-frame path share one classification. Upstream mirroring policy (status mirror + bounded body excerpt) is unchanged.

| Situation | Contract variant | HTTP Status |
| :--- | :--- | :--- |
| Invalid API key | `InvalidApiKey` | 401 |
| Unmapped path (per-surface fallback) | `InvalidUrl {method, path}` | 404 |
| Wrong method on a routed path | `MethodNotAllowed` | 405 |
| Body over the surface limit | `PayloadTooLarge` | 413 |
| Malformed / unsupported request | `MalformedRequest {param, message}` | 400 |
| Unknown or disabled model | `ModelNotFound {model}` | 404 |
| Upstream returned a non-2xx status | `Upstream {status, message}` | mirrored upstream status |
| Upstream transport failure / malformed upstream payload | `UpstreamUnavailable {message}` | 502 |
| Gateway failure | `Internal` | 500 with a fixed message (the internal cause reaches the log only) |

Each format owns one render module beside the shared taxonomy (`src/api/error/{openai,gemini,anthropic}.rs`) with a closed `render(&Error)` match — compiler exhaustiveness forces every format to render a new variant, and a new format is one new render module:

- OpenAI: the existing `type`/`code`/`param` rows verbatim (`invalid_request_error` + `invalid_api_key` for the key, `model_not_found` for the model, `api_error` + `upstream_error` for upstream failures, `api_error` + `internal` for the fixed-message internal).
- Gemini: the official Status shape `{"error": {code, message, status}}` (google.aip.dev/193): `code` is the numeric HTTP status of the failure, and `status` is the canonical google.rpc.Code-style name — `UNAUTHENTICATED` (401), `NOT_FOUND` (404), `INVALID_ARGUMENT` (400/405/413 — the vocabulary has no member closer to a wrong method or oversized body, and the numeric `code` distinguishes them), `INTERNAL` (500), `UNAVAILABLE` (502, the gateway's own upstream-unavailable failure) for the gateway's own failures; a mirrored upstream status renders the canonical HTTP-to-code name where google.rpc/code.proto defines one (400 `INVALID_ARGUMENT`, 401 `UNAUTHENTICATED`, 403 `PERMISSION_DENIED`, 404 `NOT_FOUND`, 409 `ABORTED`, 429 `RESOURCE_EXHAUSTED`, 499 `CANCELLED`, 500 `INTERNAL`, 501 `UNIMPLEMENTED`, 503 `UNAVAILABLE`, 504 `DEADLINE_EXCEEDED`), the closest semantic member as an explicit gateway extension where the canonical mapping has no row (408 `DEADLINE_EXCEEDED`, 416 `OUT_OF_RANGE`, 502 `UNAVAILABLE`), and `UNKNOWN` when no member fits.
- Anthropic: `{"type": "error", "error": {type, message}}`, mapping each rendered HTTP status onto the official table: 400/405 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 504 `timeout_error`, 529 `overloaded_error` (and 503 as the closest-semantic-member gateway extension, where the canonical table has no row), and the 500-class failures `api_error` (the gateway's own 500 and 502 rows; the official table has no 502 row).

### 6.8 Remote Compaction

Remote compaction is the gateway's fulfillment of client-directed context compaction: a client using the Responses or Messages protocol can request compaction even when its selected upstream cannot perform it natively, and the gateway fulfills the request using ordinary inference on the same routed provider/model, returning a replayable artifact in the client's own compaction protocol. The feature is client-directed (§1): an explicit compact operation, trigger, or threshold control in the client's request is the only thing that ever starts compaction work, and recognizing compaction state in a history is a replay, never a new compaction. There is no server-side conversation storage: every artifact lives with the client, sealed against tampering, and the gateway's content-free persistence contract (§1) is untouched. The domain's shared vocabulary — the mechanism and support-fact types, item identities, the envelope, sealing, boundary preparation, and the accounting ledger — lives in the `compaction_model` dependency leaf that storage, provider definitions, the codecs, the configuration loader, the gateway pipeline, and the API surfaces all import, while `src/compaction/` is the executor: the one module that coordinates calls and is alone allowed to depend on the gateway and API layers above it.

The five **mechanisms** — the closed vocabulary every declaration, fact, and carrier names — are `responses_standalone_compact` (the compact endpoint), `responses_explicit_trigger`, `responses_automatic_compaction`, `messages_on_demand_compaction`, and `messages_threshold_compaction`. A mechanism is executable natively only when its effective support is `supported`, its declaration carries the operation data (§5.9), and its replay semantics fit the request. A wire-compatible endpoint, a model name, or a provider brand is never support evidence on its own.

Every native dispatch resolves the exact upstream model and refreshes OAuth credentials before rendering its body. Wrapped native artifacts are bound to their originating provider instance and upstream model; the format alone never establishes compatibility. Required system/tool prefixes compare exact optional values, including removal. Gateway checkpoints preserve retained opaque state and current top-level instructions. Parallel tool calls and all their results form one indivisible retained unit. Native threshold streaming assembles the complete compaction delta before publishing an artifact; native pause and iteration usage survive the ordinary pipeline. Every dispatched outer request finalizes accounting on success, failure, or cancellation, with usage recorded once and duration measured from the first dispatch.

**Support resolution** (§3, §5.9): each mechanism's effective support resolves per selected model from the administrator's `compaction_support_override`, then the discovery-owned `compaction_support` fact, then the definition declaration's `default`; absent facts at every layer resolve to `unknown`. `unknown` selects gateway summarization directly — the gateway never probes an upstream just to discover support — and an explicit `unknown` override suppresses both lower layers, keeping unknown and unsupported distinct end to end.

**Inbound surfaces.** Each surface owns its wire; the shared executor resolves the decision order beneath it.

- **Responses standalone** (`POST /api/openai-v1/responses/compact`, non-streaming always): the strict body of §6.6, its success body the `response.compaction` object `{id, object: "response.compaction", created_at, output, usage}`. The output is the canonical next window — the complete ordered item list, retained messages and reasoning included, never reduced to its compaction item. Native passthrough carries the upstream's own identity, creation time, output, and usage (xAI's optional `dropped_message_count` riding beside the official fields); gateway fallback renders one `compaction` item `{"type": "compaction", "id", "encrypted_content": <sealed carrier>}` with the participating calls' usage, breakdowns zero-filled. The gateway is stateless here as everywhere: a present `previous_response_id` is a 400, and the accepted-and-ignored caching and tiering controls ride along unchanged (§6.6).
- **Responses explicit trigger**: a terminal `compaction_trigger` control item (§6.6) — protocol state, never conversation text. It must be the last input item and the request's one explicit control. The outcome is always compact-only: exactly one completed `compaction` output item and a successful completion, never an assistant summary alone, and extra assistant output never replaces the required item. A native trigger passthrough requires the upstream lifecycle to carry exactly one completed compaction item under a normal finish; adapters seal a whole foreign result — a canonical standalone window or a Claude compaction block — inside one carrier item. The synthesized lifecycle (`response.created`, `response.in_progress`, the item's `output_item.added`/`output_item.done` pair, `response.completed` carrying usage) and the aggregated body represent the same artifact and the same usage; the trigger is compact-only, so the caller's output limit bounds a gateway summary.
- **Responses automatic**: the request envelope's `context_management` array, `compaction` entries with an optional `compact_threshold` (§6.6). With a supported native automatic mechanism the controls pass upstream verbatim, every compaction item keeps its output position (§6.2), and inference continues in the ordinary pipeline — stateless replay with `store: false`, the caller free to prune history before the latest checkpoint. Without one, the request takes the gateway-emulated threshold workflow below; the checkpoint renders before the generated answer in output order, and the pending user turn is never discarded or answered by the summary.
- **Messages on-demand**: the envelope's `compaction: {"type": "summarize", "instructions"?}` control (§6.6). Success is one assistant message whose content is exactly the complete compaction block with `stop_reason: "compaction"` and no answer; streaming sends the complete block in `content_block_start`, then `content_block_stop` — never text deltas — and the message lifecycle completes normally with usage. Native `content`, `signature`, `encrypted_content`, and `tool_changes` ride verbatim. The documented native no-summary outcomes — refusal, truncation, tool use, an exhausted window, a null block — keep their protocol semantics: the original history stands and the consumed response renders with its own stop reason; neither an error nor a fabricated success. A transport-level 200 with no usable block never becomes successful replacement.
- **Messages threshold**: the envelope's `context_management.edits` with `compact_20260112` edits (§6.6) — `trigger` (`input_tokens` only, default 150000, minimum 50000 rejected not clamped), `pause_after_compaction`, and optional `instructions`. A native threshold block sits at its covered historical boundary (unlike on-demand's leading placement); a null block is a no-op that cannot authorize discarding history. Streaming renders block start, one full-content `compaction_delta`, block stop; paused, the outer stop reason is `"compaction"` with no answer, otherwise the answer follows with its own stop reason. A native upstream may compact at several sampling iterations inside one request: every distinct block, its position, and its iteration usage are preserved (§6.2).

**Replay and boundary semantics.** Before every normal inference and every re-compaction, preparation verifies the history's compaction state and reconstructs the active window, applying boundary semantics before role merging. Every gateway carrier is decoded and authenticated — a recognizable but damaged marker is an explicit client-state error, never reclassified as native state and never forwarded upstream — and the latest usable boundary wins: a later authenticated checkpoint supersedes older state, including native blobs it covers — a boundary occupying a message offset also occupies an encounter-order position among the state items sharing that offset, so state it precedes is covered with the prefix and state that follows it is the fresh suffix the restored window renders — while a null/no-op block establishes no boundary at all. A gateway summary restores once at its boundary: the covered conversational prefix is superseded, instruction items are superseded by proven identity overlap — an equal client source identifier, or an equal deterministic digest over the typed semantic item and its same-role occurrence — so a client-retained covered prefix collapses while a newly injected instruction survives, and the restored window is the preserved instructions, then the summary as one user message (the fixed line `The following is a summary of the earlier conversation:` ahead of the stored text, conversation context and never instruction authority), then the retained units whole, then the fresh suffix. Native state covered by the latest authenticated checkpoint is superseded; retained and fresh state restores at its recomputed position. A wrapped native window restores only against its originating provider instance, upstream model, and wire format, with any required system/tool prefix matching exactly; wrapping never establishes cross-vendor native compatibility. An explicit `can_export_native_summary` policy on the selected target permits readable Claude compaction text to become ordinary summary context only when neither ciphertext, tool changes, signed reasoning, nor opaque retained state would be lost. Otherwise incompatible native state fails explicitly. and cross-protocol continuation never applies the source protocol's placement rule to the target payload: a Responses checkpoint wrapping Claude on-demand state restores as the leading Claude block, its fresh suffix following once. Raw same-protocol native state replays verbatim to a compatible producer and is the caller's compatibility responsibility; carried to a producer that cannot consume it, it fails explicitly.

**Strategy decision order.** One executor resolves each carrying control, preferring the exact native mechanism, then a same-format adapter, then a cross-format adapter, then gateway summary — only eligible `supported` operations enter the ordering:

| Control | Order |
| :--- | :--- |
| Responses standalone | native standalone → gateway summary |
| Responses trigger | native trigger → standalone adapter (whole canonical window sealed in one carrier item) → on-demand adapter (block sealed in one carrier item; a native no-summary outcome fails the exactly-one-artifact contract explicitly) → gateway summary |
| Messages on-demand | native on-demand → standalone adapter (canonical window wrapped in a Messages carrier) → gateway summary |
| Responses automatic / Messages threshold | native passthrough when the mechanism is supported; otherwise request-boundary measurement, then a supported standalone/trigger/on-demand adapter over the older prefix with the pending turn retained, then gateway summary |

The `gateway_summary` strategy skips native selection for new compaction work — the mode for portable state across later provider changes — while existing native state still replays through the ordinary path. A dispatched native operation that reports a positively classified unsupported boundary (the definition's typed classifier, §5.9) before any artifact is committed or any caller-visible content is emitted falls back to summary inference exactly once; every other failure keeps its existing upstream semantics, and authentication, overload, network, and arbitrary rejections never fall back.

**Preparation order.** Completion requests carrying compaction state and standalone compact requests authenticate every recognizable gateway carrier before selecting a public route or concrete account. Authentication checks even superseded carriers; a later valid checkpoint cannot hide a damaged marker or unknown sealing key. The latest authenticated usable boundary is retained for the current request, with native null/no-op blocks ignored. Target-dependent producer/model/format compatibility and the existing window-restoration rules consume that same preparation, including a same-account unsupported-native fallback, without unsealing again. A carrier failure precedes model-not-found and performs no data-plane dispatch; valid state still requires an enabled public route. For a pool route, the active authenticated native window selects its exact producer member and upstream model regardless of priority or affinity-cache loss. A producer outside the pool or an incompatible model/format fails as inaccessible state; a member that cannot serve fails as bound-account unavailable, and its applicable quota blocks produce bound-account quota exhaustion using only its own reset bounds. Selection never substitutes another member. A later portable checkpoint releases a superseded native requirement. Direct routes retain their selected-target compatibility and explicitly configured readable-summary export behavior.

**Gateway summary content.** A gateway checkpoint replaces a covered prefix with an explicitly constructed window: the preserved instruction context, plus a summary of the eligible older history, plus the exact retained suffix. History groups into indivisible interaction units — a user message opens a unit, an assistant message opens one except inside a continuing tool exchange, and parallel assistant tool calls and their corresponding results join the same unit, and an orphan tool result is structurally invalid history that is rejected, never invented for. Compact-and-continue requests keep the pending user turn's unit through the end of history as mandatory retained state; compact-only requests may summarize a final user turn. Retention selects recent complete units backward under the retention budget — soft for mandatory state, including the contiguous suffix from the earliest retained image, never a license to truncate it — and when mandatory content leaves no older prefix to summarize, the request fails (`compaction_budget_exceeded`) instead of returning an unchanged checkpoint. Native state inside the summarized prefix fails (`compaction_inaccessible_state`); state inside the retained region rides in the checkpoint.

The summary inference is internal: one dispatch on the same routed provider/model through the normal credential path — never the public compact endpoint, never another provider — inside the request's own cancellation scope, with no fresh deadline per call. Supplied compaction instructions replace the default summarization prompt rather than appending to it; the first-party prompt's contract is to preserve the objective, the active instructions, the decisions, the constraints, the completed work, the unresolved work, the references, the tool facts, and the next actions, as text only. Tool selection is off for the inference (the definitions ride along only when retained native state requires their exact prefix), output schemas and stop sequences never propagate, and the output is bounded by the summary budget — the smaller of it and a compact-only caller cap; a later answer keeps its own original output budget. Only a complete, nonempty, tool-free summary ending normally is accepted: a refusal, truncation, empty text, or a model-requested tool call (which the gateway never executes) fails the compaction (`compaction_summary_unusable`), with no second attempt and no provider switching. Re-compaction consumes the reconstructed history — the previous summary is plain history text now — and emits a fresh checkpoint; sealing a new envelope is not another model call.

**Threshold workflow** (gateway-emulated automatic compaction). Native automatic operations keep their native accounting and timing; emulation has a documented request-boundary contract. One evaluation per request, over the restored window: the active context is measured, below the threshold the request runs as ordinary generation with the controls stripped, at or above it one compaction runs through a supported explicit native adapter when available, otherwise ordinary summary inference, and the compacted window is installed in memory — no re-evaluation, no loop, and never an invented answer or a converted compact-only request. A configured Messages native token counter measures the restored window first, including replayed native artifacts; counter failure falls back to the text estimator. Otherwise the measurement is the documented gateway estimate `ceil(utf8 bytes / 3)` over the deterministic typed rendering of the model-visible context — instructions, message text, tool-call fields, tool-output content, reasoning text, and the tool definitions' canonical JSON. It is an estimate, not a bound and not the model's tokenizer: without a successful native counter, image content and any opaque state item fail the measurement explicitly (`compaction_unsupported_measurement`) rather than counting transport bytes — a request whose context neither a successful native counter nor the estimator can represent is rejected, never approximated — and estimates never enter the accounting ledger. Defaults: a Messages threshold edit with no trigger keeps the protocol's 150,000; an emulated Responses automatic request with no threshold uses `floor(0.8 × capacity)` over the model's declared effective maximum input tokens, and a model that declares no such capacity rejects the request (`compaction_unknown_capacity`) instead of inventing a context window — a gateway default, never an OpenAI guarantee, while a native automatic request with no threshold keeps its upstream's own default. Native threshold streaming preserves a null-content opening block and delivers the full summary once in `compaction_delta`; on-demand streaming delivers the complete block in its start frame. A pause renders only the compaction result under the `"compaction"` stop reason; a continuation renders the checkpoint and then the actual generation. A completed checkpoint's validity is independent of what follows: if the continuation fails, the outer request fails — never a completed answer — and an incomplete checkpoint never invites history replacement.

**Gateway envelope and carriers.** Gateway state travels in one versioned envelope, `EnvelopeV1`: `version` (1), the gateway-minted `artifact_id` (stable across SSE and JSON representations), `replacement` — how the caller's window is consumed (`canonical_window`, `leading_window`, `historical_checkpoint`) — the `payload`, and an optional `visible_content_digest`. The payload is either a `gateway_summary` (the readable `summary_text`, the `preserved_instructions` with their roles, the exact `retained_units` as protocol-neutral messages, their `retained_state_items` with restored offsets, and the bounded `overlap_identities` the covered window is recognized by — never a copy of the summarized content) or a `native_window` (the exact native block or whole next window, its `producer_instance_id` — the originating provider instance, spelled `provider:{id}`, a credential refresh being no new producer — the originating `upstream_model_id`, `mechanism`, `native_format`, optional replay-prefix requirements, the window typed per producing family, and the exact retained pending-turn messages and state needed after a threshold adapter). Envelopes never carry credentials, URLs containing secrets, or the entire uncompressed conversation; wrapped native ciphertext stays native ciphertext, not a gateway-readable summary.

Carriers are sealed under authenticated encryption (XChaCha20-Poly1305, a fresh nonce per seal): the ASCII string `janusgate.compaction.v1.<key id>.<base64url(nonce || ciphertext)>`, the envelope JSON the plaintext, and the authenticated data binding the compaction domain, the key identifier, and — when the carrier binds visible content — that content's digest, so a carrier can never be consumed with content other than what it authenticated. Key material is configuration (§8): the first configured key seals and every configured key unseals by its carrier-carried identifier, so keys rotate by appending while existing artifacts stay readable, and removing a key intentionally invalidates its artifacts. An unknown key, a malformed carrier, failed authentication, or a mismatched visible-content binding is an explicit client-state error; with no `compaction` configuration section at all, any operation that would produce or consume a sealed carrier fails while native passthrough keeps working.

The outward carriers are protocol-shaped, never new types. The **Responses item carrier** is a `compaction` output item whose `encrypted_content` is the sealed carrier — one item per artifact; a wrapped standalone result carries the complete canonical native output window inside it. The **Messages block carrier** is a `compaction` content block whose `signature` is the sealed carrier and whose `content` is the readable summary when the envelope exposes one, else the fixed transport description `JanusGate compacted conversation state (encrypted); replay through JanusGate.` — a marker, never text sent to a model and never a substitute summary; the visible content is bound into the signature and verified on every unseal, no `encrypted_content` member is ever fabricated, and a null block keeps only its native no-op meaning. A gateway signature is recognized before any native treatment, unsealed and verified at preparation, and never forwarded to an upstream; real Anthropic signatures pass through untouched and are never resealed. Native same-protocol passthrough is unchanged by all of this: raw native state replays exactly as received, with no wrapping claiming provenance the raw contract never supplied.

| Caller state and selected upstream | Execution |
| :--- | :--- |
| Trigger control → supported native trigger | The request rides upstream; the lifecycle must carry exactly one completed compaction item |
| Trigger control → supported standalone operation | One native compact; the whole canonical window seals into one carrier item |
| Trigger control → supported on-demand operation | One native compact; the exact Claude block seals into one carrier item |
| On-demand control → supported standalone operation | One native compact; the whole returned window wraps in a Messages carrier |
| Any control → no compatible native operation | One gateway summary inference; the caller's own gateway carrier returns |
| Existing gateway summary → any target | Summary and retained history restore; ordinary target-format inference |
| Existing wrapped native window → its originating provider/model/format | The exact original state and retained suffix restore; incompatible targets require explicitly permitted readable export or reject |

**Failure decisions.** Every compaction failure renders through the shared error taxonomy (§6.7), its stable code riding the message; configuration and invariant violations stay fail-fast:

| Condition | Behavior |
| :--- | :--- |
| Structurally invalid history (an orphan tool result) | `compaction_unusable_history` (400); nothing discarded, nothing fabricated |
| Native state the target cannot access (cross-protocol, covered opaque state, an unusable native result) | `compaction_inaccessible_state` (400) |
| Gateway carrier failing unseal, verification, or visible-content binding | `compaction_invalid_gateway_state` (400); never summarized, never forwarded |
| Context unmeasurable for a threshold decision | `compaction_unsupported_measurement` (400); the threshold was not evaluated |
| Missing declared capacity for the gateway default threshold | `compaction_unknown_capacity` (400) |
| Mandatory state leaving no older prefix to summarize | `compaction_budget_exceeded` (400) |
| Refused, truncated, empty, or tool-producing summary | `compaction_summary_unusable` (502); no artifact |
| No sealing keys configured | `compaction_configuration_missing` (500, fixed message; the cause reaches the log only) |
| Positively classified unsupported mechanism/model | Fall through to the next mechanism of the decision order; the single summary fallback runs once no native stage remains, before artifact commitment (above) |
| Any other upstream failure | Existing upstream error semantics; no semantic fallback |
| Documented native no-summary outcome | Its own protocol semantics — neither error nor success artifact |
| Cancellation before a complete artifact | No successful compaction item or stop reason |

**Event ownership.** The caller sees one outer response or message lifecycle no matter how many internal dispatches ran; internal upstream response identifiers never start additional outer lifecycles. Item and block identifiers and positions are stable across live events and terminal bodies, and native compaction artifacts are emitted exactly once per identity (§6.2). Compact-only results are collected and validated before their success is published; internal summary text never leaks as ordinary answer deltas; a checkpoint renders before the answer in the stream and in the aggregated body alike, so a streaming client waits for the compaction to complete before its answer streams. The trigger lifecycle requires its successful completion — the missing-terminal degradation (§6.3) never applies to a compaction path.

**Usage and accounting.** Every actual data-plane dispatch on a compaction path — a native compact attempt, a gateway summary, a continuation generation — contributes its reported usage to request accounting: the compaction ledger holds compact and summary observations, and the answer aggregation holds continuation usage; a threshold counter's dispatch records no observation, its count being a measurement rather than billed usage; a dispatch the upstream answered without usage acquires no fabricated counts, and a threshold estimate is never an accounting row. The accounting row (§3) carries their combined billed totals — the sum over every dispatched iteration, a dispatched-but-failed native attempt included — and pre-dispatch failures still record no row. The client-visible usage is a separate view: a Messages response renders one `usage.iterations` entry per compaction iteration beside the protocol's top-level columns, which state the non-compaction iterations only — the message stage's usage, zero for a compact-only reply — so compaction input is never summed into the top-level input; a synthesized Responses result reports the participating calls' totals in the official fields, preserving native compact usage and `dropped_message_count` on passthrough. A replay request dispatches no compaction work and carries no compaction cost.

## 7. Management API (`/management-api/v0/*`)

The management API is versioned. Every version owns its routes, wire payloads, error taxonomy, and bindings, while the route contract, the `route!` declaration macro, and the bindings generator are shared by every version; the management API router mounts each version under its own prefix — currently `/management-api/v0`. Version 0's routes require authorization via `Authorization: <token>` (without any `Bearer` prefix) and are served by the version sub-router, which owns the version's errno-shaped 404 response; an unmapped path outside every version reaches no version's 404 response and is answered with the shared empty 404 (§2.2).

Every route declares its method, path, request payload type, and response payload type exactly once, next to its handler. Both payload types are concrete named types: a route that carries no request body declares an empty request type, and an inline-only type (such as `()`) is never a payload type. The bindings' route table (§7.3) is generated from these declarations.

Responses are JSON. Success responses use HTTP 200; errors use the structure from §4: `{"errno": <errno>, "message": <human-readable message>}`. Each version defines its own error taxonomy; the `errno` field is a numeric code from version 0's closed taxonomy, and each errno pins exactly one HTTP status — the two can never drift apart:

| errno | Category | HTTP Status |
| :--- | :--- | :--- |
| 1 | `invalid_request` — the request is malformed or unsupported | 400 |
| 2 | `unauthorized` — missing or invalid management token | 401 |
| 3 | `not_found` — unknown resource or path | 404 |
| 4 | `conflict` — the request collides with existing state | 409 |
| 5 | `upstream_error` — upstream provider failed or was unreachable | 502 |
| 6 | `internal` — gateway failure | 500 |
| 7 | `payload_too_large` — the request body exceeds the management body limit | 413 |
| 8 | `method_not_allowed` — the method is not registered on the addressed path | 405 |
| 9 | `unsupported_media_type` — the request body's content type is not JSON | 415 |

Request bodies are parsed strictly as JSON and must carry the `Content-Type: application/json` header; a request without it is rejected with errno 9. Every failure inside the management API version router renders this body — a rejected field, a malformed JSON body, an oversized body, a wrong body content type, an unmatched method, an unmapped path, a storage or upstream failure — so no response shaped by axum itself ever escapes the version's error domain.

The rest of this document names management errors by category and HTTP status (e.g. 404 `not_found`). Upstream failures on management endpoints always render errno 5 with HTTP 502 and the upstream status embedded in the message; a foreign upstream status is never forwarded verbatim. Failures whose cause is internal — engine failures, constraint details, lease failures, stored drift (errno 6, and constraint-violation 409s) — render their category's fixed message, so the cause is recorded in the log record and never reaches the caller. The outward OpenAI error taxonomy (§6.7) is an entirely separate error domain, with its own error type, and is never rendered on a management route.

Two strictness rules apply uniformly to every management request body.

**Names are non-empty.** Every request field naming an entity — the `name` a provider is created with, `upstream_id`, and explicit route `public_id` — must be a non-empty string; an empty name is rejected with 400 naming the field instead of falling through to a 404 lookup miss. Human labels (`providers.name`, `api_keys.name`) end there: their content — characters, case, length — is the administrator's choice and is never validated further; uniqueness comes from the schema, composition from this boundary.

**Machine-consumed text is routing-safe.** Exact upstream IDs and route public IDs are nonempty printable ASCII without whitespace, `/`, or `:`. Provider `model_prefix` follows the same composition rule but permits the empty string. Gateway API key secrets, upstream static keys, and instance base URLs are nonempty printable ASCII without whitespace. Base URLs additionally require `http://` or `https://`. Invalid management values return 400 naming the field; invalid discovered model IDs fail the complete refresh with 502 before storage. OAuth-extracted slots and base URLs are validated before storage. Existing providers are addressed by `provider_id`; unknown IDs return 404.

### 7.0 Design Rules

The route surface follows seven rules. Every future route is designed against them, so they are normative, not descriptive:

1. **One action per route.** A route's path names the resource collection and the action — `/providers:create`, `/oauth:start` — and its payload is flat. A request never selects a mode through a combination of fields; create-and-update and authorize-or-create endpoints do not exist.
2. **Fields are two-state, never three.** A field is either **always present** — required, and nullable only when it mirrors a nullable storage column (`expires_at`, capability overrides, an `api_log` row's `http_status` and five token columns) — or **absent-keeps** — omissible, and never `null`. A field that can be absent, `null`, and a value at the same time does not exist. The bindings render an always-present field as a required key (`T | null` for the nullable ones), and an absent-keeps field as `T?` — never `T | null | undefined`. One tolerance is explicit rather than accidental: for a required-nullable field, an omitted key parses as `null` (serde routes both spellings through one path, and under full-state semantics they share the single meaning "no value"), so the required key is a typing obligation on clients, not a parser rejection.
3. **Updates are full-state writes.** A `*:update` request states the complete desired readable state of its row; omitting a required field is a 400, not a keep. The only exception is write-only data — `api_key` and OAuth `credentials` — which is absent-keeps (absent keeps the stored secret, present replaces it) because it is never readable back.
4. **Variants are discriminated by type.** A payload whose shape varies by provider type is a `type`-tagged union with one variant per type, each carrying exactly the fields that type has — never a flat struct of optional fields whose validity a sibling field pins.
5. **Requests reference entities as `<entity>_id`.** A request that addresses an existing row names it by its own identifier — `provider_id`, `api_key_id`, `model_id` — on every route. The bare `id` appears only as a response row's own identifier.
6. **Every route answers `POST` with a JSON body.** No method carries semantics — reads and writes are distinguished by the action name, and a read's filters ride the body as typed fields instead of a query string. A no-argument request carries an empty `{}` object body.
7. **Responses carry only what the caller cannot derive.** The test is adaptive: it is relative to what the caller already works with, not to omniscience — given enough requests anything is knowable, so the question is whether the value is already among the data this API serves the caller. A response states assigned identity (a newly created row's `id`), server-minted values (`expires_at`, `authorize_url`), and state recomputed inside the write's transaction from inputs the caller does not hold (composed public model IDs — the provider's current prefix under the gateway-wide collision landscape). A request's own restated state is never echoed. A row carries its own stored fields plus the identity and label of whatever it references — `provider_id` and `provider` ride a model row so it stays self-describing — but never a verdict computed across resources: a status the caller can derive from rows it already fetches is derived by the client under the documented definition instead of being shipped per row (a model row carries `is_enabled` and `discovery_state`; the three-input conjunction of §3 is the client's to compute). So `providers:update` and `providers:delete` answer `{}`, a flow-begin route answers the grant-discriminated start facts, and `oauth:complete` answers the flow's observable state. Likewise, a `usage:list` row and a `usage:query` bucket carry only the log's own stored facts — ids, timestamps, statuses, token numbers — and never a name: labels resolve through the entity list routes the caller already works with (§7.1).

### 7.1 Endpoint Contracts

- **`POST /provider-pools:list`** — strict empty request `{}`; response `{provider_pools: [{id, name, model_prefix, is_enabled, members}]}`, ordered by name, with `members: [{provider_id, priority}]` ordered by ascending priority. Reads perform no upstream I/O.
- **`POST /provider-pools:create` / `provider-pools:update` / `provider-pools:delete`** — create requires `{name, model_prefix, is_enabled, members}` and returns `{provider_pool_id}`; update additionally requires `provider_pool_id` and returns `{}`; delete requires `{provider_pool_id}` and returns `{}`. Desired account references are validated within the mutation transaction; duplicate account IDs or priorities are client faults. A failed mutation leaves all prior pool state intact. Unknown references yield not-found; taken names and deleting a referenced pool yield conflict.
- **`POST /model-routes:list`** — strict empty request `{}`; response `{model_routes: [{id, public_id, is_enabled, is_automatic, target}]}`, ordered by public ID. Automatic entries and disabled or unavailable authored routes remain in this administration listing. Reads perform no upstream I/O.
- **`POST /model-routes:create` / `model-routes:update` / `model-routes:delete`** — create requires `{public_id, is_enabled, target}` and returns `{model_route_id}`; update additionally requires `model_route_id` and returns `{}`; delete requires `{model_route_id}` and returns `{}`. `target` is exactly `{"type":"direct","model_id":12}` or `{"type":"pool","pool_id":3,"upstream_id":"M"}`. Public and upstream IDs are nonempty printable ASCII without whitespace, `/`, or `:`. References use row IDs, never alternate names. Target changes preserve route identity and may retain the same public ID. Unknown references yield not-found; taken public IDs yield conflict. Pool targets do not require any member to have discovered the model at creation time. Updating or deleting an automatic entry returns 409; its provider prefix and physical model own that entry.

- **`POST /provider-definitions:list` / `provider-definitions:create` / `provider-definitions:update`** — list every stored definition version, register version 1 of a new definition, and register a definition's successor version. Each request and response carries the definition payload — `{format, inference, credential, provisioning?, discovery?, compaction?, quota?}` — the data §5 documents: optional `compaction` and `quota` members carry the whole remote-compaction and upstream-quota sections (§5.9–5.10), validated at the write boundary and stored as independent columns (§3). A definition is never updated in place: an update appends the successor version from the stored latest (§3).
- **`POST /providers:availability`** — strict request `{provider_id}`; response `{blocks, last_refresh}`. Blocks carry ordered `key`, typed `applies_to`, UTC-microsecond `observed_at`, and required-nullable `blocked_until`, sorted lexicographically by key tuple. `last_refresh` is `not_observed`, `succeeded {attempted_at, observed_at}`, `failed {attempted_at, reason}`, `unsupported {attempted_at}`, or `reset {attempted_at}`, tagged with snake-case `type`. Failure reason is exactly `credential_renewal | timeout | transport | upstream_rejected | malformed_observation`; no internal fences or foreign error strings are published. Runtime absence after restart is `not_observed`. The action performs no quota I/O.
- **`POST /providers:reset-availability`** — strict request `{provider_id}`, empty response. Advances generation/revision, clears all restrictions on that account shared across pools, and installs one automatic refresh interval of unknown/unblocked grace. An absent provider is 404.
- **`POST /providers:quota`** — strict request `{"provider_id": <integer>}`. Response `{"observed_at": <UTC microseconds>, "quotas": [<entry>]}`. Every entry carries a nonempty collision-free string tuple `key`, `label`, `scope` (`unknown` or `named {name}`), `window` (`unknown`, `duration {seconds}`, or `calendar {unit: month}`), `measurement` (`unknown`, `ratio {used_fraction}`, `counter {used, limit, unit}`, `remaining {remaining, unit}`, or `unlimited`), `routing` (`monitoring_only`, `all_models`, or `models {upstream_ids: string[]}`), and `reset` (`unknown`, `at {at: UTC microseconds}`, or `date {date: YYYY-MM-DD}`). No entries is a valid reading. Unknown provider yields 404/errno 3; no descriptor yields 400/errno 1 with `provider <id> does not declare quota viewing`; quota transport, non-2xx, JSON, or extraction failures yield 502/errno 5 without raw upstream bodies or secrets. Renewal retains its existing error taxonomy. Only inbound management authentication yields the connection-resetting 401/errno 2.
- **`POST /providers:list`** — request `{}`. Response `{"providers": [<provider>]}`, ordered by name. A provider is a union discriminated by its credential kind (rule 4): an `oauth` row renders `{"type": "oauth", "id", "name", "is_enabled", "provider_definition_name", "provider_definition_version", "format", "base_url", "expires_at"}` and an `api_key` row the same shape without `expires_at`. The definition pair is the exact immutable version the row is interpreted against, `format` is derived from it, and `base_url` is the nullable instance URL — present when the definition's expressions reference the base, `null` when they do not. Credentials are never returned.
- **`POST /providers:create`** — request `{"provider_definition_name", "provider_definition_version", "name", "model_prefix", "is_enabled", "base_url", "api_key"}`, every field required (rule 3): `base_url` is `null` when the definition's expressions never reference the base. Only definitions whose credential kind is `api_key` accept a direct write — OAuth credentials are minted by completing a flow, and a creation naming one is rejected. An unknown definition version yields 404; a `name` already taken yields 409. Response `{"provider": <provider>}` (rule 7).
- **`POST /providers:update`** — request `{"provider_id", "name", "model_prefix", "base_url", "is_enabled"}`, every field required; optional `provider_definition` carries the exact `{name, version}` rebind and optional `api_key` replaces static credentials. The transaction checks unique provider names, definition existence, credential-kind agreement, and the effective definition's base-URL requirement. Unknown references return 404; conflicting names or incompatible credentials return 409. Rename and serving-switch changes preserve every physical model and explicit route. Response `{}`.
- **`POST /api-keys:list`** — request `{}`. Response `{"api_keys": [<api_key>]}`, ordered by row id, where an api key is `{"id", "name", "key", "is_enabled", "access_control", "created_at"}`: the row's complete readable state, plaintext secret included — the administrator needs the secret to configure clients.
- **`POST /api-keys:create`** — request `{"name", "key", "is_enabled", "access_control"}`, every field required: the request is the complete key state (rule 3) except the server-assigned identity. An empty `name` or `key` is rejected with 400 naming the field; a `key` another row already holds is rejected with 409 without naming the value — the secret never reaches a rendered body. Response `{"api_key": <api_key>}`: the server-assigned `id` and `created_at` are the facts the caller cannot know (rule 7).
- **`POST /api-keys:update`** — request `{"api_key_id", "name", "key", "is_enabled", "access_control"}`, every field required: the request is the complete desired state of the row (rule 3) — a client renders the row, edits it, and sends the same shape back. The whole rewrite applies in one transaction that re-reads the row; an unknown `api_key_id` yields 404 and a `key` held by another row yields 409, and nothing is written. Response `{}`: the request already states the full readable state (rule 7).
- **`POST /api-keys:delete`** — request `{"api_key_id"}`; deletes the key, which stops authorizing traffic on the next request. An unknown id yields 404. Response `{}` (rule 7: deletion produces no readable fact).

Serving-key create/update require the complete `access_control` object: `default_access: "allow" | "deny"`, `owner_defaults: [{"type":"provider", "provider_id", "access"} | {"type":"pool", "pool_id", "access"}]`, and `route_overrides: [{"model_route_id", "access"}]`. Every nested member is required; null, omission, unknown fields, foreign decisions, and `inherit` are rejected. Empty arrays are valid. Readable policies sort provider defaults by ID, then pool defaults by ID, and route overrides by ID; input ordering is immaterial, and explicit equal-default decisions are retained. Duplicate typed owner or route references yield 400 `invalid_request`, even when their decisions agree; provider and pool IDs of the same number remain distinct. Missing references yield 404 `not_found`, taken secrets 409 `conflict`. Validation, secret uniqueness, ordinary fields, and full policy replacement share one bounded retryable transaction; failures leave every field and rule unchanged and failed creation leaves no key. Disabled owners and owners without entries are valid references. Management authentication and inventories remain independent of serving-key permissions.

- **`POST /providers:delete`** — request `{"provider_id"}`; deletes the provider and, via cascade, its models only (`ongoing_oauth_flows` rows are provider-agnostic and not attached to a provider, so a state completed after a deletion legitimately recreates the provider — see §3). An unknown id yields 404. Response `{}` (rule 7: deletion produces no readable fact).
- **`POST /oauth:start`** — request `{"provider_definition_name", "provider_definition_version", "name", "model_prefix", "base_url"?}`: the creation flow's definition reference and the new provider's naming, stated in full (rule 3). `base_url` is required when the referenced definition's expressions reference the base (§3) — the flow stores it, and the created provider's every dispatch evaluates those references against it — and a flow for such a definition without one is rejected with 400 naming `base_url`. The definition must carry OAuth credentials; its grant decides what the response carries — a union discriminated by `grant` (rule 4). An `authorization_code` flow answers `{"grant": "authorization_code", "authorize_url", "state", "expires_at"}` (the URL carries `state` and, when configured, the PKCE challenge; the TTL is 10 minutes). A `device` flow answers `{"grant": "device", "state", "expires_at", "user_code", "verification_uri"?, "verification_uri_complete"?}` with the expiry from the authorization response or the definition's fallback, and the gateway's poller begins exchanging on the stored schedule.
- **`POST /oauth:complete`** — request is a union discriminated by `grant` (rule 4): `{"grant": "authorization_code", "state", "code"}` or `{"grant": "device", "state"}`. The authorization-code form validates the paste (`code` trimmed; URL structure or whitespace is rejected) before consumption, then atomically consumes the flow and — on a failed exchange — the flow stays consumed: a retry requires a fresh `oauth:start`. The exchange runs, provisioning follows, and the provider write commits; the response is `{"status": "succeeded", "provider": <provider>}`. A `create` flow whose provider name another row already holds answers the name-taken 409 before the exchange runs — the flow stays consumed by the attempt, per the consume-then-fail order above. A completion naming a device state is rejected without consuming it. The converse rejects symmetrically: the device form naming an authorization-code flow's state is a grant mismatch rejected without consuming — such a row can never carry a terminal outcome, so without the check it would answer `pending` until its expiry. The device form reads the relational outcome without consuming a pending flow: `{"status": "pending"}` while the poller still exchanges; `{"status": "succeeded", "provider": <provider>}` or `{"status": "failed", "failure_code", "failure_message"}` once terminal — and a terminal row is consumed by exactly one successful read.
- **`POST /oauth:reauthorize`** — request `{"provider_id", "provider_definition_name"?, "provider_definition_version"?}`: begins a reauthorization flow for one existing provider, defaulting to the provider's current definition pair when no explicit target version is named (the target must carry OAuth credentials). The flow starts from the provider's stored slots and base URL; only the missing initial slots are initialized. An effective target definition — the explicit target, or the provider's own pair — whose expressions reference the base (§3) is rejected with 400 naming `base_url` when the provider row carries no base URL: the flow runs from the stored base, so such a target is unsatisfiable without one. The response is the same `grant`-discriminated union `oauth:start` returns. Successful reauthorization atomically replaces the credentials — and the definition reference when the target differs; the stored base URL joins the write only when the flow derives a replacement (the exchange's `base_url` fold or a provisioning extraction, §5.3), the begin-time base never being echoed back over the row; a failed flow leaves the provider on its old version. The two flow targets are disjoint because device flows complete without a second user step.
- **`POST /models:list`** — request `{}` or `{"provider_id"}`; unknown filters yield an empty list. Response `{"models": [<model>]}` contains physical inventory ordered by provider ID and exact upstream ID. Each row carries `id`, `provider_id`, `provider`, `upstream_id`, `is_enabled`, `discovery_state`, the four nullable discovered capability facts, and their four nullable administrator overrides. It carries no public name. Callers derive physical effective status from the model and provider switches and discovery state. Disabled and vanished rows remain visible.
- **`POST /models:discover`** — request `{"provider_id"}`; unknown accounts return 404. Renewal precedes upstream discovery. Empty model reports and incomplete pagination fail with 502 before storage. One transaction marks currently discovered rows vanished, then upserts each exact upstream ID: existing rows keep identity, serving switch, and capability overrides while discovery rewrites state and the four capability base facts; absent rows start discovered and enabled with the extracted facts. Unlisted manual rows remain untouched. Discovery never deletes rows and atomically maintains standalone or pool-owned automatic entries. Response `{"models": [<model>]}` returns all physical rows for the account from the committed refresh.
- **`POST /models:create`** — request `{"provider_id", "upstream_id", "is_enabled", "thinking_levels_override", "max_input_tokens_override", "max_output_tokens_override", "compaction_support_override"}`, every field required. The four overrides are required-nullable: reasoning levels use the closed vocabulary and canonical ordering (an empty array is known empty), token caps must be positive, compaction keys and support values use their closed vocabularies (explicit `unknown` suppresses lower facts; an empty map stores `NULL`). An absent natural key creates a manual physical model with unknown base facts. A vanished row is claimed as manual while retaining identity and the last discovered base facts. Existing manual or discovered rows return 409; unknown accounts return 404. Other accounts may independently store the same upstream ID. Automatic exposure is synchronized atomically: standalone providers use their own prefix; pooled providers contribute the model to each containing pool’s prefix namespace. Response `{"model": <model>}` returns the applied physical row.
- **`POST /models:update`** — request `{"model_id", "is_enabled", "thinking_levels_override", "max_input_tokens_override", "max_output_tokens_override", "compaction_support_override"}`, every field required; override validation matches creation. A short transaction updates the five administrator-owned columns only. State and base facts remain untouched, so the update cannot restore a vanished model. Unknown model IDs return 404. Response `{"model": <model>}` returns the applied physical row.
- **`POST /models:delete`** — request `{"model_id"}`; deletes the row. Deletion is administrator-only: discovery never deletes a row, and a deleted `discovered` row is rebuilt by the next discovery as a new row with a fresh, never-recycled identity (§3). An unknown id yields 404. Response `{}` (rule 7: deletion produces no readable fact).
- **`POST /usage:list`** — request `{"limit"?, "before"?, "filter"?}`, all three fields absent-keeps (rule 2): `limit` omitted means 100, a present value must lie in `1..=1000`, and any other value is rejected with 400 naming the field; `before` omitted starts at the newest row, and its semantics are `started_at < before` — an exclusive upper bound on the dispatch stamp in UTC microseconds, so the cursor row itself never reappears; an absent `filter` lists every row, and a present one is the shared accounting filter defined under `usage:query` below. Response `{"api_logs": [<api_log>]}`, ordered by `started_at` descending, the rowid breaking ties within a file. An `<api_log>` is the row's sixteen published columns, and the next page's cursor is the last returned row's `started_at`, which the client derives and the response never echoes (rule 7). The read fans out over the retained api-log files (§3 *ApiLog Store*): each file answers its own newest-first page under the filter and the cursor, and the pages merge on `started_at` — which never ties across files, because a row's own stamp selects its file. Two edges are accepted and documented: rows sharing one microsecond with a page boundary may be skipped (the cursor bounds the stamp, so the remaining rows of a boundary-crowding microsecond never open the next page), and rows finalized late with a `started_at` older than an already-passed cursor never appear in later pages. The row carries no name and no content column (rule 7), and both reads are never gated by the `api_logs` write switch (§3 *ApiLog*): existing api-log files stay readable while recording is off. A corrupt file fails the request explicitly; an empty store answers an empty page.
- **`POST /usage:query`** — request `{"group_by", "filter"?}`. `group_by` is required and is a set drawn from the closed dimension vocabulary `day | model | model_route | provider | api_key | endpoint_type | outcome | is_stream | http_status` — its element type is the validation, so any other value is rejected while the payload parses; a repeated dimension is rejected with 400 naming `group_by`; `[]` is legal and aggregates the whole selection into one total bucket whose `key` renders as `{}` — including when the selection matches no rows, so a zero-row total is one bucket of zeroes, never an empty list. Each bucket key is an object carrying exactly the requested dimensions — the key is a fixed object serialized in declaration order, never in the request's order — and the request order drives the bucket ordering.

  The `filter` — the one shared type `usage:list` carries too — is `{"from"?, "to"?, "api_key_id"?, "provider_id"?, "model_id"?, "model_route_id"?, "endpoint_type"?, "outcome"?, "is_stream"?, "http_status"?}`, every field absent-keeps (rule 2): a present-but-`null` field and an unknown field are rejected with 400. `from`/`to` bound `started_at` in microseconds, `from` inclusive and `to` exclusive; `is_stream` is a single boolean. Every other field is a non-empty array — an empty array is rejected with 400 — matched as SQL `IN`, so values within one field OR and the fields compose with AND. A multi-value array carries at most 100 values (one cap shared by all such fields); more is rejected with 400 naming the field. Filter values are never validated against stored rows: an unknown id or a never-recorded status matches an empty set, because a filter locates rather than addresses (rule 7). `http_status` is `NULL` exactly when no response was ever produced (§3 *ApiLog*), and `NULL` never matches an `IN` list, so there is no direct way to select those rows — `outcome` reaches them indirectly.

  Response `{"buckets": [{"key", "requests", "input_tokens", "output_tokens", "cached_tokens", "cache_write_tokens", "reasoning_tokens"}]}`, one bucket per distinct combination of the requested dimensions inside the filter, ordered by the key expressions in request order under SQLite's ordering — `NULL` first, `day` chronological (`YYYY-MM-DD`), ids numeric. The `key` is an object carrying exactly the requested dimensions: `day` (the UTC day), `model_id`, `model_route_id`, `provider_id`, `api_key_id`, `endpoint_type`, `outcome`, `is_stream`, and `http_status`, which renders `null` for the bucket the `NULL` rows form. The two enum dimensions use their recorded vocabularies (§3 *ApiLog*). `requests` counts rows; each token column is a `SUM` in which `NULL` never participates — unreported usage neither inflates nor deflates a total, an all-`NULL` bucket renders `0` — and every sum renders as a plain number. The aggregation runs per api-log file and merges in Rust (§3 *ApiLog Store*): counts and sums combine, buckets merge by key, and the ordering follows SQLite semantics — `NULL` first, enums by their stored spelling, numbers ascending — re-implemented as comparators over the closed dimension set. Day grouping is file-aligned, so day buckets never straddle files and the merge is exact. The response carries only the log's own numeric facts, never a name (rule 7).

### 7.2 OAuth Flow Semantics

- Authorization-code flows expire 10 minutes after creation; a device flow expires at its authorization response's lifetime or the definition's configured fallback, whichever applies. Completion of an unknown, expired, or already-consumed state yields 404.
- An authorization-code flow is consumed by the first completion attempt that observes it — including attempts whose exchange then fails — so a failed exchange burns the flow and a retry requires a fresh `oauth:start`. A completion rejected before consumption (an empty or malformed `code`, a grant mismatch) does not consume the row. A pasted `code` carrying callback-URL structure (`?`, `#`, `&`) or whitespace is such a pre-consume 400.
- A device flow is never consumed by its polling: the poller claims rows with a conditional lease and persists its schedule or its terminal outcome — and, the moment an exchange completes, the checkpoint its commit resumes from. A claim recovered with a checkpoint aboard resumes into provisioning and commit from it, so a restart between a completed exchange and its commit never re-presents the consumed device code — the lease alone prevents only concurrent double-exchange. The management client's completion reads the outcome without consuming a pending flow and consumes a terminal row exactly once; a failed terminal result carries only a gateway-owned code and message, never upstream bodies — `exchange_failed` marks a deterministic mapping failure of a completed exchange's decoded token response (the exchange succeeded but its token response was unusable), `provisioning_failed` and `commit_failed` diagnose the post-exchange pipeline, and `name_conflict` marks a create flow whose provider name another row claimed before the poller's commit.
- Expiry resolution is definition-driven: a provisioning-supplied expiry supersedes the response's token data, and the response's evidence is validated only when consulted — otherwise a positive reported `expires_in`, else a future `exp` claim on the access token, else the definition's `access_token_lifetime_seconds`, else `null`; no expiry, never a fabricated default. An `expires_in` that is not an integer is rejected at the response mapping; a consulted non-positive value, or a non-future `exp` claim, is a malformed token response.

### 7.3 TypeScript Bindings

- The management API's wire surface is published as TypeScript bindings behind the `management-api-typescript-bindings` feature: `cargo run --bin generate-management-api-typescript-bindings --features management-api-typescript-bindings -- <output-directory>` renders every wire payload type declaration plus the route table into one file per version, directly in the output target. The repository's own consumer is the `web/` workspace: `npm run generate-bindings` inside `web/` regenerates `web/src/management-api/generated/` from this working tree's local sources (see `web/README.md` §7.1).
- ts-rs's serde-attribute notices are switched off for the bindings dependency (`no-serde-warnings`), because the two attributes this repository uses that ts-rs 12 cannot interpret are both load-bearing and neither changes a published shape: `deny_unknown_fields` on an internally tagged request enum is the version's unknown-field rejection, and `deserialize_with` on an absent-keeps field is what makes absence keep the stored value instead of accepting `null` — the field's own `ts(optional)` already states its published shape. The notices would be permanent noise rather than signal; in exchange, a serde attribute that does change the shape (`with`, `serialize_with`, `into`) must pair with an explicit `#[ts(as = "...")]`, since nothing warns about the mismatch any more.
- Bindings are versioned with the routes they describe: each version's bindings are written into their own `<version>.ts` file in the output target (`<output-directory>/v0.ts`), and every route table key is the route's path within that version (`/providers:list`), so the file name — not the key — carries the version. One file holds everything a client of the version needs: the type declarations and the route table reference each other inside it, with no imports.
- Each version also publishes the wire types it owns besides its route payloads: its error body (`ErrorResponse`, the flat `{errno, message}` object) and its errno taxonomy (`ErrorCode`), the latter as a numeric TypeScript enum whose values are the errno discriminants tabulated above.
- Every closed set the API publishes is unordered and renders as a plain TypeScript union — the provider kinds, the upstream formats, the discovery states, and the request-accounting vocabularies (`ApiLogEndpointType`, `ApiLogOutcome`, `UsageGroupBy`) — so the bindings carry no ordering, const-tuple, or enumeration artifact of any kind.
- The route table types the path, method, request, and response of every route (`Path`, `Method<P>`, `Request<P, M>`, `Response<P, M>`), so a client addresses a versioned route without restating it. Every route's declared request and response types are published, the empty request and response types of body-less-result routes included; a payload type with no declaration of its own is a fatal declaration error rather than a route table referencing a type the file never declares.
- The unions of §7.1 render as their `type`-discriminated TypeScript unions — a TypeScript client narrows a provider by its `type` with exhaustiveness checking — and the two-state rule (§7.0) holds in the bindings verbatim: an always-present field renders `field: T` (or `T | null` only for the nullable mirror columns), and an absent-keeps field renders `field?: T`, never `T | null | undefined`.
- ts-rs owns the TypeScript declarations, which the generator collects and orders without parsing or rewriting. Tagged enums retain one member per Rust variant, including variants with identical fields. `ProviderResponse` has two credential-kind members (`oauth` and `api_key`); `UpdateProviderRequest` is the complete desired provider state with optional definition rebind and static-key replacement fields (§7.1).

## 8. Configuration & Deployment

### Configuration File (`config.jsonc`)

JanusGate is configured through a JSON file supporting comments (JSONC), supplied via the `-c` or `--config` command-line argument. The optional `pooling` object defaults as a whole and field by field to `quota_refresh_interval_seconds: 60`, `sticky_idle_timeout_seconds: 86400`, `sticky_retry_timeout_seconds: 60`, and `sticky_maximum_entries: 100000`. Every limit is positive; unknown fields and zero values are rejected during deserialization. Runtime operations use live limits after configuration reload, retaining process-local service identities. Quota deadlines recompute from the existing monotonic completion time and current interval rather than freezing a previous setting.

The root schema is: `log_level` (level filter, see below), `listen` (IP address and port, e.g. `"0.0.0.0:8080"`; an IP literal only — never a DNS name, because a listener address is a local binding fact, not a name to resolve), `tls` (optional; `certificate`, `private_key` — present serves HTTPS over TLS, absent serves plaintext HTTP), `database` (`path`, `max_connections`, `pool_timeout`), `management_api` (`token`, `cors`), `api` (`cors`), `api_logs` (optional; `path`, `retention_days` — the request-accounting store of §3 *ApiLog Store*, whose presence is the recording switch), `compaction` (optional; `keys` — the remote-compaction sealing keys of §6.8, whose presence is the switch for the gateway's sealed compaction artifacts), and `pooling` (optional; the live pool limits described above). Gateway API keys are database-managed (§7.1); the only other secrets in configuration are the compaction keys. Each `cors` object configures `allowed_origin` and `allow_private_network`: `allowed_origin` specifies allowed origins as a single string (e.g. `"*"` or `"https://dashboard.example.com"`) or an array of strings (e.g. `["*"]`, `["https://dashboard.example.com"]`, or `[]` to disallow all cross-origin requests), and `allow_private_network` is a boolean controlling Private Network Access (PNA) preflight responses (`Access-Control-Allow-Private-Network`). Refer to [`config.example.jsonc`](config.example.jsonc) for the configuration layout and available options.

Required fields state facts or secrets the gateway must never invent: `listen`, `database.path`, `management_api.token`, and — whenever the `api_logs` section is present — `api_logs.path`. Every other field carries a documented default and may be omitted: `log_level` (`info`), `database.max_connections` (4), `database.pool_timeout` (5000 ms), `api_logs.retention_days` (90), and each `cors` field (`allowed_origin` `[]` — no cross-origin requests; `allow_private_network` `false`); a whole `cors` object — or the whole `api_logs` or `compaction` section — may be omitted as well. The `compaction` section, when present, carries exactly `keys`: at least one entry, each an `id` (non-empty, unique, and free of `.`, the carrier separator it would break) and a `key` (standard base64 of exactly 32 bytes). The whole contract is enforced during deserialization — an invalid key set fails the parse with the offending value's line and column, exactly like any other schema rejection — and every parsed key is decoded to its material there, so a loaded section is valid by construction; the section's absence is itself valid: sealing is simply unavailable, so any operation that would produce or consume a sealed gateway carrier fails while native passthrough keeps working (§6.8).

### Configuration Loading, Errors, and Hot Reload

Configuration loading is one pipeline shared by startup and every reload: read the file, strip comments, deserialize strictly — unknown fields are rejected — and resolve the TLS material into a Rustls server configuration and the typed `compaction` keys into their initialized ciphers. A loading failure names its input and carries the deserializer's own message — the offending value with its line and column — verbatim; no hint layer sits on top. At startup a failure is fatal. Behind one global configuration object, an applied schema is deliberately leaked — it lives for the rest of the process, a few hundred bytes per reload, which is what lets every consumer read it as a plain dereference with no lock, guard, or copy — while the resolved TLS server configuration and compaction sealing keys are refcounted and swapped without accumulation. Consumers read the live state per request, per accepted connection, or per startup subsystem.

Once running, a watcher task (`notify`: inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows, feeding a Tokio channel) watches the parent directories of the configuration file and of the currently configured TLS certificate and private key — parent directories, so editors that replace files by rename are seen. Reloads are debounced: an event opens a 500 ms quiet window, every further event restarts it, and one unconditional reload — read, parse, resolve, apply — runs once the inputs fall quiet, so an editor's write-rename chain or a certificate rotation writing several files never reaches the parser in an intermediate state. What a reload moves:

- `management_api.token` — per request: the management authentication middleware reads the live schema. Gateway API keys are database-managed (§7.1): a created, rotated, or disabled key takes effect on the next outward request with no reload involved.
- TLS material, including the presence of the `tls` section — per accepted connection: each connection is served with the configuration current at accept time; established connections are unaffected.
- `log_level` — immediately: the global log filter moves with the reload (see Logging).
- `api_logs` presence — per dispatched request: the accounting write path reads the live switch at the dispatch mark, so removing the section stops recording at the very next dispatch, and existing api-log files stay readable either way (§3 *ApiLog*).
- `pooling.*` — per operation: the affinity cache's idle lifetimes and entry cap and the automatic quota check's refresh interval read the live limits at each use, so a reload moves them for the next prune, admission, or cadence evaluation (§6.5), while the cache's process-local service identities are retained.
- `compaction` keys — per compaction operation: the resolved sealing keys ride the applied configuration generation like the TLS material, and sealing and unsealing read the current generation at each use (§6.8), so an appended rotation key seals new artifacts at the very next operation while the retained older keys keep theirs readable, and removing a key — or the whole section — invalidates the artifacts it sealed at the next attempt to consume one.

Restart-only, because they are consumed when their subsystem is built at startup: `listen` (the bound socket), `database.*` (the open pool), `api_logs.path` and the section's addition (the api-log store is constructed at startup — same standing as `database.path`), and the two `cors` sections (the routers' CORS layers).

A reload that fails for any reason — an unreadable file, a rejected schema, TLS material that does not resolve — keeps the previously applied configuration and logs the failure at error level; a running gateway never dies over a reload. The applied schema, the resolved TLS server configuration, and the resolved compaction sealing keys are one generation behind a single cell and swap together or not at all: a configuration whose TLS material does not resolve keeps the previous schema as well. A reload that changes the TLS paths re-arms the watches.

### Logging

- The global logger is installed once during startup, after the configuration is parsed and before every other subsystem is initialized.
- The minimum severity a log record must carry to be emitted is taken **exclusively** from the root `log_level` configuration value, one of `off`, `error`, `warn`, `info`, `debug`, `trace` (case-insensitive). Environment variables — `RUST_LOG` in particular — are never consulted, and no per-target directives exist. The installed filter is open; the effective severity is the global maximum level, set from `log_level` at startup and moved by every configuration reload (§8), so the severity follows the live configuration without reinstalling the logger.
- Records are written to standard error as plain text without ANSI styling, one line per record in the format `<RFC 3339 UTC timestamp (millisecond precision)> <level padded to 5 characters> <target>: <message>`, for example:

  ```text
  2026-09-11T08:15:30.123Z INFO  janusgate::server: listening on http://0.0.0.0:8080
  ```

- **Severity policy**:
  - `error` — an operation failed on the gateway's or an upstream's behalf: a request failed with an upstream or internal error (logged once at the response boundary that renders it, with the model and provider context the boundary holds), an upstream stream aborted mid-flight (logged where the lazy upstream parser detects the abort), a request-accounting `INSERT` failed (logged once with the key, provider, and model row ids for attribution — neither the service nor the client's response changes, §3 *ApiLog*), the TCP accept loop failed an accept (retried with backoff), or a configuration reload failed (the previously applied configuration keeps serving).
  - `warn` — the gateway continues with degraded or anomalous-but-tolerated behavior: the best-effort `TCP_NODELAY` activation failed, a token-refresh lease could not be cleared after a failed refresh, an unauthorized management API request was rejected, a retention sweep failed to list the api-log directory or unlink an expired api-log file (logged and swallowed; the store keeps serving, §3 *ApiLog Store*), or a configuration-watching step failed transiently (the watcher task keeps running).
  - `info` — lifecycle and state changes: a database brought to a schema version (a fresh database's initial application or an outdated one's migrations), the listening socket, a completed token refresh, a configuration or TLS material reload applied, and every management mutation (a provider created, updated, or deleted, a provider-definition version registered — first or successor —, a provider pool created, updated, or deleted, a public model route created, updated, or deleted, an availability reset, an API key created, updated, or deleted, an OAuth flow started, completed, or reauthorized, a model created — including claiming a vanished row — a model discovery, a model update, a model deleted).
  - `debug` — per-request pipeline detail: the outward dispatch (public model, provider, upstream model, wire format, streaming mode), the upstream response status, client-fault rejections (malformed body, failed authentication, unknown model, conflicts), a compaction native attempt classified unsupported by its definition's classifier (the single summary fallback's cause, §6.8), connection-edge anomalies (failed TLS handshakes and connections that end with errors), and unauthorized outward requests.
  - `trace` — reserved; the gateway emits no `trace` records.
- Every rendered API error is logged exactly once — at the response boundary rendering it, or, for failures that become mid-stream error frames instead of an HTTP error response, at the lazy upstream parser that detects them. Log records never carry credentials, tokens, OAuth authorization codes or state tokens, prompt text, completion text, gateway compaction artifacts (summary text, sealed carriers, signatures), or upstream error bodies, matching the stateless-execution design (§1); a compaction failure's stable code and its failure reason name the failure, never its content (§6.8).
- Records emitted by dependency crates (`reqwest`, `hyper`, …) pass through the same global filter and appear under their own targets; there is no per-target suppression.

### Running the Server
```bash
cargo build --release
./target/release/janusgate -c config.jsonc
```

## 9. Development Skills

Rust changes are checked with `cargo fmt --all`, `cargo check --workspace --all-targets`, `cargo clippy --workspace --all-targets`, and `cargo test --workspace`, for both default features and `--all-features` (formatting is feature-independent). Clippy checks cover production and test targets without warnings. Large enum variants stay inline when their size does not affect hot-path allocation or storage; enum-local `allow` attributes explain that choice instead of adding a heap allocation solely for the lint. Configuration-sensitive tests serialize their complete execution against the shared reload fixture; their awaited paths never reacquire that test lock.

`skills-lock.json` is the version-controlled registry of third-party project skills. The entire root `.agents/skills/` directory is local-only and ignored, including downloaded skills and any locally authored skills stored there. Restore the registered skills from the repository root:

```bash
npx skills experimental_install
```

Restoration installs into `.agents/skills/`; it does not recreate agent-specific copies, links, or hook manifests. Record any additional required setup here rather than committing generated installation copies. The current Impeccable entry records its source and content hash without a Git ref, so restoration can fetch newer upstream content and change the lockfile. Review lockfile changes before committing them. Exact historical restoration requires installing from an immutable Git commit and confirming that the lockfile records that ref; the content hash alone does not pin the source revision.

Every `.impeccable/` directory is local-only and ignored, at the repository root and in nested workspaces. This includes configuration, design sidecars, surface briefs, critique reports, screenshots, caches, and runtime state; these files are not restored by the skill lockfile. Keep durable product and design decisions in the version-controlled `PRODUCT.md` and `DESIGN.md` files.
