# Management API

This file applies to `src/management_api/` and the
`generate-management-api-typescript-bindings` binary.

- The management API is versioned. A version is a submodule owning its routes, route registry, wire payloads, error domain, and router; the module itself mounts every version under its prefix, applies the cross-version policy (CORS), and enumerates the versions wherever they must be enumerated (mounting, bindings generation). A version's prefix is the single source of truth for its URL segment, its mount point, and its bindings file name.
- Everything version-independent is shared at the module level: the `Route` contract, the `route!` macro, and the TypeScript bindings generator. A version wraps `route!` to bind its own registry, so a route declaration names neither a registry nor a version.
- Every route is declared exactly once, next to its handlers, through `route!` (method, path, request type, response type). The version router is wired from those `Route` constants; a method or path string is never written anywhere else. The declaration is the route's whole contract: it must name both a concrete request payload type and a concrete response payload type — no route omits either, and no payload type is left implicit.
- A route's declared path is relative to its version's sub-router — the version prefix is never part of it.
- A version publicly exposes its wire surface — its route markers, its payload types down to nested rows and captured credentials, and its error body with its errno taxonomy — flattened at its own submodule, with public fields and both `Serialize` and `Deserialize`, so external Rust frontends can construct requests and parse responses. Handlers and storage stay private.
- Every route declares its request and response payload types explicitly, and both are always published in that version's bindings — the empty request type of a body-less route included. A route that carries no request body still declares an empty concrete request struct; `()` and every other inline-only type are never used as payload types, and the bindings generator treats a payload type carrying no declaration of its own as a fatal declaration error. Every payload type of a version is named and unique within it; shared shapes (the provider and model envelopes) are shared by reference, not duplicated.
- A version's error domain is entirely its own — taxonomy, response shape, logging classification — and is never shared with another version or with the outward OpenAI error type. Its failure type is the log-facing one: one concrete variant per failure, carrying the values that identify it (the rejected field, the unknown value, the provider id), never an opaque message string. The client-facing message is derived from the variant in the `ErrorResponse` conversion; a client fault's own display is its wire wording, while an internal cause renders its category's fixed message.
- Every failure the version's request lifecycle can produce converges into that failure type — a rejected field, a malformed body, a body over the version's limit, a wrong body content type, an unauthorized request, an unmatched method — so no axum-shaped rejection escapes. Request bodies extract through axum's `Json` wrapped in axum-extra's `WithRejection` with the version's error as the rejection type, and handlers return `Result<Json<..>, Error>`; the error's `IntoResponse` implementation is the single boundary that logs every failure exactly once and renders it.
- serde attributes define the wire truth, and the feature-gated `ts_rs` derives must stay aligned with them: an absent-keeps field (omission keeps stored state) deserializes through the shared `absent_keeps` adapter with `#[serde(default)]` and carries `#[ts(optional)]` — an explicit `null` on it is rejected; a required-nullable field (mirroring a nullable storage column) uses `Nullable<T>` with an explicit `#[ts(type = "... | null")]`, whose omitted key parses as `null` — the documented tolerance of README §7.0 rule 2, because serde routes both spellings through one path. A tri-state field — absent, `null`, and value at once, with three distinct meanings — never exists.
- All TypeScript bindings machinery (the linkme route registries, the `ts_rs` derives, the generator) lives behind the `management-api-typescript-bindings` feature; the normal server build must not depend on it. Each version's bindings are generated from its own registry, plus the payload types that version declares besides its routes (its error body), into that version's own single `<version>.ts` file directly in the output target — every route's declared request and response type declaration, the empty ones included, and the route table in one file, no imports.
- Every closed set a version publishes — the provider kinds, the upstream formats, the discovery states — renders as a plain TypeScript union; all published closed sets are unordered (README §7.3), so no ordering or enumeration artifact exists in the bindings.
